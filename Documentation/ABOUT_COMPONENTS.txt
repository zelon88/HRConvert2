--About Components--

HRConvert2 is one core & a small number of detachable components.

convertCore.php is the core. It converts files, serves the interface & answers the command
line. It is the only file a web request ever reaches, & it runs on its own.

A COMPONENT ADDS A CAPABILITY. IT IS NEVER LOAD BEARING FOR CONVERSION.
Every component can be deleted from an installation & every conversion still works. What is
lost is the capability that component provides, & the loss is reported rather than silent.

  Resources/coreManager.php                     Resource awareness & the listener.
  Resources/SetupCore/setupCore.php             Installation & configuration.
  Resources/DependencyCore/dependencyCore.php   Dependency management & the supply chain audit.
  Resources/PipelineCore/pipelineCore.php       Conversion pipeline dispatch.

Each core lives in a folder of its own, the same way ScanCore does. Configuration files do
not. config.php, depends.php & versionInfo.php stay in Resources beside each other, because
a configuration file is data an administrator edits & is not part of a component.

coreManager.php has not moved into a folder & keeps its name for historical reasons. It is
a Core by every test in this document.

TWO KINDS OF THING LIVE UNDER Resources/Pipelines & NEITHER IS A CORE.

  Resources/Pipelines/<Family>/pipelineConfig.php   What a pipeline declares.
  Resources/Pipelines/<Family>/pipeline.php         The converter itself.
  Resources/Pipelines/Shared/<name>.php             Code two pipelines both need.

A pipeline is verified by Pipeline Core rather than by the core, which makes it a
sub component. Pipeline Core pins each one exactly, the same way the core pins Pipeline
Core. See ABOUT_PIPELINE_COMPONENTS.txt.

The converter was called pipelineCore.php until v3.8.8. That name collided with the
dispatcher & described the wrong thing, because a converter owns no domain & is not called
on demand by the application. It is pipeline.php now.

--About Cores--

A CORE IS A COMPONENT THAT OWNS A DOMAIN & EXTENDS THE OPERATIONAL SCOPE OF THE APPLICATION.

The core converts files & serves the interface. A Core adds a whole area of responsibility
the core does not have on its own.

  Setup Core        Installing, configuring, repairing & the service unit.
  Dependency Core   Dependencies, capability detection & the supply chain audit.
  Pipeline Core     Which conversion families exist & which one gets a given conversion.
  Core Manager      Resource awareness & the manager processes.

FOUR PROPERTIES SEPARATE A CORE FROM ANYTHING ELSE IN THIS APPLICATION.

  1  IT OWNS A DOMAIN. Everything about installation is in Setup Core & nowhere else.
     Two files understanding the same thing is two implementations kept in step by hand.

  2  IT RUNS INSIDE THE CALLER. It is called, it works, it returns. A Core starts nothing
     that outlives the call. Core Manager starts processes, which is why the processes it
     starts are described separately in ABOUT_MANAGERS.txt rather than here.

  3  IT IS OPTIONAL. Every Core can be deleted & the application still converts files.
     What is lost is the scope that Core provided, & the loss is reported rather than silent.

  4  IT EXTENDS SCOPE RATHER THAN CAPABILITY. A dependency gives the application a new
     format. A pipeline gives it a new conversion. A Core gives it a new thing it is able
     to be responsible for, which is a larger claim & is why there are only four.

A CORE IS NOT A MANAGER, & THE WORD MANAGER MEANS SOMETHING ELSE IN THIS APPLICATION.
A Core is a file that is loaded. A manager is a role a long lived process runs under, with
a socket, a supervisor & a place in a budget. Core Manager is the Core that starts them.
core-manager, resource-manager, worker-manager & request-manager are the managers, & none
of those is a file. See ABOUT_MANAGERS.txt.

That distinction decides what moves when this machinery is shared with another application.
The managers have nothing to do with converting files & would serve a virus scanner or a
job dispatcher unchanged. The Cores would not.

--About The Rules Every Component Follows--

FOUR RULES, & ALL FOUR ARE ENFORCED IN CODE RATHER THAN BY CONVENTION.

  1  A COMPONENT DEFINES FUNCTIONS & DOES NOTHING ELSE.
     No component runs anything at load. The core decides when to call into it. A component
     that acted on being loaded would act during an installation check, a version report &
     every other place a version is read.

  2  A COMPONENT REFUSES TO RUN ON ITS OWN.
     Every component begins by testing $CoreLoaded & halting when it is not set. A component
     reached directly over HTTP refuses rather than executing with no configuration, no
     secret & no session.
     THIS ONE HALT CANNOT USE quickDie. Reaching that line means convertCore.php was never
     loaded, so quickDie is not defined & calling it would replace a clear refusal with an
     undefined function error.

  3  A COMPONENT DECLARES ITS VERSION IN A VARIABLE THE CORE CAN READ WITHOUT EXECUTING IT.
     The core reads the version out of the file with a regular expression. A mismatched
     component may define functions this core cannot call safely, so it must be judged
     before it is loaded, never after.

  4  A COMPONENT IS MATCHED EXACTLY.
     Not a minimum. The same rule a GUI folder & a language pack follow. A component built
     for another release may accept an argument this core has dropped, or omit one it now
     needs, & neither is detectable at runtime.

--About How A Component Is Loaded--

verifyCoreComponent() does all of it, for every component, in one place.

  Accepts   the component name, its path relative to Resources, the name of the variable it
            declares its version in, & the version this core requires.
  Returns   an availability boolean & the detected version.

The sequence is always the same.

  1  Test that the file exists. Absent is reported & is not an error.
  2  Read the file as text. Never execute it.
  3  Extract the version with a regular expression.
  4  Refuse a component that reports no version. An unknown build cannot be cleared.
  5  Refuse a component whose version is not an exact match.
  6  require_once the file.
  7  Publish the detected version as a global under the name the component uses.

STEP SEVEN EXISTS BECAUSE A require INSIDE A FUNCTION LANDS ITS ASSIGNMENTS IN THAT FUNCTION.
A component sets its version variable at the top of its own file. Loaded from inside a
function, that assignment is local to the function & is invisible everywhere else, so the -v
argument reported an empty version for a component that was loaded & working perfectly.

Three components once had three near identical copies of this logic. Collapsing them into
one function is what surfaced that bug.

--About When A Component Is Loaded--

NOT AT BOOT. ON DEMAND, BY WHATEVER NEEDS IT.

A web request never installs, configures or manages dependencies, so it never pays to read a
component it will not call. Only the Core Manager is resolved during verifyInstallation, &
only because resource awareness affects a conversion.

  coreManager.php        Resolved during verifyInstallation when resource awareness is on.
  setupCore.php          Loaded by --config, & by -fp when it installs the service unit.
  dependencyCore.php     Loaded by --setup.
  pipelineCore.php       Resolved in the main logic, directly after verifyGlobals().

PIPELINE CORE IS THE EXCEPTION TO ON DEMAND & THE REASON IS ORDERING.
It is resolved on every request that could convert something, because a conversion cannot
wait for it. It is resolved AFTER verifyGlobals() rather than during verifyInstallation,
because enumerating pipelines warns about every one it refuses & those warnings are
worthless before there is a logfile to write them to.

EACH COMMAND LOADS ONLY WHAT IT NEEDS.
--config needs Setup Core. --setup needs Dependency Core. Only --install-complete &
--reinstall-existing need both. An operator asking what is installed must not be stopped
because a component they are not using is absent, which is exactly what an earlier release
did by loading Setup Core before every --setup option.

--About Version Pins--

TEN PINS. EVERY ONE OF THEM IS AN EXACT MATCH EXCEPT WHERE NOTED.

  $RequiredConfigVersion           config.php                    MINIMUM. A newer config carrying
                                                                 every required setting is fine.
  $RequiredCoreManagerVersion      coreManager.php               EXACT.
  $RequiredSetupCoreVersion        setupCore.php                 EXACT.
  $RequiredDependencyCoreVersion   dependencyCore.php            EXACT.
  $RequiredPipelineCoreVersion     pipelineCore.php              EXACT.
  $RequiredDependsVersion          depends.php                   EXACT.
  $RequiredSecretVersion           the install secret file       EXACT.
  $RequiredGuiVersion              every UI folder               EXACT.
  $RequiredLanguageVersion         every language pack           EXACT.
  $RequiredConfigScript            the bootstrap script          EXACT.

Pipeline Core carries pins of its own for every pipeline & every shared module it accepts.
Those are listed in ABOUT_PIPELINE_COMPONENTS.txt rather than here, because the core knows
nothing about them & a pipeline is verified one level down.

RAISE $RequiredPipelineCoreVersion WHENEVER A PIPELINE IS ADDED, REMOVED OR RAISED.
Pipeline Core holds the pin list, so a pipeline moving means that list moved.

RAISE $RequiredSetupCoreVersion WHENEVER $RequiredConfigVersion IS RAISED.
Setup Core holds the model of every setting config.php declares. Forgetting does not break
anything immediately, which is the point. A setting the model does not know is reported as
unaccounted, can still be edited by hand, & simply cannot be reset.

RAISING $RequiredSecretVersion ROTATES THE SECRET & INVALIDATES EVERY SESSION IN PROGRESS.
Do it deliberately, not as part of a routine version bump.

Compare version numbers NUMERICALLY, never as strings. A string comparison ranks 24.2 below
7.6 & ranks 3.10 below 3.9. Strip a leading v first. Casting 'v3' to an integer yields 0,
which silently reduces a three part comparison to a two part one. compareVersionMinimum()
does all of this & is the only correct way to compare two versions in this application.

Run  php convertCore.php -v  to see every pin, with what is required beside what was found.
A mismatch does not stop the core. It silently removes whatever that component provides, &
that report is the only place the loss becomes visible.

--About What Happens When A Component Is Missing--

THE CORE DEGRADES. IT DOES NOT BREAK.

  No Core Manager       Conversions run without resource awareness. Every budget request is
                        approved by default. --status, -l & -k report the component missing.
  No Setup Core         --config refuses & explains why. Everything else is unaffected.
  No Dependency Core    --setup refuses & explains why. Conversions are unaffected.
                        Capability detection is unavailable & declared formats are trusted.
  No Pipeline Core      NO CONVERSION RUNS AT ALL. Uploading, downloading, deleting &
                        virus scanning continue. Every conversion family reports 34005.
                        This is the one component whose absence is not a partial loss,
                        because convertCore.php stopped converting anything itself once
                        the last family moved out of it.
  No depends.php        Dependency management is unavailable. Conversions are unaffected.
  No bootstrap script   Nothing at all. It is a convenience, not a dependency.

--Require Resource Awareness-- inverts this for the Core Manager only, for an operator who
would rather refuse work than accept work they cannot account for.

A COMPONENT THAT IS PRESENT BUT MISMATCHED IS TREATED EXACTLY LIKE ONE THAT IS ABSENT.
There is no partial acceptance & no attempt to work around a version difference.

--About The Bootstrap Script--

Documentation/Build/hrconvert2-setup.sh is a component in every sense except that it is not
PHP & cannot be version checked the same way.

It does ONE job. It makes sure PHP exists, then hands every argument to convertCore.php.
Every decision about installing, configuring, updating or repairing lives in Setup Core.

A CONFIGURATION UTILITY WRITTEN IN BASH WOULD BE A SECOND IMPLEMENTATION OF THE SAME
UNDERSTANDING, KEPT IN STEP BY HAND. That is the whole reason it is this thin.

It carries a SCRIPT_VERSION & a DisabledByCore line. The Resource Manager compares the
version against $RequiredConfigScript on its sweep. A script that does not match has
DisabledByCore rewritten to TRUE, so it refuses to run & says why. It is never deleted & is
not otherwise altered, so an operator can read exactly what was disabled. A script that is
later replaced with a matching version is re-enabled on the next sweep.

--About Adding A Component--

Five things, in this order.

  1  Create Resources/YourCore/yourCore.php.
  2  Open it with the $CoreLoaded guard, copied from any existing component.
  3  Declare $YourCoreVersion near the top, where it can be seen.
  4  Add $RequiredYourCoreVersion to verifyInstallation, with a comment saying what raises it.
  5  Call verifyCoreComponent() from whatever needs it, on demand.

Nothing else. No registry, no manifest & no change to any existing component. Step five is
one line, which is the entire point of collapsing the three loaders into one.

Then add it to showVersionInfo, so -v reports it beside the others. A component nobody can
see the version of is a component nobody can diagnose.
