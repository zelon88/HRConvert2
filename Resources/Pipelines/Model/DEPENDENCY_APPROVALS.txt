  Audit answers. Every one is a judgement a person records here.
    1a Security design is amenable to ours        Yes, procedurally. The Open Asset Import Library features an active public repository on GitHub,
                                                  maintains a formal `SECURITY.md` tracking policy, and incorporates Google Fuzzer code blocks (`fuzz/`)
                                                  directly inside its source tree to proactively map stability bugs. However, the core library architecture
                                                  is written in low-level C/C++ handling complex, highly volatile, and untrusted binary mesh geometries,
                                                  presenting a high structural parsing attack surface.
    1b Recent CVEs, issues or exploits            High Risk / Frequently Targeted. Because it parses 40+ distinct 3D file structures, it is a premier fuzzing target.
                                                  Recent vulnerabilities (such as CVE-2024-41180, CVE-2023-45842, and CVE-2023-45843) expose recurrent heap-based
                                                  buffer overflows, out-of-bounds array reads, and null-pointer dereferences inside its asset-loader modules
                                                  (specifically tracking FBX, Blend, and OBJ parsers). Malformed file uploads can trigger instant thread crashes
                                                  or arbitrary code execution.
    1c Development activity & breakage risk       Highly Active / Low-Moderate Breakage Risk. Upstream maintainers actively roll patches and optimizations
                                                  (version 5.x tiers are highly stable). The command-line parsing operations provided by `assimp-utils`
                                                  (like the `assimp` CLI structure) remain stable, meaning the risk of breaking internal HRConvert2
                                                  execution syntax during point-version patches is very low.
    1d What it needs to function                  Resource Intensive / Stateless Matrix. Requires significant memory blocks to load large coordinate vectors,
                                                  polygon faces, and material attributes into an in-memory data tree. Operates completely as a stateless console
                                                  utility requiring local file system read/write rights to map target files. Links directly against system C++
                                                  libraries and standard glibc streams.
    1e Can it be sandboxed or isolated            Highly Amenable. 3D geometry format translation is a completely self-contained, mathematical array transformation loop.
                                                  It requires no host networking channels, administrative root execution privileges, or external inter-process
                                                  communication (IPC). It isolates perfectly inside a strict, networkless Bubblewrap sandbox jail mapping exclusively
                                                  the designated file workspace.
    1f Security options & hardened configuration  None native to the binary utility. Hardening must be applied entirely from the outside via the environment orchestration.
                                                  The utility must be wrapper-invoked inside a strict Bubblewrap namespace configuration that drops all Linux kernel
                                                  capabilities, mounts an isolated tmpfs path, and limits max file payload metrics before execution.
    1g Could another dependency do this better    No. For converting across dozens of obscure, proprietary, and open 3D assets (FBX, Collada, STL, GLTF) inside a single, unified
                                                  tool repository, Assimp is functionally irreplaceable for HRConvert2's 3D Models subsystem. The parser risks
                                                  must be explicitly managed via strict Bubblewrap encapsulation.
    1h Origin & supply chain risk                 Low-Medium Risk. Maintained by a prominent global community of graphics and game development engineers.
                                                  Source code pipelines and issue logs are completely open on GitHub. Because this is an `apt` installation type,
                                                  the primary supply chain validation and patch-management burden is safely handled by your Linux distribution's security team.
    1i Dependency traps for existing installs     The Format-Specific Overflow Trap. Attackers targeting file conversion servers frequently look for applications using Assimp
                                                  because they can mask an exploit inside an obscure 3D file extension format that the application maintainer did not realize
                                                  the underlying Assimp binary was compiled to automatically parse. External sandbox encapsulation is mandatory to neutralize this vector.
    2a System package versus a source build       System Package Preferred. Installing via `apt` ensures that the platform handles complex multi-architecture C++ compilation loops
                                                  automatically, matches library configurations safely against the host OS ecosystem, and delivers rapid security patches
                                                  downstream via standard automated server package updates.
    2b Build flags, libraries & features          Default package compilation flags applied by apt are sufficient when fully encapsulated by Bubblewrap.
    2c Minimum version & version edge cases       Strictly 5.0+ as defined by the manifest facts to ensure robust modern asset parsing pipelines and built-in protection mechanisms
                                                  against legacy 4.x branch structural geometry vulnerabilities are present.
    2d Licensing implications of the build        Modified BSD-3-Clause (Highly Permissive). A business-friendly open-source copyright framework. It allows static linking,
                                                  imposes zero copyleft contamination threats, and carries no redistribution traps for internal or commercial enterprise utilization.
    3a Distribution method                        Standard distribution native package manager repositories (apt).
    3b Download source used                       Official distribution mirror networks.
    3c How an installer obtains this version      Automated package fetch via the platform manager utility (apt-get install -y assimp-utils).
    3d Inspection of any bundled binary or code   Inspection Practical but Complex. Large, sprawling C++ codebase optimized for geometric data parsing matrices,
                                                  requiring domain-specific graphics pipeline knowledge to audit low-level parser loops effectively.
    3e Sanity check of the build system           Relies entirely on the distribution package builder's native architecture integration tests.
    3f Build script provided                      No.

                                                  Distributed with cryptographic tag signatures and heavily scrutinized open-source review pipelines.
    1i Dependency traps for existing installs     The Setuid Trap. If the target host kernel disables unprivileged user namespaces by default,
                                                  bwrap requires a root-owned setuid bit to function, expanding the local attack surface if misconfigured.
    2a System package versus a source build       System Package Preferred. The distribution-provided package is kept patched, stable,
                                                  and correctly mapped to the underlying platform's specific namespace permissions.
    2b Build flags, libraries & features          Standard hardened compile blocks. Ensure libseccomp filtering is explicitly compiled in (--enable-seccomp).
    2c Minimum version & version edge cases       Strictly 0.4.0+ as defined by the manifest, though 0.8.0+ is strongly recommended to support modernized flags.
    2d Licensing implications of the build        LGPL-2.0 is highly amenable. Safe for commercial and internal utility wrapping without copyleft traps.
    3a Distribution method                        Native package repositories (apt) and official GitHub source releases.
    3b Download source used                       Upstream GitHub assets or native distribution mirrors.

    1f Security options & hardened configuration  None native to the utility. Hardening must be applied completely from the outside. The utility must be wrapped
                                                  inside a strict Bubblewrap namespace configuration that drops all Linux capabilities, forces an empty tmpfs layout,

    1g Could another dependency do this better    Yes. Upstream explicitly recommends **PyMeshLab** (the Python-bound filter engine) as a direct replacement
                                                  for the deprecated `meshlabserver` binary. If the platform configuration allows Python bindings, migrating
                                                  to PyMeshLab is highly recommended to align with upstream maintenance tracks.
    1h Origin & supply chain risk                 Low-Medium Risk. Maintained transparently by the Visual Computing Lab of ISTI-CNR.

    2a System package versus a source build       System Package Acceptable ONLY to avoid the extreme complexity of compiling legacy desktop Qt frameworks

                                                  data science and machine learning infrastructure.
    1b Recent CVEs, issues or exploits            Low Risk. Because NumPy handles multi-dimensional array memory allocation via optimized C code, it occasionally faces

    1f Security options & hardened configuration  Native controls are managed via implementation limits. Ensure Python scripts importing NumPy handle array sizes

    1h Origin & supply chain risk                 Low-Medium Risk. Maintained by the trusted upstream NumPy Team. Source assets are cryptographically signed
