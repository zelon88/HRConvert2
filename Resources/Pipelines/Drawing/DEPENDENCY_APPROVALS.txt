  Audit answers. Every one is a judgement a person records here.
    1a Security design is amenable to ours      Yes. Designed specifically as a minimal, unprivileged attack surface reduction boundary.
                                                Maintained by Red Hat/GNOME developers with structured disclosure and explicit security modeling.
                                                Codebase is exceptionally tight, readable, and avoids macro or parsing complexity.
    1b Recent CVEs, issues or exploits          Extremely clean track record. No high-severity RCE or jailbreak flaws in years.
                                                CVE-2019-12439 was a minor local info leak due to a temporary file descriptor layout bug.
                                                Most environment breakout vulnerabilities stem from the underlying Linux kernel namespaces rather than bwrap.
    1c Development activity & breakage risk     Highly Active / Low Breakage. Maintained continuously under the containers organization on GitHub.
                                                CLI arguments and core runtime flags are frozen and stable; update regressions are virtually non-existent.
    1d What it needs to function                Kernel Namespace Support. Relies directly on user, mount, IPC, PID, and net namespace system calls.
                                                Requires unprivileged user namespaces enabled on the host (user.max_user_namespaces > 0).
                                                Dynamically links against standard glibc; needs no background daemons or permanent disk writes.
    1e Can it be sandboxed or isolated          N/A. This is the sandbox controller itself. It is transient and destroys its environment upon exit.
    1f Security options & hardened configurationMaximal isolation flags must be applied when executing sub-commands: --unshare-all, --uid, --gid,
                                                --ro-bind for system runtime folders, and explicit --seccomp filters to drop dangerous syscall architectures.
    1g Could another dependency do this better  No. It is the gold standard for rapid, unprivileged, daemonless command sandboxing on Linux.
                                                Alternative tools like Minijail lack the widespread distro adoption, while Podman/Docker bring major daemon overhead.
    1h Origin & supply chain risk               Very Low Risk. Maintained by primary enterprise Linux contributors (Fedora, Red Hat, SUSE).
                                                Distributed with cryptographic tag signatures and heavily scrutinized open-source review pipelines.
    1i Dependency traps for existing installs   The Setuid Trap. If the target host kernel disables unprivileged user namespaces by default, 
                                                bwrap requires a root-owned setuid bit to function, expanding the local attack surface if misconfigured.
    2a System package versus a source build     System Package Preferred. The distribution-provided package is kept patched, stable, 
                                                and correctly mapped to the underlying platform's specific namespace permissions.
    2b Build flags, libraries & features        Standard hardened compile blocks. Ensure libseccomp filtering is explicitly compiled in (--enable-seccomp).
    2c Minimum version & version edge cases     Strictly 0.4.0+ as defined by the manifest, though 0.8.0+ is strongly recommended to support modernized flags.
    2d Licensing implications of the build      LGPL-2.0 is highly amenable. Safe for commercial and internal utility wrapping without copyleft traps.
    3a Distribution method                      Native package repositories (apt) and official GitHub source releases.
    3b Download source used                     Upstream GitHub assets or native distribution mirrors.
    3c How an installer obtains this version    Standard automated package management fetch (apt-get install -y bubblewrap).
    3d Inspection of any bundled binary or code Inspection Practical. Clean, straightforward, minimal C files without obfuscation or macro masking.
    3e Sanity check of the build system         Fully automated via native continuous integration testing suites embedded in the upstream source.
    3f Build script provided                    No. Managed safely via the native OS package controller.

--Dia--

  Approval record
    Status                                      ADOPTED

  Manifest facts, read from Resources/Contract/depends.php
    Binary                                      dia
    Install type                                apt
    Package                                     dia
    Minimum version                             0.97
    Required                                    NO
    Subsystem                                   Drawings
    License                                     GPL-2.0
    Depends on                                  Bubblewrap
    Source                                      https://wiki.gnome.org/Apps/Dia
    Purpose                                     Converts diagrams.

  Audit answers. Every one is a judgement a person records here.
    1a Security design is amenable to ours      No. Dia is an abandoned utility whose source code infrastructure has been archived by GNOME. 
                                                It has no active security team, no formal vulnerability disclosure program, and does not accept or track modern advisories. 
                                                The application was built during an era lacking modern secure coding standards, making it highly susceptible 
                                                to adversarial input manipulation.
    1b Recent CVEs, issues or exploits          High Risk / Abandonware. While it lacks frequent new CVE assignments, this is due to a lack of active security auditing 
                                                rather than code safety. Historical vulnerabilities show extreme susceptibility to XML External Entity (XXE) injection, 
                                                arbitrary file inclusion, and heap-based memory corruption flaws when parsing malformed vector shapes or compressed 
                                                diagram metadata (.dia files are gzipped XML).
    1c Development activity & breakage risk     Dormant / Dead Upstream. The final formal release was version 0.97.2 in December 2011. 
                                                The GNOME project has officially retired its wiki space. Downstream Linux distribution maintainers (Debian/Ubuntu) 
                                                provide minimal compilation-only patches simply to keep the package building against modern GTK runtimes. 
                                                Breakage risk to features is near zero due to a complete feature freeze.
    1d What it needs to function                Legacy GUI Stack Dependencies. Even when executed in command-line export mode (e.g., `dia -e output.png input.dia`), 
                                                it pulls in massive legacy user-space library dependencies, including GTK+ 2, Glib, X11 client libraries, and font config engines. 
                                                Requires read/write filesystem access to its isolated processing path and standard system glibc calls.
    1e Can it be sandboxed or isolated          Highly Amenable. Because diagram conversion is a stateless, pure data translation workflow requiring no host network, 
                                                IPC, or system directory interaction, it isolates perfectly inside a strict, zero-network Bubblewrap sandbox mapping 
                                                only the input file and output directory targets.
    1f Security options & hardened configurationNone native to the binary. Hardening must be applied completely from the outside. The utility must be invoked strictly 
                                                via Bubblewrap, passing non-interactive flags (`--headless` or standard CLI export arguments), dropping all Linux kernel 
                                                capabilities, and hiding the underlying host system paths via strict read-only and ephemeral tmpfs layouts.
    1g Could another dependency do this better  Yes. Inkscape or `rsvg-convert` (librsvg) are modern, actively fuzzed, memory-hardened, and corporate-supported dependencies 
                                                that handle diagram and vector layout translations far safer. Shifting the HRConvert2 manifest contract away from Dia 
                                                to Inkscape or an internal modern library should be mandated for the next cycle.
    1h Origin & supply chain risk               High Risk. The upstream project is officially abandoned. The entire supply chain integrity relies on downstream 
                                                Linux distribution packaging maintainers backporting stability adjustments into historical source mirrors.
    1i Dependency traps for existing installs   The X11/Display Server Trap. Because Dia is inherently built as a desktop GUI application, calling the binary 
                                                inside a minimalist, headless Docker container can trigger unexpected application crashes if the binary attempts to 
                                                initialize an X11 display context, requiring careful fallback handling or virtual framebuffers (like `xvfb-run`) if headless flags fail.
    2a System package versus a source build     System Package Acceptable ONLY because compiling an archived, legacy GTK+ 2 application from source on a modern compiler 
                                                toolchain requires introducing an excessive amount of deprecated compiler dependencies into the build system. 
                                                The package version via `apt` handles this structural dependency resolution automatically.
    2b Build flags, libraries & features        Default package compilation flags applied by apt are sufficient when fully encapsulated by Bubblewrap.
    2c Minimum version & version edge cases     0.97+ as defined by the manifest facts. Ensure that any package deployment correctly routes output files without 
                                                invoking interactive dialog boxes that hang the background thread.
    2d Licensing implications of the build      GPL-2.0. Clean for internal server orchestration within HRConvert2, but requires open-source license compliance 
                                                reviews if the full container footprint is distributed commercially.
    3a Distribution method                      Standard distribution native package manager repositories (apt).
    3b Download source used                     Official Debian/Ubuntu package mirror archives.
    3c How an installer obtains this version    Automated package fetch via the system package manager utility (apt-get install -y dia).
    3d Inspection of any bundled binary or code Inspection difficult due to high density of legacy C architecture styles, archaic GTK+ binding conventions, 
                                                and long-abandoned documentation files.
    3e Sanity check of the build system         Relies entirely on the distribution package builder's native target architecture integration checks.
    3f Build script provided                    No.
