                               application supplies, what belongs in the Engine at all.

contract still said "Nothing here has been done yet" after five of its six steps had landed.

that names its own check either passes or is visibly wrong the next time somebody runs it.

--The Boundary, Which Is Now Enforced Rather Than Remembered--

THE ENGINE CALLS NO APPLICATION FUNCTION. CHECKED ON EVERY RUN.

ABOUT_ENGINE_CONTRACT.txt records a debt of ten application functions the Engine still
called. That debt is CLEARED, & more usefully it is now impossible to reopen quietly.

  PROVEN BY   python3 Documentation/Build/hrconvert2-check.py
              Check eight, "the Engine never calls application code".

The check reads the kernel set from Resources/Kernel/kernel.php & allows exactly those names.
It said eight here until v3.9.9. Anything else the Engine calls that the Engine does not
define is a failure, reported by name & by file.

A DEBT A LINTER WATCHES IS NOT THE SAME KIND OF DEBT. The ten functions were found by a call
order check that follows the call graph rather than by reading, because reading attributes a
call to the line a function was DEFINED on rather than to the moment it RUNS. That is how
locateDependency was moved into the Engine & had to be moved back out.

--What Is Deliberately Not Moving--

THE KERNEL DOES NOT MOVE INTO THE ENGINE, & THAT STILL HOLDS.
verifyCoreComponent() loads the Engine so it cannot live inside the Engine. It calls
purgeSensitiveMemory(), so that cannot either. Logging is kernel because an application whose
logging lived in the Engine would lose the ability to report an Engine that failed to load,
at the one moment there was something worth reporting.

BUT "NOT IN THE ENGINE" HAS BEEN READ AS "INSIDE convertCore.php", & THOSE ARE DIFFERENT CLAIMS.
The mechanical rule is about the FILE the kernel loads. Nothing in it requires the kernel to be
interleaved with an application. The direction below gives the kernel a file of its own.

SESSIONS & THE INSTALL SECRET WAIT FOR AN AUTHENTICATION CORE.            DECIDED AT v3.9.9
They move when authentication arrives, together, into a core that does not exist yet. An
earlier draft of this file proposed putting them in the kernel. That was the wrong home,
because authentication is a large subsystem & the kernel is only worth having while it stays
small & identical in every application. ABOUT_ENGINE_CONTRACT.txt records the decision & the
constraint that core will have to solve, which is that a session is derived before the
Engine loads & every kernel log line carries its label. The kernel already treats the label
as optional, so a kernel without sessions prints No Session & is correct.

--The Direction, Rederived For Three Applications--

WHAT CHANGED IT.
HRProtect is expected to iterate the Engine alongside HRConvert2, with improvements traded
back & forth until the Engine stands on its own. ABOUT_ENGINE_CONTRACT.txt anticipates
HRProtect for scanner pipelines & HRCloud3 for file operation & automation pipelines.
Trading a component between applications only works if it is a unit that can be copied & a
version that can be compared. The audit below asks that of every shared layer.

  from line 33 to line 5932. They are Resources/Kernel/kernel.php now, with $KernelVersion,
  pinned exactly by $RequiredKernelVersion. The seven session & secret functions stayed in
  the application, deliberately, for the reason given above.

              php convertCore.php -v   prints a Kernel line.

  on 21. There is one definition now & it is the file. Checks eight & nineteen read the kernel
  from Resources/Kernel/kernel.php & the contract document points there instead of listing.
  PROVEN BY   grep -n "kernel_path" Documentation/Build/hrconvert2-check.py

  three applications as differing in what a pipeline does rather than in how one is declared,

  already depends on it, calling runVirusScan behind a guard, & check eight cannot see that

  It also hardcodes HRConvert2's sixteen pipelines in its pin table, which is the same disease
  as the Contract folder.

  TWO SCANNER IMPLEMENTATIONS.                                           RESOLVED AT v3.9.9
  Step eight has the proof. What follows is the finding as it was made.
  runVirusScan in Pipeline Core dispatches a scanner pipeline by kind & family. Upload
  scanning, URL scanning & the OCR pipeline all use it. The user requested scan does not.
  userVirusScan, userClamScan, userScanCoreScan & startScanCore run the scanners directly,
  about 350 lines beside a dispatcher that already does the job. Scanning is HRProtect's whole
  purpose, so this is the duplicate it would inherit.

FOUR LAYERS, NOT THREE.
The contract describes three tiers. The audit finds four, & the third is the one without a
home.

  THE KERNEL          Pre Engine & identical in every application. Logging, memory
                      shredding, input sanitizing, argument parsing, dependency location,
                      component loading, the install secret & session identity.
                      Its own file. Its own version.
  THE ENGINE          The runtime every application needs. Managers, budgets, sandbox, data
                      locations, cleaning, network policy, Dependency Core, Setup Core &
                      Pipeline Core. Its own directory, its own version, & the same bytes in
                      every application.
  APPLICATION DATA    What the shared layers read & each application owns. Identity, the
                      dependency manifest, the configuration template & model, the pipeline
                      pin table & the pipelines. Found through contractPath() in the kernel
                      or a path the application supplies, & NEVER kept inside a shared tree.
                      The first three & the pipeline pin table are in Resources/Contract
                      as of v3.9.9.
  APPLICATION LOGIC   What makes the application itself. Conversion, the interface, its own
                      commands.

THE ORDER OF WORK.
Each step is separately testable & separately revertible. A step marked REVERSES changes a
decision recorded in ABOUT_ENGINE_CONTRACT.txt, & that decision is made deliberately before
the code moves, not by the code moving.

  1. ONE DEFINITION OF THE KERNEL, & A VERSION FOR IT.                                DONE
     The file is the definition & carries $KernelVersion. closeHRC2Connection is
     closeClientConnection & $PathExt is gone.
     PROVEN BY   php Documentation/Build/hrconvert2-test-redeclare-cli.php
                 php Documentation/Build/hrconvert2-test-cliargs-cli.php

  2. THE KERNEL BECOMES A FILE.                                              DONE, REVERSED
     DONE. 21 functions moved with every body & every comment block byte identical, 91
     functions conserved exactly, no seam damaged. The version is read before the file is
     required, so a mismatched kernel is never executed, & that was proven with a side effect
     planted in a wrong version kernel that did not fire, beside a control that did.
     The healthy interface renders through a real web server identically to the core before
     the move, apart from per session tokens.
     The plan text below is kept as it was written, as the record of the reasoning.
     The contract says the kernel lives in the application entry file. The rule behind that
     is that verifyCoreComponent cannot live in the file it loads, & that rule is about the
     ENGINE's file. A kernel file required directly by the entry point as its first act, with
     a plain die when it is absent, satisfies it completely. That die is the lowest level
     fallback there is & the only honest one, because nothing can log before the code that
     logs exists.
     The home is Resources/Kernel/kernel.php, beside the Engine rather than inside it, so
     the Engine cannot provide what is needed to load the Engine stays true at directory
     level. The unit two applications trade becomes two directories, each with an exact
     version. A pure relocation, because a PHP function is global wherever it is defined.

  3. CHECK NINETEEN, WHICH STEP TWO MAKES EASY.                                        DONE
     It holds the kernel to calling only itself, PHP & the Engine behind a function_exists in
     the same function. It flags a call into ANY other file in the tree, Pipeline Core
     included, which the old rule's shape would have missed. Thirteen planted faults across
     checks eight, eleven, twelve & nineteen behave as required in both linters.
     It was going to be called check nine. There already is a check nine.
     Before step two, enforcing question three needs an allowlist of call sites, which is
     fragile & was rightly deferred. After it the rule is mechanical. Nothing in the kernel
     file may call a function defined under Resources/Engine without a guard. One file
     boundary, one comparison, & a negative test that plants an unguarded call.

  4. APPLICATION DATA LEAVES THE ENGINE TREE.                                         DONE

     either. The Engine & Pipeline Core read none of them by a path of their own.

  8. ONE SCANNER PATH.                                                                DONE
     Every scan goes through runVirusScan. userScanWithScanner gives each file the user chose
     to each scanner they chose, & userClamScan, userScanCoreScan & startScanCore are gone,
     about two hundred lines. This is the change that most directly becomes HRProtect's core
     feature, because HRProtect is that dispatcher with a different application around it.
     DONE FIRST, BECAUSE THE DISPATCHER COULD NOT YET BE TRUSTED. runVirusScan reached two
     scanner pipelines that had never scanned anything. Both took sandboxCommand's pair as the
     command, so ClamAV called every file clean & ScanCore called every file infected. They
     are fixed & proven, & check twenty stops the shape coming back. See Decisions & Findings.
     DECIDED AT v3.9.9. A USER IS TOLD A VERDICT & NOTHING ELSE, BY EITHER SCANNER.
     The ClamAV half already read its scanner's output for a verdict & threw it away, because
     that output is an exfiltration channel. The ScanCore half wrote ScanCore's own report
     where the user downloads it, naming the installation's path, the account ScanCore ran as,
     the scanned file's path on the server & the signature that matched. One path, one rule.
     THREE FAULTS WENT WITH THE OLD CODE. Each scanner returned the last file's verdict alone,
     so an infected file followed by a clean one was reported clean. A ScanCore report that
     held one detection made every later file in the session read as infected. A scan with
     every scanner reset neither log, so its report carried every earlier scan's lines.
     WHAT CHANGES FOR AN OPERATOR. The user's scan runs in the sandbox now, like every other
     scan, & a host that requires a sandbox & cannot build one reports files as not scanned
     rather than scanning them unsandboxed. A scanner that cannot finish never reads as clean.
     FOUND IN THE FIELD THE NEXT DAY. Every user scan said its file could not be scanned. The
     scanner sandboxes had never run before this release, so neither held what its scanner
     needs. ScanCore's own directory was not in the namespace, & PHP inside it had no
     configuration & so no ctype. ClamAV had neither its signature database nor the
     certificates ClamAV 1.5 verifies that database against. The ScanCore pipeline hands its
     sandbox the ScanCore directory as a read only resource, & the clamav & scancore profiles
     bind /var/lib/clamav, /etc/clamav & /etc/php read only. ClamAV's scanned directory is read
     only now, as its comment always said, & neither scanner runs without a temporary location.
     THE LESSON. The first proof below ran on a host with no bubblewrap, where a sandbox that is
     not required is skipped, so it proved nothing about the sandbox. Every scan proof now runs
     with bubblewrap present, & once more with it hidden.
     FOUND IN THE FIELD AGAIN. With that fixed, ScanCore found the test file & ClamAV 1.0 with
     its real database still DID NOT RUN. The listener scaled Scan to 18% & 740M of a configured
     50% & 2048M, because one scan was in flight on a lightly loaded server, & the kernel killed
     clamscan while it loaded its database. A one signature test database never came near it.
     Scan keeps its configured memory now & only its processor share is scaled, which is what
     config.php always said to treat that figure as. Each scanner logs its exit status when a
     scan does not finish, so the next failure names its cause instead of being inferred.
     PROVEN BY   The real kernel, Engine, Pipeline Core, scanner pipelines & ScanCore, with
                 only verifyFile stubbed, scanning the EICAR test string & a clean file in that
                 order. Every scanner & every mode reports the test file infected & the clean
                 file clean, & the report holds no server path, signature or account name.
                 The same run on the code before this step reports ClamAV's scan of the two
                 files clean, puts
                 five server paths, two signature names & two account lines in one ScanCore
                 report, & reports a later scan of the clean file alone as infected, carrying
                 six stale lines. With the sandbox required & unavailable, the report says the
                 file could not be scanned & that the scan DID NOT RUN.
                 Through a real bubblewrap sandbox, as root & as www-data, with the real
                 clamscan given a one signature database & the real ScanCore, every scanner &
                 every mode gives the same verdicts. With the profiles & the pipeline as they
                 were the day before, both scanners report every file not scanned, which is
                 the field report. Inside that sandbox, php said Could not open input file &
                 clamscan said it could not find /var/lib/clamav.
                 scaleConversionLimits at 28% pressure with one scan in flight gives Scan 18%
                 & 737M before & 18% & 2048M after, & every other type the same as before. The
                 field log said 18% & 740M. A clamscan that exits 137 is logged with its status
                 & told where to raise the ceiling.

       runOcrOperation is runOperationPipeline & takes the family as its first argument.

--Decisions & Findings--

Things found while migrating that are NOT migration work & were deliberately not fixed in
passing. A refactor that also changes behaviour produces a failure nobody can bisect.

  THE FIRST TARGET WAS LOWERCASED ONE WAY & NOT THE OTHER.
  RESOLVED AT v3.9.9, by lowercasing everything rather than nothing. The command line is now
  case insensitive throughout, including the -y confirmation flag, which was being compared
  exactly while the command beside it was lowercased.
  A target is safe to lowercase because a target is never a path. Every path & every section
  name reaches its consumer through extractCliOption, which lowercases nothing & says so.
  What arrives as a target is a sub command, a role name, a version, a count, the word now,
  or a startup key, & a startup key is a sha256 HMAC, which is lowercase hexadecimal already.
  ADDING A CASE SENSITIVE TARGET MEANS READING IT WITH extractCliOption INSTEAD.
  PROVEN BY   php Documentation/Build/hrconvert2-test-cliargs-cli.php
              Every vector is parsed again with every element upper cased & must produce an
              identical result. A table of answers can be made to pass by editing the table.
              A property cannot, so that is the check that holds this decision.
  CORRECTION. THAT LIST OF TARGETS MISSED TWO, & THE PROPERTY TEST COULD NOT HAVE SEEN EITHER.
  It proves the parser is consistent, & says nothing about what a consumer does with what it
  is handed. Both were found by running the documented commands.
    --pipeline --describe Image    The name is a target & pipelines are keyed by declared
                                   name, so the documented example refused every pipeline.
                                   Pipeline names are matched without regard to case now.
    --app arguments                Values belong to another application & may be paths. The
                                   caller reads them from the raw vector, which the parser
                                   returns unchanged. The command stays lowercased.
  THE RULE, RESTATED. A consumer of a name compares without regard to case. A consumer of
  something that may be a path reads the raw vector.
  PROVEN BY   --pipeline --describe Image, IMAGE & image each describe Image & exit 0.
  ALSO FOUND, NOT FIXED. With the equals form the next argument is never read as the second
  target. Two commands read one. --pipeline takes a pipeline name after its action & is
  documented without an equals sign, & --start-manager takes a key that only a listener from
  an older release still passes on the command line, in the space form. --app values follow
  the same rule, so a handler sees what the parser would have given it. Changing it is a
  kernel change with nothing asking for it yet.

  THE --app MECHANISM HAD NEVER WORKED. FOUND BECAUSE OF THE ABOVE, FIXED AT v3.9.9.
  The dispatcher read $ApplicationArgumentHandler, which nothing sets. The Engine
  configuration & the contract both set $EngineApplicationArgumentHandler, so a declared
  handler was never called & every --app argument was refused. Behind that, the branch was
  a separate if ahead of the main chain, so even a refusal fell through to the unrecognized
  argument branch, printed the whole help text under its own answer & exited 2.
  Each fault hid the next. HRConvert2 declares no handler, so nothing visible changes here
  except that the refusal now stands alone. HRProtect & conversion from the command line are
  the two things that will declare one.
  PROVEN BY   A test handler declared in a disposable copy receives --appScan /Some/Path as
              --appscan & /Some/Path & exits 0. Put back the old global name & it is never
              called. Put back the lowercased call & it receives /some/path. As shipped,
              --appfoo prints the two line refusal, no help, & exits 2.
  STILL OPEN AFTER STEP SEVEN. The handler's return value is not read, so a handled --app
  argument always exits 0. This was to be decided with the dispatcher's interface, & --app
  stayed with the application, so the first application to declare a handler decides it.

  AN ENGINE THAT IS MISSING WAS FATAL, THOUGH THE CODE SAID IT WAS A WARNING.
  RESOLVED AT v3.9.9. The fallback paradigm is kept & the machinery changed to honour it.
  Four layers, because the failure arrives in four different places.

    verifyGlobals        requestConvertLoc falls back to the CONFIGURED data location, which
                         is the same answer the Engine itself returns with no listener
                         running. The same result by a shorter route.
    parseCommandLine     A command needing the Engine is refused with a sentence naming -v,

    showVersionInfo      toolRequirement joins toolPath as an Engine safe accessor, & the

  WHAT WAS LEARNED   toolPath already carried the right guard & the right comment, & it still
  died four frames deeper than it was reading. Testing the function in front of you is not

  RESOURCES/CONFIG.PHP IN THE REPOSITORY CARRIES AN ABSOLUTE INSTALL PATH.
  DECIDED AT v3.9.9. IT STAYS, & THE PATH IS NOW CHECKED INSTEAD OF BELIEVED.
