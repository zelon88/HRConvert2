This plain text file contains descriptions of all the native error messages contained in or produced by the HRConvert2 Diablo engine.
These descriptions should give administrators a starting point for debugging problems with HRConvert2 installations.
Each section in this file contains information about a different error message. The first one is an example to demonstrate the structure of this file.
Details about each section are below.

HARDWARE REQUIREMENTS ...
This application requires at least a Raspberry Pi Model B+ or greater.
This application will run on just about any x86 or x64 computer.

DEPENDENCY REQUIREMENTS ...
The authoritative list of dependencies is Resources/Contract/depends.php & nothing else. Run  php convertCore.php -v  to see what this installation has.

ADDITIONAL INFORMATION ...
HRConvert2 logs information about its operational activity to the Logs subdirectory of the data location by default.
Root logs to the Engine subdirectory beside it, & repeats its warnings & errors on the terminal when run there by hand.
A command line account other than root logs to a folder of its own in the temporary directory.
The default logging directory can be adjusted by modifying the --Log Storage Directory-- section of the config.php file.
Log entries that represent normal, expected behavior begin with 'Op-Act,' to signify "Operational Activity".
Log entries that represent abnormal behavior begin with 'WARNING!!!' or 'ERROR!!!'.
If a log file does not exist, HRConvert2 will attempt to create one.
If an attempt to create a log file or write log entries fails for any reason, HRConvert2 will output errors directly to the page instead.
If a log file exists, was created on the current date, and is smaller than the "Maximum Log File Size" in config.php, HRConvert2 will append log entries to it.
Once the "Maximum Log File Size" specified in config.php has been reached, HRConvert2 will create a new log file with a numerically incremented file name.
Actual maximum log file size will vary slightly from the "Maximum Log File Size" because it must be exceeded before HRConvert2 will replace it.
Typically the "Maximum Log File Size" is only exceeded by a small number of bytes.
Time will be omitted from logs in situations where time has not been initialized yet.
The application name will be replaced with 'HRConvert2' in errors in situations where the config.php file has not been initialized yet.
The log number will be replaced with '###' in the event that the error number supplied by the calling code was invalid.
If "Enhanced Logging Verbosity" is enabled in config.php, all significant core operations will produce a log entry.
If "Enhanced Logging Verbosity" is disabled in config.php, only warnings and errors during core operations will produce a log entry.
As of v3.8.9 every entry carries a sequence number immediately after its tier label.
An error therefore reads  ERROR!!! 00042, <TIMESTAMP>, <APPLICATION_NAME>-####, <SESSION_IDENTIFIER>: message
The number counts entries rather than seconds and starts at zero when the process starts.
A gap in that sequence is the only evidence that an entry was written and never arrived.
Two entries stamped with the same second are otherwise impossible to order.
Every example below omits the sequence number for readability. The number is present in a real log and is not part of the error itself.
Log files are also named for the role that writes them, as HRConvert2_Web, HRConvert2_Manager or HRConvert2_Cli.
An error raised by a web request is therefore in the Web log rather than in a single shared file.
See Documentation/ABOUT_LOGGING.txt for the whole of this.
As of v3.8.5 every conversion pipeline is a detachable component beneath /Resources/Pipelines/ rather than code inside convertCore.php.
No error number changed value when those pipelines moved. Only the FILE section of each affected entry was updated to name its new location.
An operator who read a number in an older release reads exactly the same number today.
Every FILE section below was derived by scanning the code for the call that raises each number rather than by assuming which pipeline owns a block.
A number raised from more than one file names every file that raises it.
The 2000 block is raised by /Resources/Pipelines/Shared/libreOffice.php, which serves the Document pipeline and the OCR pipeline alike.
An operator seeing one of those numbers may have been running either one. The log line above it names which.
The Pipeline Core reserves 34000 through 34019. It became an Engine core at v3.9.9 & none of its numbers changed.
The 32000 and 33000 blocks were already taken by Setup Core and Dependency Core.

--About An HTTP Status Code, Which Is Not One Of Ours--

A numbered error in this file is one HRConvert2 raised deliberately.
A status code is what the web server said when HRConvert2 raised nothing at all.
They are different problems & the difference tells you where to look.

  A numbered error means the application ran & decided something was wrong.
  A status code usually means the application did not get far enough to decide anything.

500, INTERNAL SERVER ERROR.
PHP stopped. Nothing in this file will explain it, because nothing here was reached.
Look in the web server error log rather than in the HRConvert2 log.
  /var/log/apache2/error.log on Debian & Ubuntu.
  docker logs <container> for a container.
The line you want names a file & a line number & begins with PHP Fatal error.
  A call to an undefined function means a component did not load, or was called before it
  loaded. Run  php convertCore.php -v  & read which components report FAILED.
  A permission denied on a path means the web server user cannot reach it. Run  -fp  as
  root, which corrects ownership on every path this application manages.
  An undefined variable that is fatal usually means a configuration this release requires
  is missing. Compare $ConfigVersion in config.php against $RequiredConfigVersion.
  Anything mentioning memory_limit or max_execution_time is PHP refusing to continue rather
  than HRConvert2 failing. The -fp argument writes a drop in that raises both.

404, NOT FOUND.
The web server did not find the file, so HRConvert2 was never involved.
  Check the address. The application lives at /HRProprietary/HRConvert2/convertCore.php &
  not at the directory above it.
  A 404 on a file that exists on disk is an Apache configuration problem rather than a
  missing file. Run  -v  & read the Apache configuration line.
  A 404 for everything under the data location is CORRECT & is what protects it.
  The Live exposure line in  -v  reports PROTECTED when that is working.

403, FORBIDDEN.
The web server found the file & refused to serve it.
  Almost always ownership. Run  -fp  as root.
  A 403 on the data location is the protection working, exactly as a 404 there is.

502 or 504, BAD GATEWAY or GATEWAY TIMEOUT.
A reverse proxy in front of this application gave up waiting.
  A long conversion outlives a default proxy timeout. Raise it on the proxy rather than
  here, because HRConvert2 has no way to make the proxy wait.
  A detached conversion is supervised after the reply is sent, so the proxy timing out does
  not stop the work. The file appears when the worker finishes.

413, PAYLOAD TOO LARGE.
The upload was refused before HRConvert2 saw it.
  This is upload_max_filesize & post_max_size in PHP, & LimitRequestBody in Apache.
  The -fp argument writes the PHP side. The Apache side is yours.

A BLANK PAGE WITH NO STATUS CODE AT ALL.
PHP produced output & then died, or produced nothing & exited zero.
  Check the web server error log first, exactly as for a 500.
  A blank page after an upload is usually a warning printed into an AJAX reply. The
  interface reads that reply as a filename & shows nothing. Search the HRConvert2 log for a
  WARNING at the same second.

WHAT TO GATHER BEFORE ASKING FOR HELP.
  php convertCore.php -v            every component, dependency & subsystem, with versions.
  The last fifty lines of the HRConvert2 log for the role that failed.
  The web server error log for the same minute.
  Whether the same operation works from the command line, which separates a web server
  problem from an application problem in one step.

ERROR MESSAGE
  The exact error response produced by the application.
  Text wrapped in angle brackets < > denote encoded information.
  <TIMESTAMP> will be replaced with an abbreviated date.
  <SESSION_IDENTIFIER> will be replaced with a short but unique number to identify related log events.
  <APPLICATION_NAME> will be replaced with whatever the --Application Name String-- is set to in config.php.
  <FILE_PATH> will be replaced with an absolute file path.
  <FILE_NAME> will be replaced with a file name.
  <ADDITIONAL_DATA> will be replaced with the result of a system call or standard output from a called dependency.
  <FILE_TYPE> will be replaced with a human readable one word string describing the file such as 'Video' or 'Document'.
  <FILE_EXTENSION> will be replaced with a file extension.

FILE
  The file path pointing to the file which contains this error message.
  File is relative to the root HRConvert2 installation directory.
  <SELECTED_LANGUAGE> will be replaced with the ISO 639-1 code that represents the language that was used during the event.
  <SELECTED_GUI> will be replaced with a text string that represents the GUI that was used during the event.
  <SELECTED_COLOR> will be replaced with a text string that represents the color that was used during the event.

FATAL
  Whether or not the occurrence of this error will halt execution of the application.
  Will either be YES or NO.

LOGGED
  Whether or not the occurrence of this error will be written to a log file in the --Log Storage Directory-- section of the config.php file.
  Will either be YES or NO.

ERROR DESCRIPTION
  A brief and concise description of the error message as well as possible causes & solutions.

  Setup Core & the Engine, & one of them is missing. Restore it from the release this core
  came from.

FATAL

LOGGED
  YES

ERROR DESCRIPTION

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-4, <SESSION_IDENTIFIER>: Could not verify timezone!

FILE
  convertCore.php

FATAL
  YES

LOGGED
  YES

ERROR DESCRIPTION
  PHP's timezone is not one this PHP recognizes. It comes from date.timezone in php.ini, or
  from the system default when that is unset, & config.php has no setting for it.
  Every log entry, every session directory & every deletion threshold is derived from the
  time, so an unknown timezone makes all three untrustworthy rather than merely wrong.
  Set date.timezone in php.ini to a name PHP recognizes, such as America/New_York.
  A list of names is available from timedatectl list-timezones.

  YES

LOGGED
  YES

ERROR DESCRIPTION
  The GUI was assembled but did not complete.

  so a languageStrings.php that is present but does not run to completion, with no baseline

  header.php, convertGui1.php or convertGui2.php, & footer.php must each report success.
  A file that is present but did not execute to completion produces this.

  This may be the result of incorrect file permission levels on the UI subdirectory.

ERROR DESCRIPTION
  An image conversion was refused because the server could not build a sandbox for it.
  ImageMagick parses untrusted image files & has a long history of memory corruption bugs.
  The delegate system invokes other programs by design, which is what ImageTragick abused.
  policy.xml restricts that natively, but a policy file is a blocklist & has been bypassed.

  blocks bubblewrap until an AppArmor profile is installed for it.
  A container blocks the required syscalls unless it was started with the correct options.
  See --Require Sandbox-- & --Require Sandbox On Docker-- in config.php.
  Run  php convertCore.php -v  to confirm whether this server has a working sandbox.
  See INSTALLATION_INSTRUCTIONS.txt for the AppArmor profile this requires.

FILE
  Resources/Pipelines/Model/pipeline.php

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION
  A model conversion was requested into a format that no installed utility can produce.
  The two utilities cover different sets & neither covers the whole of --Supported Model Formats-- in config.php on its own.
  Assimp writes obj, stl, ply, 3ds, dae, x3d, fbx, gltf, glb and 3mf.
  MeshLab writes ply, stl, obj, off, dae, x3d, dxf, wrl, ctm and u3d.
  A format in neither list cannot be produced, however the conversion is routed.
  This is reported before the retry loop is entered, because retrying a command that cannot succeed only delays the same failure.

  Assimp reads OFF perfectly well and has no OFF exporter at all.
  An earlier version routed on the input extension alone, so an obj to off conversion reached Assimp, which answered that it could not guess the output format, and the retry loop repeated the identical command until it timed out with error 9000.
  Remove the format from --Supported Model Formats-- in config.php, or install a utility that can write it.

  cleared against a minimum.

  produced an empty result & a conversion that reported failure without naming a cause.
  NOTE. A missing language data package produces a DIFFERENT failure that this check
  cannot detect. Tesseract itself is present & current, & the conversion still produces
  nothing. Install tesseract-ocr-<lang> for every language the server needs to read.

FILE

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION

  pdftotext is part of the poppler-utils package rather than being a package of its own.
  Install it with  sudo apt install poppler-utils
  The minimum is the MinimumVersion of its entry in Resources/Contract/depends.php.
  poppler uses a date style version where the major is the YEAR & the minor is the MONTH,
  so 24.02 is February 2024 rather than version twenty four point two.
  Check the installed version by running  pdftotext -v  in a terminal.

  cleared against a minimum.

  rasterizes the page & reads it with Tesseract instead. A server with no poppler can
  still OCR a PDF, just more slowly & with less exact output.
  When it occurs during the image fallback route, there is no alternative & the operation
  fails.

  NOTE. pdftotext cannot read a scanned page. A PDF with no text layer produces nothing at
  all even when pdftotext is present & current, which is the entire reason method 2 exists.
  An empty result is not necessarily a fault in this dependency.

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-31017, <SESSION_IDENTIFIER>: A startup key for <ADDITIONAL_DATA> was presented a second time & refused as a replay!

FILE
  Resources/Engine/engine.php

FATAL
  NO

  YES

ERROR DESCRIPTION
  A manager startup key that had already been spent was presented again.
  A startup key is an HMAC over a short time bucket and is valid for the current window and the one before it.
  A key that crosses a process boundary is now spent the moment it validates, and a second process presenting the same key is refused however soon it happens.
  Time alone cannot make a leaked key dead. Whoever holds a copy validates it against the same clock this application does, so the window decides only how long they have and never whether they succeed. Spending the key is the part this application controls.
  The key is also carried in the environment rather than on the command line, because /proc/PID/cmdline is world readable and a manager process runs for days.
  CAUSE. Almost always a second launch of the same manager role within the same window, such as a service unit and an operator both starting the listener at once.
  It is also what a replay of a captured key looks like, so a run of these with no matching launch is worth investigating.
  RESOLUTION. Start the listener once. Run --status to see what is already running, and --stop-listener before starting it again.
  The ledger of spent keys lives in the manager socket directory and holds hashes rather than keys, so reading it grants nothing. Entries older than three windows are dropped automatically.
  This control defends against a key that leaked, not against an account that holds the install secret.
  Deleting the ledger un-spends a captured key, and the only accounts that can delete it are root and the web server user, both of which can already read the secret and mint a valid key directly. Losing the ledger to either of them costs nothing that was not already lost.
  The directory holding it sits inside the data location, owned by the web server user, so an unprivileged local account cannot remove it. That is the account this control exists for.
