HRConvert2 has one default GUI set in config.php and additional GUIs can be installed by administrators and selected by the user at runtime.
The default GUI used by HRConvert2 can be selected by adjusting the --Default GUI-- section of config.php.
Administrators can prevent user GUI selection by adjusting the --Allow User Selectable GUI-- section of config.php.
If --Allow User Selectable GUI-- is set to TRUE in config.php, users can adjust GUI output using a 'gui' GET request.
To send a GET request, append the following string to the end of the HRConvert2 URL (without quotes):  '?gui=<GUI_CODE>'
Substitute <GUI_CODE> in the string above for the name of the GUI defined by the name of the folder where its files are contained.
If a user submits an unsupported GUI the default will be used instead.
If a supported GUI is missing required files, or reports a version the core does not accept, HRConvert2 falls back to the Default GUI & logs a warning.
A fatal error occurs only when the Default GUI is not available as a fallback.

--About GUIs--

The HRConvert2 GUI is modular and separate from the core logic of the application.
This design makes modifying the look and feel of HRConvert2 easy.
This document will teach administrators and developers how GUIs are handled and structured.
In this document when we refer to a GUI, we refer to a set of files required to render HRConvert2.
In this document when we refer to a language pack, we refer to the files required to localize a GUI into a specific language.

An HRConvert2 GUI is made up of 9 components. Each component serves a specific function. The 9 components of a GUI are:

  1. header.php
  2. convertGui1.php
  3. convertGui2.php
  4. footer.php
  5. styleCore.php
  6. index.html
  7. A 'Languages' folder with at least one ISO 639-1 supported Language Pack.
  8. uiVersionInfo.php
  9. A 'Resources' folder containing 'Image', 'CSS' & 'JS' subdirectories.

These components are stored in a folder named after the GUI.
That folder is placed inside the 'UI' subdirectory of the installation location.
The GUI name must also be added to the --Supported GUIs-- section of config.php or it will be ignored.
If --Allow User Selectable GUI-- is enabled, users can select this GUI with a GET request or from the selector bar in the interface.
Users should not access the GUI directly. All requests should be directed to convertCore.php which will construct the GUI on-demand.

During operation, HRConvert2 initializes the GUI using the following process:

  1. Initialize the GUI to Default.
  2. Build an array of GUIs that are included with HRConvert2.
  3. Check if the $SupportedGuis variable from config.php is set properly.
    3a. If not, use the included array of default GUIs instead.
  4. Check if the $DefaultGui variable from config.php is set & supported.
    4a. If not, use Default instead.
  5. Check if the $AllowUserSelectableGui variable from config.php is set.
    5a. If not, use $DefaultGui instead.
  6. Check if a GUI was specified via GET or POST input & is supported.
    6a. If so, use it. If not, use $DefaultGui instead.
  7. Build a candidate list containing the selected GUI, then the Default GUI.
  8. For each candidate in turn:
    8a. Define all required GUI files & folders.
    8b. Check that the GUI folder exists.
    8c. Check that every required GUI file exists.
    8d. Load uiVersionInfo.php & compare $GuiVersion to $RequiredGuiVersion.
    8e. If every check passes, stop. Otherwise write a warning & try the next candidate.
  9. Reset the gui GET variable to the GUI that actually loaded.
  10. Load styleCore.php & read the colour codes from it.
  11. If no candidate succeeded, terminate the application with error 25.

--Administration Tips--

Language Packs are contained within GUIs. GUIs typically contain multiple language packs.

config.php lists the languages the INSTALLATION offers. A GUI is not required to carry all
of them, & is not expected to. Adding a language to --Supported Languages-- makes it
selectable; it appears for the GUIs that actually carry it & falls back for the ones that
do not. That is the intended way to add a language: naturalize a pack inside your GUI, list
the language in config.php, & leave the other GUIs alone.

When a language cannot be served, verifyLanguage() walks a ladder rather than failing:
  1. The language the user selected.
  2. $DefaultLanguage from config.php.
  3. English, which is the core's own built-in floor & cannot be configured away.
Each rung that is missing or incomplete writes a warning naming the pack & the folder. The
first rung that is present is used. An error occurs only if the GUI carries no usable pack
at any of the three.

Whichever pack is used, the core also picks a BASELINE pack from the remaining rungs &
loads it FIRST, then loads the selected pack over the top of it. A pack therefore only has
to define the strings it wants to change. Anything it omits keeps the baseline's value
instead of rendering as an empty string. This is what makes a partially translated or
out-of-date pack usable rather than broken.
Errors will occur if an installed GUI does not support the following colors: Red, Green, Blue, Grey, Orange, Purple, Dark.
Server administrators can:
  Enable or disable GUIs by modifying the --Supported GUIs-- section of the config.php file.
  Add or remove language packs to a GUI by creating a folder in the 'Languages' subdirectory of each enabled GUI folder.
  Allow or prevent GUI selection via GET request by modifying the --Allow User Selectable GUI-- section of the config.php file.

--Development Tips--

The modular design of HRConvert2 is designed to make adding new GUIs and/or languages simple for administrators to manage and easy for developers to maintain.
If you are maintaining a branch of HRConvert2 and are focusing on a single language pack you can build your logic directly into the GUI pages themselves.
Any GUI files that are not needed can be left blank after the opening PHP tag.
To create a new GUI, copy & paste an existing GUI from the UI folder and modify the files with your favorite text editor.
To install a new GUI, place a folder in the 'UI' subdirectory of the installation location.
To enable or disable a GUI, update the --Supported GUIs-- section of the config.php file.
GUIs can utilize the icons and scripts in the default Resources directory or include their own.
If any non-stock directories are added to HRConvert2, a copy of index.html must be pasted into the directory.
Do not create any files named index.html. This filename is reserved by the application for document root protection mechanisms.
Upper Case variables are Global in scope. Lower case variables are severely limited in scope.
Limited scope variables are destroyed with purgeSensitiveMemory() as soon as they are no longer required.
Your GUI can come with its own Documentation folder, or any additional files or folders you wish.
Every folder requires the stock index.html. Copy and paste an existing one.

--About GUI Versions--

Every GUI declares its own version in uiVersionInfo.php as $GuiVersion.
The core carries the version it is built against as $RequiredGuiVersion.
A GUI whose version does not match the core is not loaded.

The comparison is an EXACT match. It is not a minimum.
This differs from config.php, which is accepted at or above a minimum version.
A configuration file that is newer than the core still contains every setting the core
looks for, so it can be used. A GUI does not work that way in either direction.
A GUI newer than the core may reference language strings, arrays or helper functions that
the core does not provide. A GUI older than the core may omit elements the core expects to
find, or may still call functions the core has removed.
Neither produces a clean failure. Both produce a partially rendered page, a PHP notice
printed into the middle of an AJAX response, or a silently missing control.
Refusing to load is the only outcome that fails visibly.

The version is checked in verifyGui(), BEFORE any file that produces output is loaded.
Only uiVersionInfo.php is read to perform the check, & that file only assigns a variable.
This ordering is deliberate. A GUI cannot be replaced once header.php has begun printing,
so the decision has to be made while replacing it is still possible.

A GUI that fails the check falls back to the Default GUI & writes a warning to the log.
A user cannot choose their way out of a broken GUI, so the fallback is silent to them.
Error 25 is thrown only when the Default GUI ALSO fails, at which point nothing is left to
render & the application stops.

When building a new GUI, set $GuiVersion to match the $RequiredGuiVersion of the core it
is being built against. Check the current value by running  php convertCore.php -v

WHEN TO CHANGE A GUI VERSION.
  Change it when the GUI will no longer work correctly with the previous core.
  A new language string the GUI reads.
  A new array or variable the GUI expects the core to provide.
  A changed function signature the GUI calls.
  A structural change to the markup that the core or the stylesheet depends on.

WHEN NOT TO CHANGE A GUI VERSION.
  Do not change it for a typo, a colour, a margin, or a corrected comment.
  Those changes do not affect whether the GUI works with the core.
  The commented version stamp at the top of the file may still be updated to record when
  the file was last touched. That stamp is documentation. $GuiVersion is a compatibility
  contract & means something different.

ALL GUIS MUST BE UPDATED TOGETHER.
  A version bump applies to every GUI in the installation at once. All or nothing.
  A GUI left behind is a GUI the core will refuse to load.
  This is deliberate & exists to catch exactly that mistake. Changing one GUI & forgetting
  the others is easy, & the resulting breakage is hard to diagnose without this check.

--About index.html--

This file serves to act as reliable and predictable document root protection for the server.
If users are allowed to view the document root of the server they could navigate manually to other users' hosted scratch space.
This would allow users to see some temporary files of other users while they were in the process of working on them.
This file simply redirects the user to the main HRConvert2 landing page with a message asking them to wait.
The visual effect of the loading text is that a malicious actor knows they have hit some protection mechanism.
If you want to modify the global index.html file, modify the one in the installation location and then copy & paste to all other subdirectories.
HRConvert2 will automatically create new index.html files in folders it creates using the one from the installation location as a template.
This file must be manually copied & pasted into any folders that are manually created by administrators or developers of HRConvert2.

--About 'Languages' Folder--

The 'Languages' folder must exist in each GUI.
The 'Languages' folder contains the major language-specific files for the GUI.
Each subdirectory of the 'Languages' folder represents a different language pack.
A language pack is a folder named for an ISO 639 code containing two required files:
  languageStrings.php, Every displayed string, plus $LanguageVersion.
  flag.png, The flag shown in the language selector.
A pack missing either file is treated as absent & the fallback ladder continues past it.

A language pack declares $LanguageVersion & the core carries $RequiredLanguageVersion.
That comparison is REPORTED, NOT ENFORCED. A mismatch writes a warning naming the pack,
the version it reports, the version the core wants & the baseline pack its missing strings
are coming from. The pack is still loaded & the interface still renders.

This is deliberate & it differs from the GUI & config.php contracts on purpose.
A GUI is refused on a version mismatch because a GUI is CODE; it calls functions & reads
arrays, & the wrong vintage produces a half-drawn page or a PHP notice in the middle of an
AJAX reply. A language pack is DATA. The only thing a stale pack can get wrong is a string
it does not define, & the baseline already answers that. Refusing a pack over its version
would mean an installation that gains one new string loses every translation it has, which
is a far worse outcome than a handful of English words on an otherwise translated page.
So the version is a maintenance signal for the administrator's log, not a gate.
Update $LanguageVersion when you bring a pack up to date. Nothing breaks if you forget.

--About 'Resources' Folder--

The 'Resources' folder is REQUIRED. It contains & organizes the scripts, stylesheets, &
images required by the GUI.
The HRConvert2 core will define the following variables which map to subdirectories of the 'Resources' folder:
  $GuiResourcesDir, Maps to 'Resources/' folder.
  $GuiImageDir, Maps to 'Resources/Image' folder.
  $GuiCSSDir, Maps to 'Resources/CSS' folder.
  $GuiJSDir, Maps to 'Resources/JS' folder.

verifyGui() checks that all four of those directories exist before it accepts a GUI.
A GUI missing any one of them is refused with a warning naming the folder, & the core falls
back to the Default GUI.

This folder was once described as optional. It is not, & it never really was. The core
hands every GUI a $GuiImageDir, a $GuiCSSDir & a $GuiJSDir & then expects the stylesheet,
the favicon, the flags & the script library to be found underneath them. header.php builds
its paths from those variables unconditionally. A GUI without the folder does not degrade
into an unstyled but working page; it emits a stylesheet link to a directory that does not
exist, a script tag to a library that does not exist, & an interface whose every control
calls into that missing library. Checking for the folder up front converts a page that
silently does nothing into a logged warning & a working Default GUI.

The included GUIs keep their client side script library at 'Resources/JS/HRC2-Functions.js', & the
Workflows panel's at 'Resources/JS/HRC2-Workflows.js'. header.php points $WorkflowsJsPath at the
second & loads it only while $EnableWorkflows is on. Both are stamped with their modification time,
so a browser fetches a new copy the moment one changes.
header.php points $JsLibraryPath at it & loads it before anything that calls into it.
That file is static javascript & CANNOT read a language pack, so every string it shows a
user is passed in as an argument by the PHP that calls it. Pass those strings through
json_encode() rather than echoing them into a quoted javascript literal. A translation
containing an apostrophe will otherwise end the literal early & break the whole script.

It also carries the one definition of what a core reply means, which every interface must
use rather than testing a reply for itself:
  reply_is_error($replyText, $failureStrings), Whether a reply reports a failure.
  line_is_filename($line), Whether one line of a reply names a file.
  download_file($basePath, $fileName), Points the hidden anchor at a file & triggers it.

A file list drawn again after each operation publishes the files it was drawn from, each time it is
drawn, with HRC2.configure({ sessionFiles: [...], filesListed: true }). The included GUIs do this at
the top of the list. Archive All & Scan All read those files when pressed, & without them they act
on the files the page held when it was first drawn.

AN INTERFACE MUST NOT DEPEND ON THE SCRIPT LIBRARY BEING THE CURRENT COPY.
A GUI page is generated fresh on every request. The script library beside it is a static
asset that a browser, a proxy or a CDN caches for as long as it is permitted to. The two
update at different moments, so a user WILL at some point run a new page against an old
library. Treat that as a normal operating condition & not as a fault.

Call the library through a wrapper that tests for the function & falls back to a local copy
when it is absent, exactly as the rest of the application falls back. Try the requested
thing, warn, use the default, & only then fail. A GUI that calls a library function
directly throws a ReferenceError on a stale cache.

This matters far more than it first appears, because of where those calls happen.
jQuery CATCHES anything thrown inside a .then() handler & converts the promise into a
rejected one rather than letting it reach the console. That rejection is not seen by the
failure arm of the same .then(), because that arm belongs to the REQUEST, & the request
succeeded. So an exception inside a success handler is silent. The spinner runs forever,
the error is never displayed, & the user has nothing to report.

Give every operation exactly one teardown path that stops its spinner, guard it so it
cannot run twice, & call it from a catch as well as from every planned exit.
A spinner that never stops is the worst outcome available. It tells a user that work is
still happening & leaves them nothing to describe.

A CORE ERROR ARRIVES WITH AN HTTP 200 & A BODY.
The request succeeds, so the success handler is the one that runs & the body is the only
thing that separates a failure from a success. Every reply must be tested before it is
acted on. An error carries the ERROR!!! tag, & a refusal the core makes BEFORE attempting
an operation carries no tag at all, only the alert string. Both are failures.
Never treat an empty reply as a failure. A successful download prints no filename.
An upload's reply is tested as well. Dropzone marks every upload that got an HTTP 200 finished
unless it is told otherwise, so the script library hands it a success handler that tests the reply
& hands a failure to Dropzone's own error handler. Until v4.1.3 a refused upload looked uploaded.
Never accept a line of a reply by its position. The core opens every reply with a doctype
& prints a line break after every error message, & both of those are lines.

--About Uploaded Files--

The $Files variable contains an array of all valid uploaded filenames that exist in the user's scratch space.
$FileCount carries how many there are.
BOTH interfaces receive these, not only convertGui2.php. buildGUI() reads the scratch space
before either one is loaded, so convertGui1.php can tell a first visit apart from a return
visit & can offer controls that only make sense when the session already holds something.
An upload page that renders a destructive control to a visitor with nothing to lose is
inviting them to press it, so gate such a control on $FileCount.
The GUI must iterate through this array, determine what format it is, & display the correct options.
When submitting a file as input, only submit its name with extension. HRConvert2 will determine the path.
When redirecting the user to a download you must send them to the proper filename and hosted file path.

--About Identify & Sorting--

$Files arrives in the order $SortToUse names, so an interface draws it as it is.
$SortToUse is two digits, what the list is sorted by & then the direction, as ABOUT_REST_API.txt
describes under sort. Every link & form an interface draws carries it as sort=, or a refresh, a
change of language & every operation that draws the list again put the files back in name order.
A sort control asks for the page again with a new code. The included GUIs draw one for each of
the four, & pressing the one in force again turns its direction around.

$FileDetails holds what the core read about each file when it put the list in order, keyed by
the name in $Files.
  Size            The size in bytes.
  SizeText        The size in words, such as 1.2 KB.
  Modified        When it last changed, as a timestamp.
  ModifiedText    When it last changed, as YYYY-MM-DD HH:MM.
  Type            Its extension.
  Kinds           The kinds of file it is, such as Document or Image, from v4.1.4. A file can be
                  more than one kind. ABOUT_WORKFLOWS.txt lists them.
A row shows these rather than reading the file again.
A size, a date & a hash read left to right in every language, so isolate each one, with a bdi
element or unicode-bidi, or a language read from right to left reorders its parts.

$AllowUserIdentify is whether --User File Identification-- is on. An interface draws no Identify
control while it is off, because the core refuses every request & says so in words.

The script library carries Identify for any interface that wants it. The reply is one line of
JSON, & HRC2.readIdentifyReply(replyText) looks for it rather than assuming where it is, because a
PHP warning would come first.
  HRC2.bindIdentify(spec), One file's panel. Opening it identifies the file the first time.
    openId        The control that opens the panel.
    submitId      The button that identifies the file again, with a report when one is asked for.
    suffix        What the panel's elements are numbered with. The library uses
                  loadingCommandDiv, victoryCommandDiv & failureCommandDiv with it, as a
                  conversion does, & writes the summary into identifySummary with it.
    fileName      The file.
    reportId      The box that asks for a report.
    nameId        The report's name, which is greyed out unless the box is ticked.
  HRC2.bindIdentifyAll(spec), Every file the list shows. The same keys, with fileNames in
    place of fileName & no openId. The files are read when it is pressed.
  HRC2.configure({ identifyText: { yes, no, unknown, failure } }), The words it writes. They come
    from the language pack, as every word a user sees does.
A panel is any element with data-identify-file, naming its file, & data-identify-suffix.
The library writes into each element inside it with data-identify-field, naming one of Size,
Modified, Description, MimeType, Charset, ExtensionMatches, SHA256, SHA1, MD5, Details & Notes.
Details & Notes are one line for each entry, so give them white-space: pre-line.
Every value is written with textContent, because a record repeats what a file says about itself.
Never write one as markup.
A list drawn again keeps what was read. The library holds every record by its file's name &
writes it into the panels the new list draws.

--About Ticking Files & Workflows--

A file list may give every file a box, & the script library keeps which are ticked, by name, in
the order they were ticked, so the selection survives the list being drawn again. Each box is
  <input type='checkbox' class='hrc2-pick-box' data-hrc2-file='NAME' data-hrc2-row='ROW' data-hrc2-kinds='KINDS'>
NAME is the file, escaped for an attribute. ROW is the number the row's elements are suffixed
with, as ConvertGuiCounter1 numbers them. KINDS is $FileDetails[NAME]['Kinds'] joined by spaces.
An element with class hrc2-pick-mark beside it, in the same parent, is where the library writes the
box's place in the order. The included GUIs lay the real box over that square & hide it.
The bar above the column is optional, & the library finds each part by its id.
  hrc2SelectAll          A box that ticks every file, or none when any are ticked. It shows all,
                         some or none, & its own hrc2-pick-mark draws which.
  hrc2SelectMenuWrap     Holds the arrow & its menu. A click outside it closes the menu.
  hrc2SelectMenuButton   The arrow that opens hrc2SelectMenu.
  hrc2SelectMenu         Holds buttons with data-hrc2-select of all, none or kind:NAME.
  hrc2SelectionCount     Where the library writes how many are ticked.
Call HRC2.bindSelection with no arguments below the last row, every time the list is drawn. It binds the boxes &
the bar & draws the selection into them, & lets go of a file the list no longer holds.
HRC2.configure({ selectionText: { selected, usable } }) supplies the words. usable carries {fit} &
{count}, which the library fills in.
Draw the arrow's menu so it opens toward the side a line starts on. The included GUIs anchor it to
the left, & to the right where the page is dir rtl.

A ticked file converts every eligible ticked file. HRC2.bindRun does it for any control whose
static values name convertSelected, pdfworkSelected or filesToArchive, when its file is ticked among
others. A file is eligible when its own row has the same control, by the same id with its own row
number, so give every control & every name box an id ending in its row. Each eligible file is sent
in a request of its own, named by its own row's name box, & an archive is sent once holding them all.

The Workflows panel is HRC2-Workflows.js, & HRC2.startWorkflows(settings) starts it, handing it
the tokens & the file list. settings carries the words, as text, & the operations' names, as
operations, & may carry endpoint & elements to change where it posts & draws. The library finds
these ids unless elements names others.
  hrc2Workflows         The panel. Its button toggles it with toggle_visibility.
  hrc2WorkflowsButton   The button. The library keeps its aria-expanded true while the panel is open.
  hrc2WfBoxes           The three boxes, hidden until the library has drawn them.
  hrc2WfFilesBox, hrc2WfPickBox, hrc2WfRunBox
                        The boxes. The library adds hrc2-wf-attention to the one that needs it.
  hrc2WfFiles, hrc2WfPattern, hrc2WfSelect, hrc2WfAbout, hrc2WfRun, hrc2WfStop, hrc2WfStatus
                        Where it writes the files, reads a name pattern, lists the workflows,
                        describes one, runs, stops & reports.
Put the words for workflows being unavailable into hrc2WfStatus as the page draws it, so a page
whose library did not load still says something true. The library replaces them once it runs.
Draw the panel only while $EnableWorkflows is on. See ABOUT_WORKFLOWS.txt.
