--About Running Them--

  cd /var/www/html/HRProprietary/HRConvert2
  python3 Documentation/Build/hrconvert2-check.py
  bash Documentation/Build/hrconvert2-check.sh
  python3 Documentation/Build/hrconvert2-doccheck.py
  php Documentation/Build/hrconvert2-messages-cli.php

The first two check the code, the third the documentation, & the fourth each message the code
can log against the error catalogue. All four are run from the installation root, beside
convertCore.php, & the fourth takes none of the options below. Running one from
anywhere else exits two & says so, rather than reporting that a tree it cannot see is clean.

EACH READS THE ENTRY POINT & THE MODEL FROM THE CONTRACT, FROM v4.2.4.
$EngineEntryPoint & $EngineConfigModelProvider in Resources/Contract/app-engine-config.php name
the file the checks start from & the function that models the application's settings, which are
convertCore.php & applicationConfigModel() here. Another application on the Engine runs all three
unchanged. Until v4.2.4 both names were written into the checkers, & an application had to find
& change each.

  --list           Name every check & say in one line what it looks for.
  --only <name>    Run one check. This is what to use while fixing something.
  --quiet          Print nothing & report the answer in the exit code.
  --fix            The documentation checker only. Repair what cannot change a meaning.

EXIT CODES.
  0   Every check passed.
  1   Something was reported.
  2   It was asked something it could not answer.

Nothing stops early. An operator wants every fault in one pass rather than the first one
seven times.

--About Why There Are Two Of Them--

A checker has bugs like anything else, & a bug in a checker is INVISIBLE.
The result it produces when it is broken is the same silence it produces when the code is
clean, so nothing about the output says which one happened.

Two implementations sharing no code do not share bugs.
The Python parses. The Bash uses awk, grep & the shell. When they agree the answer is
probably right, & when they disagree exactly one of them is right.

A DISAGREEMENT IS DATA RATHER THAN NOISE.
The checks marked PYTHON ONLY below do not run in the Bash, & the Bash reads the call order
& the kernel more coarsely than the Python does. Its header & --About What They Do Not Do--
say why. Any other difference is a bug in one of them & is worth ten minutes.

hrconvert2-check.py IS AUTHORITATIVE.
The Bash tool is a second opinion. Where they differ & the difference is not a documented
one, believe the Python until proven otherwise.

--About The Checks--

  syntax      The php binary parses every file.
  balance     Every brace, parenthesis & bracket closes.
  order       Nothing in the main logic calls a component before that component is loaded.
  undefined   Every variable a function reads exists. PYTHON ONLY.
  duplicate   No function is defined twice.
  pins        Every version pin matches the file it points at.
  errno       Every error number raised is documented in ERROR_DESCRIPTIONS.txt.
  guard       Every component under Resources refuses to be loaded directly.
  contract    The Engine never calls application code.
  kernel      The kernel calls only itself, PHP & a guarded Engine. Coarser in Bash.
  caps        No comment line is entirely capitals.
  purge       Every cleanup at a return carries the comment that belongs with it.
  exit        Every function has one exit.
  config      Every setting a configuration template holds is modelled, & is held once.
  locals      Every lowercase local is destroyed before the function returns. PYTHON ONLY.
  sentence    Every comment block ends a sentence. PYTHON ONLY.
  name        No function parameter has a generic name. PYTHON ONLY.
  return      No function destroys a value it is about to return. PYTHON ONLY.
  args        Every call supplies the arguments its function requires. PYTHON ONLY.
  pairs       A function that returns a pair is never assigned whole to one variable. PYTHON ONLY.
  spacing     Separators & blank lines follow the house shape. PYTHON ONLY.
  frame       Every function opens & closes with a separator. PYTHON ONLY.
  globals     No function destroys a global it declares. PYTHON ONLY.
  configs     No setting is set by the administrator & by the Engine. PYTHON ONLY.
  owner       An owner is changed only through changeOwnerWithoutFollowing().
  static      No function destroys a static it keeps. PYTHON ONLY.
  stray       Nothing ships that is not part of the application.
  logo        The Engine's own logo is the file the Engine was distributed with.

This heading carried a count until v3.9.9 & the count was wrong by three. A number in a
heading is a status sentence with nothing checking it, so there is no number.

Each one is described at length above the function that performs it, & each description
says what it CANNOT see as well as what it can. Read those before chasing a finding.

EVERY CHECK BUT ONE WAS WRITTEN AFTER A FAULT REACHED A RUNNING INSTALLATION.
None of them are hypothetical. Until v4.0.0 none of them were caught by reading the code.
Two were, frame & globals, by a manual pass that read every line, & static was found by
another at v4.2.4. Each exists so that the next fault of its kind does not wait for a pass.

  order       A fatal on the first web request after the data location functions moved into
              the Engine. verifyGlobals called requestConvertLoc which called
              resolveDataLocation, which the Engine defines & which had not loaded yet.
              Reading the call sites showed nothing, because requestConvertLoc is DEFINED
              early in the file. It RUNS late.
  undefined   A parameter renamed in a function body & not in its signature. Valid PHP &
              fatal at runtime. Also found two variables being purged that the function
              never created, which produced a warning on every virus scan & shredded
              nothing while appearing to.
  errno       Seven quickDie calls raising numbers ERROR_DESCRIPTIONS.txt did not document.
              At v3.9.9 it was found to be blind to a number inside a plain die, because it
              read the source with every string removed. Two had never been documented,
              one of them written into a generated file as a string inside a string.
  contract    The Engine calling eighteen application functions, none deliberately. Each
              was a function moved without a helper it quietly depended on.
  guard       Written after noticing an earlier version of this check tested the raw text,
              so a file whose only mention of the guard was in a comment passed.
              At v3.9.9 the kernel passed with its guard deleted. It defines quickDie &
              declares $CoreLoaded, so both halves this check looked for were present
              without any guard at all. The kernel is now held to its own guard's exact
              shape, above its first function.
  kernel      Five functions went into the Engine & came back, locateDependency,
              reloadApparmorProfile, closeHRC2Connection (now closeClientConnection),
              extractCliOption & parseArgumentVector. Every one passed questions one, two & four of
              ABOUT_ENGINE_CONTRACT.txt & failed three, & every one was caught by hand.
              reloadApparmorProfile went back into the Engine at v4.0.5, with the sandbox
              it serves, which left nothing in the application that calls it.
  pins        Verified by hand every release until it was not.
  config      A fatal on --check-depends after eight settings were added to config.php, to
              the required list & to the file, & not to the global declaration where the file
              is loaded. The settings were tested by name through a list at runtime, so
              nothing read them anywhere & every other check saw nothing wrong.
              At v4.2.4 the list & the declaration went, because the kernel reads the names
              from the two templates. Two settings had been in neither since they were added,
              so the Pipeline Core never saw the administrator's value. The check holds each
              template to its model instead.
  locals      Six locals found & purged by hand across three functions in one round, then
              one hundred & twenty more the moment the check existed. Convention five had
              been enforced by attention alone.
  return      The locals check, obeyed without thought, added every lowercase parameter to
              every purge call, including the ones that were also the return value.
              purgeSensitiveMemory takes by reference, so eighteen functions returned NULL,
              including every conversion pipeline. The first symptom was a fatal three calls
              away from any of them. A check that produces instructions must know what its
              instructions can break, & this one now does.
  frame       Five functions in convertCore.php had lost a separator & were found by reading
              it line by line. A first draft of this check found nine more in three other
              files, which nobody had read that closely.
  globals     updateApplication purged $Lol, a global it declares. With memory protection
              on, every line ending printed after an update was gone. The same fault was in
              waitForStream in the Engine, & both read as correct code.
  configs     The one written first. The documents promised that an administrator's setting
              beat the Engine's, & the code reads the Engine's second, so it never could. No
              name was shared yet. This keeps the promise true rather than lucky.
  owner       Until v4.0.1 -fp & the installer gave the installation to the web server account
              with chown -R, & root then ran that code. Root also gave the capability cache to
              that account by name in a folder it could change, so a link planted there handed
              any file on the host over, & that was proven before it was fixed.
  static      verifySystemdRun purged the three statics holding its probe, so a probe its
              comments said ran once per request ran before every conversion.

--About What They Do Not Do--

THEY DO NOT RUN THE APPLICATION & THEY DO NOT TEST BEHAVIOUR.
A conversion that produces the wrong file passes every check in both of them.
They are a net for one class of fault. Testing is still testing.

THREE PATTERNS ARE REPORTED THAT ARE NOT FAULTS.
A foreach that binds by reference, written as foreach ($x as &$y), assigns $y where nothing
appears to. A file brought in with require may assign variables into the calling scope,
which is how a GUI supplies its button codes. A catch block binds its exception to a name.
The first & third are resolved by the Python. The second cannot be, because a parser reading
one function has no way to know what a required file will do.

A PIN WHOSE COMPONENT IS NOT INSTALLED IS SILENT.
Config, the GUI, the language pack & the install secret are all pinned & none of them is a
component with a version constant, so a missing match cannot be told apart from a pin that
was never meant to have one. The application reports that at load time instead.

THE BASH TOOL FOLLOWS ONE LEVEL OF CALLS RATHER THAN THE WHOLE CALL GRAPH.
It finds a component called directly by the main logic & not one reached through three
other functions. That second case is exactly what produced the fatal described above, so
the Python is the one to trust for order.

THE BASH TOOL DOES NOT IMPLEMENT undefined.
Working out which names a function creates needs a pass per function over its whole body,
& in awk on a file of seven thousand lines that took longer than everything else in the
script put together. A check nobody waits for is a check nobody runs.

--About Reading The Source Correctly--

BOTH TOOLS BLANK EVERY COMMENT & STRING LITERAL BEFORE READING ANYTHING.
A brace inside a string is not a brace. A variable name inside a regular expression is not
a variable. A check that reads raw text finds all of them & reports every one.

THE WHOLE FILE IS READ RATHER THAN ONE LINE AT A TIME & THAT MATTERS.
A string in PHP may run across several lines, & a reader that starts fresh on each line
treats the remainder of that string as code.
Generated code inside a string is the worst case, because it looks exactly like the thing
being searched for. The capability cache this project writes contains the text
if (!isset($CoreLoaded)) inside a string, & a per line reader reported it as a variable
read that was never declared.

Line positions are preserved through blanking, so a reported line number is the real one.
The comment case check reads the ORIGINAL rather than the blanked source, because a comment
is exactly what blanking removes.

Heredoc & nowdoc are not handled & this project does not use them. A file that starts using
one will produce noise rather than silence, which is the safer failure.

--About The Documentation Checker--

hrconvert2-doccheck.py READS THE DOCUMENTS THE WAY THE OTHER TWO READ THE CODE.
It judges every plain text & markdown file in Documentation & every pipeline's
DEPENDENCY_APPROVALS.txt. It has no twin.

  header      Every plain text file opens with the standard header & nothing else.
  sections    Every section is a rule, a title, a blank line, a body & a rule.
  whitespace  No line ends in whitespace & no three blank lines sit together.
  entries     ERROR_DESCRIPTIONS.txt holds one entry per number, in order, & its FILE &
              FATAL fields agree with the code wherever the code says so plainly. A
              reservation calls no documented number unused, from v4.3.1.
  messages    Every message the code raises is documented under its number, with a
              <PLACEHOLDER> for each part the code fills in, from v4.3.1.
  names       Every function & setting a document names still exists.

The layout it holds files to is the one ABOUT_DOCUMENTATION.txt describes. A changelog, the
application's CHANGELOG.txt or the Engine's ENGINE_CHANGELOG.txt, is the project's record, so
only its header is judged. Its entries are never changed, not even for whitespace, & a COMMIT
header that is factually wrong is the one exception. An application's ENGINE_RECONCILIATION_
file is judged the same way, from v4.3.1, because the names in it are that application's.

--fix repairs trailing whitespace & the blank lines between sections, which cannot change
what a document says, & nothing else. It never writes to a changelog. Every other finding
is a sentence somebody has to rewrite, so it is reported & left alone.

It was written after the manual pass at v4.0.0 found what it looks for by reading every
document. Its first run then found five entries whose FATAL field said the opposite of what
the code does, which nobody reading the documents alone could have seen. v4.3.0's QC pass
found twenty messages the code raised that no entry documented, with a script of its own,
which became the messages check at v4.3.1.
What each check cannot see is written above it, as it is in the other two. None of them can
tell whether a sentence is still true.

A NAME THE ENGINE'S DOCUMENTS CITE FROM THE REFERENCE APPLICATION PASSES BY A LIST, FROM v4.3.1.
The documents explain the Engine by what the reference application does with it, & an application
built on the Engine carries the documents & not that application. REFERENCE_NAMES &
REFERENCE_LABELS list each function & each setting they cite, with the reason it is cited, & a
name in either passes as one that exists does. A name in neither still fails.

--About The Message Checker--

hrconvert2-messages-cli.php HOLDS THE CODE & THE ERROR CATALOGUE TO EACH OTHER, FROM v4.3.1.
Rule 17 has every warning & every error documented in ERROR_DESCRIPTIONS.txt. The code checkers
hold an error to its number, & nothing held a warning to anything, or an error to its words, until
this. It was HRProtect's tests/check_messages.php.

  php Documentation/Build/hrconvert2-messages-cli.php

It reads every warningEntry(), errorEntry(), quickDie() & refuseCommandForUser() in the entry
point & in Resources, but ScanCore's own, with PHP's tokenizer, & runs none of it. Its header
says how a text & a number are read.

  UNDOCUMENTED  A call no line of the catalogue agrees with. Write the line.
  STALE         A warning's line no call agrees with. Correct it, or take it out.
  UNREADABLE    A call whose text or number cannot be read. Write it so that it can.
  VAGUE         A line with fewer than ten characters of its own, which would agree with every
                call. Write the words the message begins with.

A CALL & A LINE AGREE WHERE ONE COULD BE THE OTHER.
A placeholder in a line stands for something the call joins to its text, & something the call
joins stands for a placeholder, or for up to two words the line spells out. Neither stands for a
sentence, so a call that begins with a name does not agree with every line that ends as it does.

A MESSAGE HELD IN A VARIABLE IS EVERY TEXT THE VARIABLE IS GIVEN THAT CAN REACH THE CALL.
Each must have its line. A text another call handed back, through list(), cannot be read, so such
a call begins with a sentence of its own that says what was being done, & the notice follows it.
An error's number is read the same way, so a number chosen as the code runs is held to the lines
of each number it may be, & 0 is where a number is set before it is chosen.

A LINE IS HELD TO A CALL ONLY IN A TREE THAT HOLDS THE FILE ITS BLOCK NAMES, FROM v4.3.2.
The kit's catalogue documents the Example's convertCore.php & the Starter's app.php beside the
Engine, & an application that adopts it keeps every line, because an application adds to the
Engine's documents & takes nothing away. A block whose sentence naming its file names only files at
the root of an application, none of which the tree holds, is another application's, & is counted
apart rather than called stale. A block naming a file beneath Resources is held as ever.
The documentation checker holds the kit's documents to the Example's code, so it is run from the
Example's assembly. The other three pass from the Starter's as well.

It is a PHP build tool, gated three ways, as --About Where They Live-- describes. It gives up root
where it is given it, because it only reads, so it needs no contained run.

--About Adding A Check--

A convention nobody can verify is only taste.
Every check in these tools is a convention this project already had, turned into something
a machine decides rather than something a reader is trusted to notice. That is the whole
value & it is the test for whether a new one belongs.

IN THE PYTHON.
Write a function named check_<something> that accepts what it needs & a report callable,
& returns the number of findings. Add one line to the checks tuple in the main logic. That
tuple is the only place a check has to be registered.

IN THE BASH.
Write a shell function named check_<name> & add the name to CHECK_NAMES & to describe().
The name must match the Python's, because --only <name> should mean the same thing in both.

IN BOTH.
Write what the check CANNOT see in the comment above it. Every description in these tools
says that, & it is the difference between a finding somebody investigates & a finding
somebody learns to ignore.

--About Where They Live--

A DEPENDENCY PROBE RUNS IN A DISPOSABLE ENVIRONMENT & IN A DISPOSABLE DIRECTORY.
dependencyEnvironmentPrefix() in Dependency Core points HOME & every XDG location at
/tmp/<application>-probe-<account> & moves the working directory there before the command
runs. The folder is used only when it is not a link, the running account owns it & its mode is
0700. Tools read code & configuration from HOME, so a folder another account could write would
run that account's code as whoever probes, & --setup probes as root. A name another account
has taken is warned about & a folder with an unpredictable name is made instead.
Both halves are needed. A tool that reads HOME writes to the first; a tool that ignores it
& writes to a relative path writes to the second, & for a probe that would be the
installation root. That is where the .cache & .config directories came from.
It is applied to every version probe, the capability probe & the source build. It is NOT
applied to a package manager, which installs to the machine on purpose.
A sandboxed command needs none of this. sandboxCommand sets the same four variables to its
own tmpfs, so a conversion has never been able to write into the installation.

A SCRIPTED EDIT WRITES AFTER EVERY CHANGE, NEVER ONCE AT THE END.
Anyone editing this codebase with a script rather than by hand will reach for the obvious
shape, which reads the file, applies several changes to a string, & writes at the end. That
shape is a trap & it cost four rounds during v3.9.1.

When any one change fails to match, the write never runs & EVERY change is discarded,
including the ones that worked. Worse, a message printed beside each change prints before
the write, so the script reports success for edits that never reached the disk. A function
signature was changed, reported as changed, & was not changed. It was found later by a
checker noticing a symptom, & the time in between was spent reading correct code looking
for a fault that was not there.

  Write after each change & print only once the write has returned.
  Then a failure costs exactly the change that failed, & every message is true.

The failure to match usually has its own cause. An anchor built from memory, or from a grep
run several commands ago, does not match a file that has moved on. Anchor on a line number
from a grep in the SAME command, & re-read before constructing anything.

A PHP BUILD TOOL IS GATED THREE WAYS & EACH ANSWERS A DIFFERENT QUESTION.

PHP_SAPI says which interface php was BUILT to speak. It does not say who started the
process. A web server that shells out, a cgi wrapper, or a php-cli invoked from a request
handler all report cli & are all a web request wearing a different hat.

So the ENVIRONMENT is asked as well. A request carries a method, a host, a gateway, a
server name or a remote address, & a tool run from a terminal carries none of them. Either
gate alone is a gate somebody can walk around.

Then ROOT IS DROPPED if it was given. A test reads no secret, writes no file & touches
nothing outside its own output, so somebody typing sudo out of habit should not hand that
to it. SUDO_UID names whoever ran sudo & is where to land; without it the target is nobody.

THE GROUP IS DROPPED BEFORE THE USER & the order is not a style choice. After setuid the
process is no longer root & is no longer permitted to change its group, so dropping the
user first leaves the group as root permanently. It looks like it worked. The tools print
both ids for exactly that reason, so the failure is visible rather than assumed.

A PHP BUILD TOOL MUST REFUSE TO RUN OVER HTTP & THE CHECK IS ONE LINE.
  if (PHP_SAPI !== 'cli') { if (!headers_sent()) http_response_code(404); die(); }
Documentation/Build sits inside the web root, so a php file there is EXECUTED by the web
server rather than served as text. Both test tools extract functions from convertCore.php &
evaluate them, which is what a build tool needs to do & what nothing reachable over HTTP
should ever do. A python or shell tool leaks its source instead, which is untidy rather
than dangerous, & neither is secret.
A BUILD TOOL RESOLVES ITS PATHS FROM THE WORKING DIRECTORY & NEVER FROM __DIR__.
That looks like a convenience & is a second layer of the same protection. A web request
gets a working directory of the SCRIPT'S OWN FOLDER under every common configuration, so a
tool asked for Resources/Engine/engine.php finds nothing & stops. Two separate things have
to fail before anything runs: the SAPI check, & then the process has to be standing in the
installation root, which is not something a request can arrange.
Rewriting these paths as __DIR__ relative would make the tools work from anywhere, which is
exactly what is not wanted. Leave them relative.

Anything new added to that directory in PHP carries the same line, & its filename ends in
-cli so the constraint is visible in a directory listing. Reading a file to discover that
it will not run over HTTP is a thing nobody should have to do twice.

Documentation/Build is inside the web root & is served like anything else there.
A python file has no handler configured, so a web server hands back its source rather than
running it. Nothing in any of these tools is secret & this project is open source, so that
is untidy rather than dangerous. Both directories should still carry the index.html every
other directory in this project carries.

--Delete Build Environment-- in config.php removes the Dockerfile & a Build folder in the
installation root. It does not remove Documentation/Build, & it should not while the Resource
Manager & three source builds read scripts from that folder. None of the checking tools is
needed at runtime & none of them is loaded by anything.

--About The Engine's Tests--

THE CHECKERS DO NOT RUN THE ENGINE. THE TESTS DO, FROM v4.3.1.
Documentation/Build/Tests holds the Engine's own suites, the library they share & two runners. Its README.txt says
how to run each & what each holds. They came from HRProtect's tests, & the Engine keeps them so an application's
developer runs them rather than writing their own. The kit is not an application, so its assemble-example.sh puts
the Example together in a new folder, & the suites & the checkers are run from there.

A SUITE RUNS AS ROOT, & ONLY INSIDE contained.sh.
What the suites test is root's to do, from a folder only root may open to a file root writes without following a link,
so a suite keeps root rather than drop it as a build tool that only reads does. It is kept from a machine that matters
another way. contained.sh runs it in bubblewrap with everything the machine has mounted bound read only, & two
filesystems in memory as the only places anything can be written. The library does not take the runner's word for
that. It asks the kernel whether the filesystem root, & every other filesystem it can see, could be written, & stops
where one could. So a suite run by mistake outside the runner stops before it runs anything, & says why.
contained-install.sh adds an installation's folders in memory, for a test that installs & runs a whole application.

A SUITE IS A PHP BUILD TOOL, & CARRIES THE SAME MARKS.
Each file of PHP ends in -cli & refuses HTTP in its first statement, as --About Where They Live-- asks. Each finds
its library by the folder it is run in, & never from __DIR__, so it is run from the root of the application it
tests. A web request is refused by the first of those, & could not answer the library's question about the
filesystem if it were not.

A SUITE LIFTS THE REAL FUNCTION.
The library reads a function out of the tree under test & defines it as the tree has it, rather than copying it, so
a suite tests the code that ships. It refuses to lift one that removes, renames or runs anything unless the suite
names that call as one it expects. Where a check needs a fault at one exact moment, a name swapped between two looks
at it or an account that is not root, the library lifts the function into a namespace & the check stands in for what
it calls. Not a byte of the lifted code changes for it.

--About The Standing Findings--

A clean run is the goal & is not always the state.
As of v4.0.0 all three checkers report nothing outside Resources/ScanCore.
From v4.2.3 both linters report nothing inside it either, because the ScanCore v1.9 it bundles was cleaned up to them.

SCANCORE IS CHECKED HERE UNTIL IT HAS TOOLING OF ITS OWN.
ScanCore is HRProprietary software, so it is held to the same standard as this application,
& both linters check it by default. --no-scancore leaves Resources/ScanCore out of every check.
The summary counts ScanCore's findings apart from the application's, so a new finding in the
application is never lost among the ones ScanCore is carrying.
Two things are judged differently there, because ScanCore is a program of its own.
  1. A function name is matched within one program. ScanCore runs as a separate, sandboxed
     process, so a name it shares with this application never meets it in one request.
     The ScanCore pipeline is application code & is matched with the application.
  2. ScanCore never sets $CoreLoaded. Its guard is a refusal to run anywhere except a command
     line, & that is what the guard check holds it to.
Everything else ScanCore reports is real work for a ScanCore release.

The contract debt this section listed at v3.9.0 is cleared. The Engine called seven
application functions then, & it calls none now, so it is PORTABLE as well as usable.
Check eight fails the build if it reopens. See Documentation/ABOUT_ENGINE_CONTRACT.txt for
how each group was answered.

EVERY FINDING IS AN INSTRUCTION RATHER THAN A DIAGNOSIS.
A message says what to do, because the reader may not carry the whole convention set.
"never destroys $x. Add it to the purgeSensitiveMemory() call before the return" can be
acted on by somebody who has never read convention five. "convention five violated" cannot.
These tools exist so that compliance does not depend on who is reading the code or on how
much of it they hold in their head at once. A reader who runs them & does what they say
produces compliant code, & that is the whole point of writing the conventions down at all.

A FINDING THAT IS KNOWN DEBT SHOULD STILL BE REPORTED.
A green run that hides a real problem is worse than a red one that names it.
