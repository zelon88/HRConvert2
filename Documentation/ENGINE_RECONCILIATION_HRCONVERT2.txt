--What This File Is For--

EVERY APPLICATION CARRIES ITS OWN COPY OF THE ENGINE, & EACH COPY CAN CHANGE.

HRConvert2 & HRProtect each bundle the Engine, & neither knows the other exists. Both started from
the HRProprietary Engine v4.2.4 starter kit, & both may change their copy. HRProtect keeps the same
record of its own changes in ENGINE_RECONCILIATION_HRPROTECT.txt.

This file lists what HRConvert2 changed in its copy since that baseline, release by release, so the
two copies can be compared & merged into one Engine by hand. It records what changed, why, & what
an application on the other copy has to do to take the change.

Nothing here is an instruction to change the other copy. Reconciling is a deliberate step taken by
the Engine's maintainer, & this file is what that step reads.

--v4.2.5--

TWO ENGINE FILES CHANGED, IN THREE WAYS, & BOTH ARE BACKWARD COMPATIBLE.

--Release binaries--

WHAT CHANGED. buildOwnCopy() reads a new, optional key of a manifest entry's Fallback, Method. Where
Method is release, the line --install-depends & --update-depends print for an own copy, & the log
entry beside it, say the own copy is being fetched, as a release binary checked against its
checksum, rather than built from source, & no longer say a build takes an hour on an ARM board.
checkDepends() reads the same key of the entry its architecture resolves to, & hands it to
showDependencyFindings() as a new finding, FetchesRelease, so the line --check-depends prints
beneath such an entry says --install-depends fetches the own copy, where it said builds.
Nothing else differs. The command run, the folder it is handed, DEPENDENCY_PREFIX,
DEPENDENCY_VERSION & DEPENDENCY_SHA256, the checks made of what it installed & the rename into
service are exactly as they were. A Fallback with no Method, or any other, is said to build, as
every Fallback was before. An own copy is still called an own build wherever it is named, because
it lives where every own build does.

WHY. HRConvert2 v4.2.5 takes Dasel, yq, Pandoc & Resvg as the binaries their projects publish,
pinned by version & checksum, because no LTS release carries a version that works. Each is fetched
in seconds, & the old line told an administrator to expect an hour.

--A program that cannot say its version--

WHAT CHANGED. installDepends() took an entry whose program answers with no version this release can
read, unknown-version, as present, & went on to the next. It still does, unless the entry can have
an own build on this host, which the new function ownBuildIsDeclaredHere() answers exactly as
settleOwnBuild() decides it. Such an entry is now installed like any other, so settleOwnBuild()
makes the own build, which it already did for unknown-version wherever it was reached. Where it
makes one, the reason it prints says the program on the host answers with no version this release
can read, where it said the package manager's was unknown-version.

WHY. Before, --check-depends said --install-depends would build the own copy of such an entry, &
--update-depends did build it, but --install-depends did nothing. A program that cannot say which it
is may be another program of the same name. Ubuntu 24.04's dasel package is Dasel 2, which has no
version command & cannot do what Dasel 3 does, & its yq package is a different program in Python.
--install-depends --subsystem="Structured Data" called both present, & every Data conversion then
failed. An entry that can have no own build is untouched, so nothing that works is reinstalled.

TO TAKE BOTH. Copy the file, & raise the application's own pin, $RequiredDependencyCoreVersion in
its entry point, to v4.2.5. A manifest that never names Method behaves exactly as it did. An entry
with a Fallback whose program answers with no version is given its own build by --install-depends,
as --check-depends already told the administrator it would be. Nothing else in an application
changes. The pin is the only thing HRConvert2 moved for either change.

--A repair & a section the configuration utility only displays--

WHAT CHANGED. runConfigUtility() skipped every section a configuration model marks Writable FALSE in
every mode. A repair now adds a missing setting to such a section as it does to any other, & the
interactive walk & every reset still skip it. planConfigRepairOutcome() skipped those sections too
when it decided what a repair leaves missing, so a setting missing from one was neither added nor
named, & the stamp was raised over the file still lacking it, which every command then refused with
error 28000. It now looks at every section, so such a setting is named & the stamp kept wherever a
repair cannot add it.

WHY. HRConvert2 v4.2.5 adds ten format lists to its section Supported File Format Information, which
its model marks Writable FALSE, so its format lists are never reset or edited by the utility. The
repair INSTALLATION_INSTRUCTIONS.txt prescribes after the drop in added the two timeouts, raised the
stamp to v4.2.5 & left the ten out, & the installation then refused every command.
ABOUT_COMMAND_LINE_ARGUMENTS.txt already said a repair adds each missing setting & names any it
cannot.

TO TAKE IT. Copy the file, & raise the application's own pin, $RequiredSetupCoreVersion in its entry
point, to v4.2.5. A model with no section marked Writable FALSE behaves exactly as it did. One with
such a section has a missing setting there added by a repair, at the default its model holds, &
one without a default named. The pin is the only thing HRConvert2 moved for it.

THE KERNEL, engine.php, engineConfig.php, config-template.php, the Engine's depends.php, every other
Core, every Manager & the three checkers are unchanged, & are still the baseline's v4.2.4.

--What HRConvert2 now relies on, unchanged--

Nothing below is a change to the Engine. Each is something the Engine already did that HRConvert2
v4.2.5 depends on for the first time, so a reconciled Engine has to keep doing it.

AN APT ENTRY WITH AN EMPTY PACKAGE & A FALLBACK HAS ONLY ITS OWN COPY. installOneDependency() runs
no package manager for it, & believePackageInstall() has settleOwnBuild() fetch or build the own
copy, which is then the only copy. Dasel, yq & Pandoc are such entries.

ARCHITECTUREOVERRIDES MAY CARRY A WHOLE FALLBACK. Resvg names its package everywhere, & has an own
copy on x86_64 & arm64 alone, each with its own checksum, through an override per architecture.

cleanFiles($path, $allowedRoots) TAKES AWAY A WORK FOLDER. HRConvert2's new shared module,
workFolder.php, removes the folder a conversion worked in through it, held to the folder above.

sandboxCommand() PUTS AN INPUT & AN OUTPUT IN ONE FOLDER AT /work, & RUNS THE COMMAND THERE. The
LaTeX pipeline names TeX's document by its name alone, because paranoid TeX refuses one named by
an absolute path, & relies on --chdir /work, & on proc_open's working folder where no sandbox is built.

A SANDBOX PROFILE'S OPERATION TYPE NEED NOT BE IN THE LIMITS TABLE. The new profiles' types are
LaTeX, Data, Trace, Email & Markup, which $MaximumPerConversionResources does not name, so each
conversion of them is given --Default Per Conversion Resources--.

HRCONVERT2'S ERROR NUMBERS NOW RUN TO 48019. The Data pipeline reserves 44000 through 44019, LaTeX
45000 through 45019, Trace 46000 through 46019, Email 47000 through 47019 & Markup 48000 through
48019. HRProtect's own blocks are best begun at 50000, so the two never share a number.

--Seen, & left for the Engine's maintainer--

Each of these is in the Engine, was noticed while v4.2.5 was built, & was not changed, because an
Engine change is made deliberately & not on the way past.

sandboxCommand() APPLIES A PROFILE'S Environment ONLY INSIDE A SANDBOX. Where --Require Sandbox--
lets a command run without one, the variables a profile names are dropped. HRConvert2 passes TeX's
paranoid settings with the command for that reason, from the LaTeX & Markup pipelines, so they
hold either way. A profile's variables are what its tool needs, sandboxed or not.

THE BASE SANDBOX DOES NOT SHOW /var/cache/fontconfig. Every tool that finds fonts through
fontconfig, LibreOffice & Inkscape among them, reads every font on the host each time it starts.
The xelatex & pandoc profiles show the cache themselves, which halved the time a short LaTeX
document takes. Showing it read only in the base sandbox would do the same for every such tool.

--subsystem MATCHES ANY SUBSYSTEM WHOSE NAME HOLDS WHAT IS TYPED. --subsystem=Data would have caught
Metadata too, for --install-depends & --uninstall-depends alike, so HRConvert2 named its new
subsystem Structured Data. A whole name match, or a match on whole words, would remove the trap.

THE ENGINE'S config-template.php NAMES HRCONVERT2'S OPERATION TYPES as the valid keys of --Maximum
Per Conversion Resources--, which is application knowledge in an Engine file, & does not name the
five v4.2.5 adds. An administrator may still add a key for each.

Documentation/Build/hrconvert2-release-fetch.sh IS GENERIC. It fetches, checks & installs any
release binary for any manifest entry, as build-7zip.sh builds one, & knows nothing of HRConvert2
but its name. It is a candidate for the kit, under a name of the Engine's.

--A sandbox profile can require a sandbox--

WHAT CHANGED. A sandbox profile may carry a new, optional field, RequireSandbox. The new function
sandboxRequiredProfiles() names every profile whose RequireSandbox is TRUE, compared strictly, so a
1 or a 'TRUE' is not a request, lowercase & in the order the application declared them.
sandboxCommand() asks it, & where no sandbox can be built it refuses such a profile whatever
sandboxIsRequired() says, writes a warning naming the profile, & returns FALSE as it does for every
refusal, so no caller changes. Where a sandbox is not otherwise required, -v's Sandbox required line
says NO, except for the profiles it names, & the operating environment check's FAILED line for the
sandbox says their conversions will be refused. A sandbox that can be built is built exactly as
before. A profile without the field, & every profile of an application that sets none, behaves
exactly as it did, so HRProtect needs nothing to take the change.
config-template.php's --Require Sandbox-- & --Require Sandbox On Docker-- say so. Neither setting
changed, & neither did its default.

WHY. --Require Sandbox-- set to FALSE accepts the risk of a tool's own bugs where no sandbox can be
built. A tool that reads a file an upload names by its path, & writes it into what it makes, needs no
bug, & HRConvert2 v4.2.7 traced seven that nothing passed with their commands stops: LibreOffice,
Calibre, Inkscape, Resvg, Dia, Assimp under the meshlab profile, & FFMPEG with FFprobe. A tool with a
setting that stops it, as Pandoc's --sandbox, paranoid TeX & Graphviz's SERVER_NAME do, carries the
setting with its command instead, & its profile does not set the field.

THE KERNEL, engineConfig.php, the Engine's depends.php, every Core, every Manager & the three
checkers are unchanged by v4.2.7.

--v4.3.0--

ONE ENGINE FILE CHANGED, & ONE FOLDER IS NEW. BOTH ARE BACKWARD COMPATIBLE.

  Resources/Engine/engine.php                 v4.2.7 to v4.3.0
  Resources/Engine/Sandbox/                   New. passwd, group, machine-id & index.html.

HRConvert2 v4.3.0 requires Engine v4.3.0. Both changes close what v4.2.7 saw inside a sandbox & left
below for this file's maintainer. A fault inside the sandbox is fixed in the Engine when it is found,
& recorded here, so the two copies can still be merged with the reason for each change.

--A sandbox shows the Engine's own identity, & none of the host's--

WHAT CHANGED. sandboxCommand() no longer shows a tool the host's /etc/passwd, /etc/group or
/etc/machine-id, or the host's name. The new function sandboxIdentityFlags() binds the passwd, group
& machine-id in Resources/Engine/Sandbox in their place, names the host sandbox with --hostname, &
runs the tool as the one account those files name, sandbox, whose uid & gid are 1000, with --uid &
--gid. verifySandboxLauncher() returns a fourth value, whether the launcher it built carries
--unshare-user --disable-userns, which it does exactly where bubblewrap 0.8 or later built a sandbox
with them. --uid needs --unshare-user, so only there is the account chosen. Elsewhere the tool runs
as the web server's account, which only the host's passwd names, so the host's passwd & group are
shown as before. The machine-id & the host name are the Engine's either way. A file missing from the
folder is warned of, & the host's is shown in its place, so a conversion still runs. -v prints a new
line, Sandbox identity, OWN or HOST, saying what a tool sees.

WHY. HRConvert2 v4.2.7 found Calibre copying the host's /etc/passwd into a book an EPUB's manifest
named it in, inside its sandbox. The base sandbox showed it, & the group file, because LibreOffice
aborts with Signal 6 when getpwuid() finds no user, & the machine-id beside them. A passwd naming the
one account a tool runs as answers getpwuid() as the host's did, & a tool that copies it copies
nothing of the host's. A machine-id names its host for good, & the host's name is the next thing a
tool could copy, so neither is the host's either. LibreOffice, Calibre & every tool HRConvert2's
format suite runs convert as before under the new account.

HOW TO TAKE IT. Copy Resources/Engine/Sandbox, sandboxIdentityFlags(), the fourth value of
verifySandboxLauncher(), the changes to sandboxCommand() & the Sandbox identity line of
showVersionReport(). A caller reading two or three values from verifySandboxLauncher() is unaffected,
& so is every sandbox profile. A tool that read a file below a host account's home, which nothing in
either application does, would find no such account. HRProtect needs nothing more, unless a tool of
its own is installed below /opt, which the next change is about.

--The base sandbox no longer shows /opt--

WHAT CHANGED. --ro-bind-try /opt /opt is gone from the base sandbox. A profile shows the folder of a
tool installed below /opt in its ReadOnlyPaths.

WHY. Nothing every dependency needs is installed below /opt, & what is there is whatever an
administrator put there. HRConvert2's installation guide clones its own source below it.

HOW TO TAKE IT. A profile whose tool lives below /opt names its folder. HRConvert2's calibre profile
names /opt/calibre, where Calibre's own installer puts it. An application on the other copy finds its
tools below /opt once, with command -v & readlink -f on each tool a profile runs, & names each folder.

--What HRConvert2 now relies on, unchanged--

Nothing below is a change to the Engine. Each is something the Engine already did that HRConvert2
v4.3.0 depends on for the first time, so a reconciled Engine has to keep doing it.

AN OPERATION PIPELINE LOADS A SHARED MODULE AS A CONVERSION PIPELINE DOES. Identify declares the new
ffmpegDemuxers.php & OCR the new imageMagickDecoders.php beside libreOffice.php, & the Pipeline Core
loads each once per request before the first pipeline that declared it, whatever its kind.

A NEW SHARED MODULE IS PINNED BY HAND ONCE. --build --pins --write rewrites the version of every module
in $EngineAcceptedSharedModules & adds none, so each new module was added to the table by hand first.

--Seen, & left for the Engine's maintainer--

A SANDBOX SHOWS THE WEB SERVER'S ENVIRONMENT. Bubblewrap passes its own environment into the
namespace, & a tool can read it from /proc/self/environ & copy it into what it makes, as Calibre copied
the passwd. Apache's names its account & its folders, & an administrator's SetEnv & PassEnv add
whatever they name. --clearenv with PATH, LANG & what each caller names set again would show none of
it. Each tool's need for a variable of the host's has to be traced first, as v4.2.7 traced paths.

TWO OF THE ENGINE'S MESSAGES ARE NOT WHAT ERROR_DESCRIPTIONS.txt SAYS. 31007 is raised for a manager
role whose subcomponent could not be loaded as well as for one not recognized, & only the second is
documented. 32011 is documented as naming the path it could not create, & names none. HRConvert2 v4.3.0
found both comparing every message the code raises with the one documented under its number.

--v4.3.1--

ONE ENGINE FILE CHANGED, & IT IS BACKWARD COMPATIBLE. SEVEN OF THE ENGINE'S MESSAGES ARE DOCUMENTED AGAIN.

  Resources/Engine/Cores/pipelineCore.php     v4.2.4 to v4.3.1

HRConvert2 v4.3.1 requires Pipeline Core v4.3.1. The Engine itself is v4.3.0, as before, & nothing
else in it changed.

--A converter that ran to its end is not asked again--

WHAT CHANGED. The Pipeline Core has three new functions. pipelineRetryIsDue() takes the path a
converter writes, the attempts made & the exit status of the last one, & is TRUE before the first
attempt, & after it only where pipelineCommandWasStopped() says a signal ended the last one & where
pipelineAttemptIsDue() allows another. pipelineCommandWasStopped() is TRUE for an exit status of 129
through 159, which is 128 plus a signal numbered 1 through 31. runPipelineCommand() runs a command
with its standard error sent to its standard output, & returns what it printed & its exit status.
pipelineAttemptIsDue() is unchanged.

WHY. Seventeen retry loops in fifteen of HRConvert2's pipelines asked a converter that ran to its end
& left no file as many times as --File Operation Retry Count-- allows, five by default, with six
seconds of waiting between them, & a converter given the same file did the same each time. The
Document pipeline had the rule in its own code from v4.3.0. A rule every pipeline keeps belongs to the
Pipeline Core, as pipelineAttemptIsDue() does, & the number a signal is told by is held in one place.
Bubblewrap & the shell both report a process a signal ended as 128 plus the signal's number, which
HRConvert2 measured with bubblewrap 0.9 & dash, inside a sandbox & out. A status above 159 is a
converter's own. FFMPEG from 6.1 exits with its own error code, 183 for a file it reads nothing in &
234, 254 or 255 for others, & msgconvert's Perl exits with 255 where it dies, so HRConvert2's own
tests found both asked again for a file neither could read while the rule was above 128.

HOW TO TAKE IT. Copy the three functions & raise the application's pin to the Pipeline Core. A
pipeline that calls none of them is unaffected. Every pipeline in HRConvert2's library that retries
calls them from v4.3.1, & libreOffice.php calls pipelineCommandWasStopped(), so an Engine that runs
that library needs all three. HRProtect's own pipelines need nothing more.

ERROR_DESCRIPTIONS.txt documents 503, 504, 31007, 31018, 31019, 32011 & 34002 as the Engine raises
them. v4.3.0 left 31007 & 32011 below for this file's maintainer, & the new messages check found the
other five, each documented without the detail the Engine adds to it. Nothing in the Engine's code
changed for any of them. 31007 is documented with both its messages, & 32011 without the path it
never named.
hrconvert2-doccheck.py gains that check, which compares every message the code raises with the ones
documented under its number, & its entries check reads each reservation, which may call no documented
number unused, as 41000's did once 41009 was documented. ABOUT_QUALITY_CONTROL.txt names both.
ABOUT_PIPELINE_COMPONENTS.txt & CREATING_CONVERSION_PIPELINES.txt describe the three new functions.

A SECOND KIND OF PIPELINE DECLARES ffmpegDemuxers.php. The Metadata pipeline, an operation pipeline,

was refused in a message would name nothing. HRConvert2's Metadata pipeline keeps whether it built a
command apart from what sandboxCommand() returns, from v4.3.1, so it reports a refusal as one either
way.

WHAT CHANGED. A manifest entry's Fallback may say 'Always' => TRUE. The new ownBuildIsAlways() is
TRUE where this host can have the entry's own build & the Fallback it resolves to says so.
resolveDependencyChoice() then reports the own build's state & nothing else. It is absent where
nothing is at the own build's path, with a line saying only the own build is used, misconfigured
where the own build is not root's alone or the conversion account cannot run it, & the own build's
own state otherwise, & it never falls back to the package manager's copy. settleOwnBuild() never
asks the package manager's copy & never takes the own build away for it. dependencyIsInstalled()
counts only the own build in service. checkDepends() never says the package manager's copy
qualifies. installOneDependency() installs nothing through the package manager, &
believePackageInstall() builds the own copy as before. updateDepends() upgrades nothing through the
package manager for such an entry, & counts it installed where the package manager's copy is, so a
host that had the package gets the own build. uninstallDepends() is unchanged, & still removes the
package with its subsystem.

WHY. An own build was used only while the package manager's version fell outside the entry's window,
so a host whose package manager caught up went back to the copy it keeps current. That is right for
7-Zip, & wrong for a build whose point is what it leaves out. HRConvert2 builds Assimp with three
importers, because Assimp chooses an importer by what a file holds where none claims its extension,
so every importer it carries is reachable from an upload, & a distribution's carries seventy.
Debian's sid carries 6.0.6, inside any window the entry could set.

HOW TO TAKE IT. Copy ownBuildIsAlways() & the changes to the seven functions above, & raise the
application's pin to the Dependency Core. An entry whose Fallback does not say 'Always' behaves
exactly as before, which is every entry HRProtect has.

--A sandbox profile may hold its tool's address space--

WHAT CHANGED. A profile may say 'AddressSpaceLimit' => TRUE. limitCommand() then puts prlimit --as=
in front of the command, with the memory the profile's type is allowed in bytes, inside any scope, &
does so where per conversion limits are turned off too, because the profile asked for it & the host
did not. prlimit is found with locateDependency(), & where it is missing a warning says so & the
conversion runs without the ceiling, because limitCommand() never refuses. The new
sandboxProfileAsks() says whether a profile gives a setting a true value, read as
sandboxProfileFlags() reads MapToRoot. The verbose Conversion Scope line names the address space, &
says off where per conversion limits are.

WHY. A scope's MemoryMax kills a tool only once memory is used, & no scope can be made on a host
whose kernel delegates no cgroup controller, where a conversion is only deprioritized. HRConvert2
found a 20 byte glb that makes Assimp ask for 4.1 GiB. Under a 2048 MiB address space it fails at
once with std::bad_alloc, having used 14 MiB. An address space is not the memory used, so a tool
that reserves far more than it uses, as a JVM does, would be stopped by it, & only a profile
measured under it asks for it.

HOW TO TAKE IT. Copy sandboxProfileAsks() & limitCommand(). A profile that does not ask is limited
exactly as before.

--A profile mapping to root names one account--

WHAT CHANGED. The new sandboxAccountFlags() returns the number of the Engine's own account & the
--uid & --gid flags that choose it. sandboxIdentityFlags() takes the flags from it, &
sandboxCommand() takes them away again for a profile whose MapToRoot is set, so that profile's --uid
0 --gid 0 is the only account named.

WHY. bubblewrap 0.9 prints Only the last --uid option will take effect, & the same of --gid, where
either is given twice, & every MeshLab conversion carried both lines in its output from v4.3.0,
which named the Engine's own account beside a profile's.

HOW TO TAKE IT. Copy sandboxAccountFlags() & the changes to the other two. HRProtect declares no
profile mapping to root.

--A converter that crashed is not asked again--

WHAT CHANGED. pipelineCommandWasStopped() is TRUE for 137 & 143 alone, which are KILL & TERM, where
it was TRUE for 129 through 159. pipelineRetryIsDue() is unchanged, & reads it.

WHY. A memory ceiling & a supervisor stop a converter with KILL or TERM, & an attempt made again may
finish. A converter that crashed, with SEGV, ABRT, BUS, FPE or ILL, is given the same file again &
crashes again. A model that crashed Assimp was converted, & crashed it, as many times as --File
Operation Retry Count-- allows.

HOW TO TAKE IT. Copy the function & raise the application's pin to the Pipeline Core. Every pipeline
that retries asks a crashed converter once. HRConvert2's libreOffice.php asks the function whether
something stopped LibreOffice, so a LibreOffice that crashed is asked once too, & its comment, & the
Document pipeline's, say so.

--The Engine's documents--

ABOUT_DEPENDENCIES.txt documents 'Always'. ABOUT_RESOURCE_RATE_LIMITING documents AddressSpaceLimit,
& convertCore.php's list of profile fields names it. ABOUT_PIPELINE_COMPONENTS.txt &
CREATING_CONVERSION_PIPELINES.txt say what is asked again. ERROR_DESCRIPTIONS.txt says it of 7001 &

--What HRConvert2 now relies on, unchanged--

Nothing below is a change to the Engine. Each is something the Engine already did that HRConvert2
v4.3.2 depends on for the first time, so a reconciled Engine has to keep doing it.

AN OWN BUILD'S VERSION IS COMPARED IN THREE PARTS. compareVersionMinimum() compares the patch level
& reads one a version leaves out as 0, so an Assimp reporting 6.0, as every Assimp did before patch
0008, is older than 6.0.6. The Assimp entry's floor, its Fallback's Version & what the own build
reports are all 6.0.6.

A FALLBACK MAY PIN NO CHECKSUM. buildOwnCopy() hands DEPENDENCY_SHA256 empty where the Fallback's
Sha256 is, & build-assimp.sh pins its source by commit instead.

--Seen, & left for the Engine's maintainer--

A FALLBACK THAT CHANGES ONLY ITS PATCHES IS NOT BUILT AGAIN. settleOwnBuild() builds an own build
again where it answers below the version pinned, & a build carrying a new patch on the same release
answers the same version. HRConvert2's Assimp is such a build, & a patch added on 6.0.6 reaches a
host that built 6.0.6 already only once its build is moved out of the builds folder &
--install-depends is run again. A mark the build leaves of what made it, such as a checksum of the
Fallback's BuildCommand & of the script & patches it runs, compared before a build is called
unchanged, would catch it.

A FALLBACK CANNOT PIN A COMMIT. The Engine hands over a version & a checksum, & a build fetched by
commit holds its commit in its own script. A Commit field handed over as DEPENDENCY_COMMIT would put
that pin in the manifest beside the others.

A SUBSYSTEM TWO TOOLS SERVE IS JUDGED BY THE ONE THAT CAN BE ASKED. capabilityVerdict() reads every
record naming a pipeline's subsystem, & one that could not answer adds nothing, so where one tool of
two answers, its answer contradicts every format only the other handles. HRConvert2's 3D Models had
Assimp answer for MeshLab, & v4.3.2 asks Assimp nothing instead, which is a change to its manifest &
none to the Engine. A record could say which of a pipeline's formats it answers for, or a direction
an installed tool of a subsystem cannot answer could leave the subsystem unknown, which would stop
narrowing wherever such a tool is installed, so each subsystem would have to be read first.

--v4.3.5--

THREE ENGINE FILES CHANGED. EVERY COMMAND HAS A TIME LIMIT, & NOTHING AN INTERRUPTED COMMAND LEFT IS KEPT.

  Resources/Engine/engine.php                 v4.3.3ur, changed again
  Resources/Engine/Cores/pipelineCore.php     v4.3.2ur, changed again
  Resources/Engine/config-template.php        v4.3.1r to v4.3.1ur

The two already marked ur keep their stamps, as the note under v4.3.4 says a stamp ending ur does.
Every change here is HRConvert2's & is un-reconciled. An application that takes them needs
--config --repair once, because the template gains two settings the kernel then requires.

--A time limit for every command--

WHAT CHANGED. New resolveConversionRuntime($sandboxProfile) returns whether a time limit applies & its
seconds. It reads the profile's type from new --Maximum Per Conversion Runtime-- & a type it does not
name from new --Default Per Conversion Runtime--. 0 is no limit. An entry that is not a whole number of
seconds is warned of & the default is used, & a default that is not one is warned of & 600 is used.
limitCommand() puts timeout, found by locateDependency(), outside everything else it builds, for every
command, whether or not --Enable Per Conversion Limits-- is TRUE. It sends TERM & never KILL, so a
command it stops exits 124 & is never asked again. Where timeout is missing it warns & runs the command
without one. The Engine's config model holds both settings, without a Default, so the template's is
the one a reset writes.

WHY. A converter that never finishes holds its worker for ever with resource awareness off. Seven of
HRConvert2's pipelines bounded their own converter, each with its own figure, & the rest none, which the
maintainer asked to have replaced by one clean, config driven limit at the Engine. Its own table, because the listener scales the resources table &
hands it back as two figures, & a time limit must not shrink with load.

HOW TO TAKE IT. Copy resolveConversionRuntime() & limitCommand(), & the two settings into the Engine's
template & model. Each application's sandbox profiles name its types, & its table names the same
types. A pipeline that ran a timeout of its own drops it & keeps its handling of 124.

--A data limit where no scope can be made--

WHAT CHANGED. Where per conversion limits are on & verifySystemdRun() reports no scope, limitCommand()
adds prlimit --data, of the type's memory figure, nearest the command, beside the --as a profile may
already ask for, so one prlimit sets both. Where prlimit is missing it warns, & a profile asking for
an address space limit keeps its own warning. The two warnings verifySystemdRun() writes say the fallback
is scheduling priority & a data limit on each process.

WHY. Most hosts cannot make a scope for the web server account, so a conversion there had no memory
ceiling at all. A data limit needs no permission & does not stop a tool that reserves more than it
uses, as an address space limit does. Every case of HRConvert2's format suite converts under the
template's figures. The figures measured are in DEVELOPMENT_NOTES.txt under Per Conversion Limits.

--Nothing an interrupted command left is kept--

WHAT CHANGED. The Pipeline Core gains pipelineCommandWasInterrupted($exitStatus), TRUE for 124 & for 129
through 159, & discardInterruptedOutput($outputPath, $exitStatus), which removes a file an interrupted
command left at the path & warns, & warns of the time limit whatever was left. pipelineRetryIsDue() calls
it after every attempt, before it decides.

WHY. A converter a ceiling killed after writing part of its file left the part, so no attempt followed
& the part was offered as the result. The time limit makes a stopped command an ordinary event.

HOW TO TAKE IT. Copy the two functions & pipelineRetryIsDue(). A pipeline that retries through it needs
nothing more. One that runs a command another way runs it through runPipelineCommand() & hands the status
to discardInterruptedOutput(). HRConvert2's OCR, Metadata, Archiver, PDF, Archive, Document & Model
pipelines, & its libreOffice.php shared module, do.

--A shell that stays--

Ubuntu 24.04's dash keeps sh -c between PHP & a command, so bubblewrap's parent was the shell, & a pipeline
that killed the shell took the sandbox with it. timeout is bubblewrap's parent now. A pipeline that kills a
command it started has the shell replace itself, by starting the command with exec, as HRConvert2's Identify
does, or stops every process under it, as its archive extraction does.

--Seen, & left for the Engine's maintainer--

THE MANIFEST DOES NOT NAME timeout OR prlimit. The Engine runs both, as it runs nice & systemd-run, &
HRConvert2's copy of the manifest predates the 'system' type canon's v4.3.3 manifest declares Coreutils
& Util-linux with. Canon's Coreutils names timeout. Its Util-linux names setsid alone, & needs prlimit,
which HRConvert2's Engine has run since v4.3.2.

THE SETUP CORE'S WARNING THAT A KERNEL DELEGATES NO CGROUP CONTROLLERS still says per conversion limits fall
back to scheduling priority. They fall back to a data limit on each process too. The Setup Core is canon's,
& unchanged here.

THE ENGINE'S CONFIG MODEL GIVES --Maximum Per Conversion Resources-- A Default without Scan, which the
template has, so a reset of that table writes one without it & the built-in Scan ceiling is used, with a
warning. collectConfigModel() overwrites it with the template's wherever the template can be read.

--Maximum Per Conversion Resources-- NAMES FIVE TYPES NO PROFILE HAS: Spreadsheet, Presentation, Audio,
Subtitle & Stream. LibreOffice's work is Document's, & FFMPEG's is Video's, so the five are never read.
The new runtime table names only the types the profiles name.
