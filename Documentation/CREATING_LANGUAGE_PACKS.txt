ADDITIONAL INFORMATION ...
HRConvert2 has one default language set in config.php and multiple languages that can be selected by the user at runtime.
The default language used by HRConvert2 can be selected by adjusting the --Default Language-- section of config.php.
Administrators can prevent user language selection by adjusting the --Allow User Selectable Language-- section of config.php.
If --Allow User Selectable Language-- is set to TRUE in config.php, users can adjust language output using a 'language' GET request.
To send a GET request, append the following string to the end of the HRConvert2 URL (without quotes):  '?language=<LANGUAGE_CODE>'
Substitute <LANGUAGE_CODE> for the code of an installed language as listed in the --Supported Languages-- section of config.php.
Most languages are represented by two letter ISO 639-1 codes. Aramaic has no ISO 639-1 code, so aii & arc use ISO 639-3 codes instead.
If a user submits an unsupported language the default will be used instead.
If a supported language is missing required files, HRConvert2 falls back to the Default Language, then to English, & logs a warning for each.
A pack that reports a version the core does not expect is still used. A warning is written & a baseline pack loaded underneath it supplies any string it lacks.
A fatal error, 16, occurs only when none of the three is available.

--About Language Packs--

HRConvert2 is designed to make localization into a new language by creating 'language packs' easy.
This document will teach administrators and developers how languages are handled and structured.
In this document when we refer to a GUI, we refer to a set of files required to render HRConvert2.
In this document when we refer to a language pack, we refer to the files required to localize a GUI into a specific language.

An HRConvert2 Language Pack is made up of 3 components. Each component serves a specific function. The 3 components of a Language Pack are:

  1. languageStrings.php
  2. flag.png
  3. index.html

NOTE. verifyLanguage() requires languageStrings.php & flag.png. A pack missing either one is not loaded.
index.html is required by the document root protection mechanism rather than by the language subsystem, but every folder needs one.

These components are stored in a folder named after the language code.
Most are two letter ISO 639-1 codes.
The 'aii' & 'arc' languages have no ISO 639-1 codes, so ISO 639-3 codes are used instead.
The ISO named folder is then placed inside the 'UI/<GUI>/Languages' subdirectory of the installation location.
The language code must also be added to the --Supported Languages-- section of config.php or it will be ignored.
The $SupportedLanguages variable is a keyed array of language code & endonym.
The KEY is the language code & the folder name.
The VALUE is the endonym, which is the name of the language written in that language itself.
The endonym is used as the alt text & title of the flag button in the selector bar.
A user who has landed on a language they cannot read still recognizes their own.
Adding an entry as a flat list value rather than as a key will break language verification.

If --Allow User Selectable Language-- is enabled, users will be able to select this language pack by sending a GET request.
Users should not access the GUI directly. All requests should be directed to convertCore.php which will construct the GUI on-demand.

During operation, HRConvert2 initializes the language using the following process:

  1. Initialize the language to english.
  2. Build an array of languages that are included with HRConvert2.
  3. Check if the $SupportedLanguages variable from config.php is set properly.
    3a. If not, use the included array of default languages instead.
  4. If a language was specified via GET or POST input, sanitize it.
  5. Check if the $DefaultLanguage variable from config.php is set & supported.
    5a. If not, use english instead.
  6. Check if the $AllowUserSelectableLanguage variable from config.php is set.
    6a. If not, use $DefaultLanguage instead.
  7. Check if a language was specified via GET input.
    7a. If not, use $DefaultLanguage instead.
  8. Check if the specified language is supported.
    8a. If not, use $DefaultLanguage instead.
  9. If all checks have passed and the specified language is supported, set the language to use to the one specified via GET request.
  10. Reset the language GET variable to the currently specified language so future requests will continue using the same language.
  11. Define all required language related files & folders.
  12. Check for the existence of languageStrings.php & flag.png.
    12a. If either is missing, try the Default Language, then English, & warn for each.
  13. Load a baseline pack from the remaining rungs first, then the chosen pack over the top of it.
  14. Compare $LanguageVersion to $RequiredLanguageVersion.
    14a. If they do not match, warn. The pack is still used & the baseline supplies any string it lacks.
  15. If no pack is usable at any of the three rungs, terminate with error 16.

--Administration Tips--

Language Packs are contained within GUIs. GUIs typically contain multiple language packs.
A GUI missing a language pack that config.php lists falls back to the Default Language, then to English, & writes a warning.
An error occurs only if none of the three is in that GUI.
Errors will occur if an installed GUI does not support the following colors: Red, Green, Blue, Grey, Orange, Purple, Dark.
Server administrators can:
  Enable or disable language packs by modifying the --Supported Languages-- section of the config.php file.
  Add or remove language packs to a GUI by creating a folder in the 'Languages' subdirectory of each enabled GUI folder.
  Allow or prevent language selection via GET request by modifying the --Allow User Selectable Language-- section of the config.php file.

--Development Tips--

The modular design of HRConvert2 is designed to make modifications easily translatable to other languages.
If you are maintaining a branch of HRConvert2 and are focusing on a single language pack you can build your logic directly into the GUI pages themselves.
Any language pack files that are not needed can be left blank after the opening PHP tag.
To translate HRConvert2 into a new language, copy an existing language pack and translate the 'Languages/<LANGUAGE_CODE>/languageStrings.php' file into the desired language.
To install a new language pack, place a folder named after a 2 digit ISO 639-1 language code into the 'Languages' subdirectory of the installation location.
To enable or disable a language pack, update the --Supported Languages-- section of the config.php file.
GUIs can utilize the icons and scripts in the default Resources directory or include their own.
If any non-stock directories are added to HRConvert2, a copy of index.html must be pasted into the directory.
Do not create any files named index.html. This filename is reserved by the application for document root protection mechanisms.
Upper Case variables are Global in scope. Lower case variables are severely limited in scope.
Limited scope variables are destroyed with purgeSensitiveMemory() as soon as they are no longer required.
Your Language Pack can come with its own Documentation folder, or any additional files or folders you wish.
Every folder requires the stock index.html. Copy and paste an existing one.

By placing localization specific code into 'Languages/<LANGUAGE_CODE>/languageStrings.php', GUI updates can be easily applied from one language pack to another.

--About Language Pack Versions--

Every language pack declares its own version in languageStrings.php as $LanguageVersion.
The core carries the version it is built against as $RequiredLanguageVersion.
A pack whose version does not match the core is STILL USED, & a warning names it.

THE COMPARISON IS REPORTED, NOT ENFORCED.
A GUI reads a fixed set of string variables, & a pack that does not define every one of them
would leave blanks in the interface. In PHP 8 an undefined variable also emits a warning, & a
warning printed into an AJAX response corrupts it, because the GUI treats every line of that
response as a filename. A missing string is therefore not a cosmetic problem.
The core answers that with a BASELINE rather than with a refusal. buildGUI() loads another
pack from the ladder first & the chosen pack over the top of it. A later assignment wins, so
every string the chosen pack defines is shown in the user's language & every string it lacks
falls through to the baseline. No interface can print an undefined variable.

The version is checked in buildGUI(), AFTER the pack has been loaded.
It has to be, because the version is declared inside the file being checked.
This is the opposite of how a GUI is checked, & the difference is deliberate.
A language pack contains nothing but variable assignments, so a stale one can be completed
by what is loaded underneath it. A GUI prints HTML & cannot be repaired that way, which is
why a GUI is checked before it is loaded & refused when it does not match.

Refusing a pack over its version would mean an installation that gains one new string loses
every translation it has. A page in the wrong language beats no page at all, & a page that is
right except for one new button beats both. So the version is a maintenance signal for the
administrator's log, not a gate.

When building a new language pack, set $LanguageVersion to match the $RequiredLanguageVersion
of the core it is being built against. Check the current value by running
  php convertCore.php -v
That command also reports how many packs in each GUI currently pass, & names the ones that
do not.

WHEN TO CHANGE A LANGUAGE PACK VERSION.
  Change it when the LOGICAL structure of the pack has changed.
  A new string variable the GUI reads.
  A removed string variable.
  A renamed string variable.
  A change to the plural helpers or to any logic the pack contains.

WHEN NOT TO CHANGE A LANGUAGE PACK VERSION.
  Do not change it for a typo, a grammar correction, or a better word choice.
  No variable name changed & no functionality changed, so the pack still works with the core.
  The commented version stamp at the top of the file SHOULD be updated to record when the
  file was last touched. That stamp is documentation & is per file.
  $LanguageVersion is a compatibility contract & is shared by every pack.

ALL LANGUAGE PACKS MUST BE UPDATED TOGETHER.
  A version bump applies to every pack in every GUI at once. All or nothing.
  Twenty six packs across two GUIs is fifty two files, & every one of them must carry the same
  $LanguageVersion.
  A pack left behind is a pack the core warns about on every request, & a string it lacks is
  shown from the baseline instead of in the user's language.
  This is the single most common mistake when adding a string. Add the string to one pack,
  bump its version, & the other twenty five warn & show it in the baseline's language. Add
  the string to all twenty six & bump none, & nothing tells anybody the packs moved on.
  Add the string everywhere first. Bump the version everywhere last.

--About languageStrings.php--

This file contains the major language-specific text elements & logic.
This file is loaded whenever a GUI is displayed.
This file exists to make the other GUI files more universal.
All translated text or text elements should be placed in this file & called by variable reference.
Using this file to contain localized text elements improves the maintainability of multiple language packs.
This file must declare $LanguageVersion as a string.
The core carries $RequiredLanguageVersion & compares the two after loading.
A mismatch is a warning. The pack is still used, & the baseline loaded underneath it supplies any string it lacks.
The check happens after the file is loaded, because the version is inside it.
This works because a language pack contains only variable assignments.
Simple logic is permitted where localization requires it.
Plural selection is the common case. $FCPlural1 & $FCPlural2 exist for languages that inflect nouns for number.
Languages that do not inflect leave both empty & write the sentence so it reads correctly for any count.
A string the page fills in carries placeholders in braces, such as {fit} & {count}. A translation keeps
every placeholder its English carries, in whatever order the language needs, because each is replaced by
its name. $Gui2Text137, $Gui2Text138 & $Gui2Text139 carry them, from v4.1.4, & $Gui2Text170 &
$Gui2Text179, from v4.1.5. A sentence with a count in it is written so it reads correctly for any count, as
a plural helper would otherwise be needed. {kind} is the name of a kind of file, as $Gui2Text114 through
$Gui2Text127 give it, so a language whose words for all agree with the noun writes the sentence around
it, as all files: {kind}.
Do not repeat a closing HTML tag that footer.php already supplies. $GuiFooterText1 ends without its final closing anchor tag for this reason.
From v4.2.0 a pack carries $GuiAuthText1 through $GuiAuthText43, the words of the sign in bar & the sign in pages,
under Set GUI - Sign In Related Variables. $GuiAuthText30 is followed by a number on the page, so it ends where
a number reads correctly after it, as a colon does in English. Sign in is a verb on a button, & reads as one.

--About flag.png--

Every language pack must contain a flag.png.
The image is 24 pixels wide by 18 pixels tall, which is the 4:3 ratio used by the flag set.
It appears as the face of that language's button in the selector bar.
The endonym from $SupportedLanguages is used as the alt text & title, so the image never
carries meaning on its own.
The stock flags are from https://github.com/lipis/flag-icons by lipis, under the MIT
license. See ICON_CREDITS.txt.
A flag is a country, not a language, & several languages have no country to point at.
Where no honest flag exists, the stock packs use a letterform on a solid ground instead.
aii & arc use the first letter of their endonym in Syriac script. sw uses SW, because
Swahili spans Tanzania & Kenya with no single claim.
A pack missing flag.png will not load.

--About index.html--

This file serves to act as reliable and predictable document root protection for the server.
If users are allowed to view the document root of the server they could navigate manually to other users' hosted scratch space.
This would allow users to see some temporary files of other users while they were in the process of working on them.
This file simply redirects the user to the main HRConvert2 landing page with a message asking them to wait.
The visual effect of the loading text is that a malicious actor knows they have hit some protection mechanism.
If you want to modify the global index.html file, modify the one in the installation location and then copy & paste to all other subdirectories.
HRConvert2 will automatically create new index.html files in folders it creates using the one from the installation location as a template.
This file must be manually copied & pasted into any folders that are manually created by administrators or developers of HRConvert2.
