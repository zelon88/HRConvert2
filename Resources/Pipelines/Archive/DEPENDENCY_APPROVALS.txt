  Audit answers. Every one is a judgement a person records here.
    1a Security design is amenable to ours        No. The quality of the codebase means it can never be used outside of a highly restricted sandbox.
                                                  While security advisories do get patched, the quality of documentation is non-existent.
                                                  No published security policies. Does not accept advisories. Does not participate in disclosures.
    1b Recent CVEs, issues or exploits            CVE-2025-0411 (Mark-of-the-Web Bypass) - Disclosed by ZDI, this vulnerability allowed extracted files
                                                  to bypass Windows web-mark protections.
                                                  CVE-2025-11001 & CVE-2025-11002 (Symbolic Link Traversal): Critical directory traversal bugs allowed
                                                  remote code execution via malicious ZIP files. The vendor patched the logic ("IsSafePath" validation)
                                                  within a standard release cycle.
                                                  CVE-2026-48095 (NTFS Heap Overflow): Disclosed by GitHub Security Lab, this flaw led to potential
                                                  arbitrary code execution via malformed archive files. The fix was rolled into version 26.01 silently
                                                  on the same day the coordinated advisory went public, showing strong reactive coding but zero
                                                  vendor-side marketing or disclosure
    1c Development activity & breakage risk       Stable. Igor Pavlov actively maintains the project with multiple updates per year via SourceForge.
                                                  Breakage risk is low because command-line syntax changes are exceptionally rare.
                                                  However, the legacy Linux port (p7zip) is not as good as 7zz; we must move to the official 7zz binary,
                                                  which tracks the upstream source, or build from source.
    1d What it needs to function                  Self-Contained. The standalone binary is statically linked against most helper components,
                                                  requiring only standard POSIX libraries (glibc, libstdc++, libgcc). It requires standard file system
                                                  read/write access to the specific target directory and temporary directories (/tmp) to store unpackaged
                                                  chunks during multi-part stream extractions.
    1e Can it be sandboxed or isolated            Highly Amenable. Because it is naturally stateless and requires zero network access, it sandboxes well.
                                                  Since HRConvert2 spawns conversions dynamically, the binary can be wrapped easily within existing
                                                  restricted namespace using standard Linux execution boundaries.
    1f Security options & hardened configuration  None. The binary itself does not have security configuration toggles. Hardening must be environmental
    1g Could another dependency do this better    Yes, conditionally. For standard formats like .zip and .tar.gz, native tools are far safer because they
                                                  don't include 7-Zip’s massive parser framework.
                                                  For proprietary .rar or native .7z formats, 7zz remains functionally unrivaled despite its memory risks.
    1h Origin & supply chain risk                 Medium-High Risk. Source code hosting relies entirely on SourceForge and a single developer infrastructure.
                                                  There is no modern corporate signing key infrastructure, no distributed consensus among multiple maintainers,
                                                  and no reproducible build validation tooling provided by the upstream project.
                                                  The codebase is maintained by Igor Pavlov, a private freelance developer believed to reside in Russia.
    1i Dependency traps for existing installs     Legacy Forks in apt repositories. We currently use p7z, but we should switch to 7zz or source build ASAP.
    2a System package versus a source build       Source Build Preferred, package version acceptable when 23.01+ is used.
                                                  Distro-packaged binaries are built for broad compatibility rather than maximum defense.
                                                  Custom source builds allow HRConvert2 to strip unwanted parsers out of the source tree and apply strict
                                                  compiler-level hardening optimizations.
    2b Build flags, libraries & features          Mandatory Fortification Flags. If building from source, you must discard the default makefiles and compile with
                                                  maximum fortification flags to turn potential code execution exploits into safe application crashes:
                                                  -D_FORTIFY_SOURCE=3 -fstack-protector-strong -fPIE -pie -Wl,-z,relro,-z,now
    2c Minimum version & version edge cases       Strictly 23.01+. Do not permit any deployment older than version 23.01, as earlier versions contain unpatched
                                                  vulnerabilities.
    2d Licensing implications of the build        Complex Blended License. 7-Zip uses a mixed LGPL + unRAR restriction model.
                                                  The core code is LGPL, but specific decompression submodules (primarily the RAR decoding engine) contain explicit
                                                  licensing language forbidding the reverse engineering or reuse of the code to create a RAR compressor.
                                                  This is fine for an internal HRConvert2 tool, but carries compliance weight if redistributed commercially.
    3a Distribution method                        Tarball Binaries / Source Archives. Distributed via the official 7-zip.org portal as compressed source tarballs or
                                                  pre-compiled standalone console binaries for Linux architectures (x86_64, ARM, etc.).
    3b Download source used                       Official URL (https://7-zip.org), or SourceForce (downloads.sourceforge.net/sevenzip) as Mirror.
    3c How an installer obtains this version      Package Manager Install.
    3d Inspection of any bundled binary or code   Inspection Impractical. High Obfuscation Risk remains present in Assembly files.
    3e Sanity check of the build system           Required, Included.
    3f Build script provided                      No.

    1a Security design is amenable to ours        Yes. Designed specifically as a minimal, unprivileged attack surface reduction boundary.
                                                  Maintained by Red Hat/GNOME developers with structured disclosure and explicit security modeling.
                                                  Codebase is exceptionally tight, readable, and avoids macro or parsing complexity.
    1b Recent CVEs, issues or exploits            Extremely clean track record. No high-severity RCE or jailbreak flaws in years.
                                                  CVE-2019-12439 was a minor local info leak due to a temporary file descriptor layout bug.
                                                  Most environment breakout vulnerabilities stem from the underlying Linux kernel namespaces rather than bwrap.

                                                  CLI arguments and core runtime flags are frozen and stable; update regressions are virtually non-existent.

                                                  Dynamically links against standard glibc; needs no background daemons or permanent disk writes.

    1f Security options & hardened configuration  Maximal isolation flags must be applied when executing sub-commands: --unshare-all, --uid, --gid,
                                                  --ro-bind for system runtime folders, and explicit --seccomp filters to drop dangerous syscall architectures.
    1g Could another dependency do this better    No. It is the gold standard for rapid, unprivileged, daemonless command sandboxing on Linux.
                                                  Alternative tools like Minijail lack the widespread distro adoption, while Podman/Docker bring major daemon overhead.
    1h Origin & supply chain risk                 Very Low Risk. Maintained by primary enterprise Linux contributors (Fedora, Red Hat, SUSE).
                                                  Distributed with cryptographic tag signatures and heavily scrutinized open-source review pipelines.
    1i Dependency traps for existing installs     The Setuid Trap. If the target host kernel disables unprivileged user namespaces by default,
                                                  bwrap requires a root-owned setuid bit to function, expanding the local attack surface if misconfigured.
    2a System package versus a source build       System Package Preferred. The distribution-provided package is kept patched, stable,
                                                  and correctly mapped to the underlying platform's specific namespace permissions.
    2b Build flags, libraries & features          Standard hardened compile blocks. Ensure libseccomp filtering is explicitly compiled in (--enable-seccomp).
    2c Minimum version & version edge cases       Strictly 0.4.0+ as defined by the manifest, though 0.8.0+ is strongly recommended to support modernized flags.
    2d Licensing implications of the build        LGPL-2.0 is highly amenable. Safe for commercial and internal utility wrapping without copyleft traps.
    3a Distribution method                        Native package repositories (apt) and official GitHub source releases.
    3b Download source used                       Upstream GitHub assets or native distribution mirrors.
    3c How an installer obtains this version      Standard automated package management fetch (apt-get install -y bubblewrap).
    3d Inspection of any bundled binary or code   Inspection Practical. Clean, straightforward, minimal C files without obfuscation or macro masking.
    3e Sanity check of the build system           Fully automated via native continuous integration testing suites embedded in the upstream source.
    3f Build script provided                      No. Managed safely via the native OS package controller.

  Audit answers. Every one is a judgement a person records here.
    1a Security design is amenable to ours        Yes. Info-ZIP tools follow a stable, mature, and well-understood design.
                                                  While the code is written in legacy C and lacks modern memory-safe guardrails,
                                                  the tools have been thoroughly fuzzed and hardened by the open-source community over decades.
    1b Recent CVEs, issues or exploits            Low Risk / Heavily Patched. Historical issues like CVE-2022-0529 and CVE-2022-0530 involved integer
                                                  overflows and heap-based buffer overflows when handling invalid multi-byte characters or malformed entries.
                                                  Modern distro packages include robust patches for these edge cases.
    1c Development activity & breakage risk       Dormant / Very Low Breakage Risk. The upstream Info-ZIP project has been stable and largely quiet for years,
                                                  with active maintainership handled downstream by Linux distributions backporting stability fixes.
                                                  Syntax and behavior are set in stone, meaning update breakage is non-existent.
    1d What it needs to function                  Standard System POSIX access. Requires direct read/write file system rights to targeted input paths
                                                  and output archives. Relies on standard glibc calls and runs completely as a stateless console application.
    1e Can it be sandboxed or isolated            Highly Amenable. Requires zero network operations or inter-process communication (IPC) frameworks.
                                                  It operates perfectly when completely isolated within a restricted Bubblewrap container mapping only
                                                  the explicit extraction directories.
    1f Security options & hardened configuration  Native defensive flags should be strictly enforced via the tool invocation logic inside HRConvert2,
                                                  specifically ensuring that when unzipping, standard input validation matches extraction constraints
                                                  and no absolute paths or parent directories are targets.
    1g Could another dependency do this better    No. Info-ZIP's `zip` and `unzip` are the ubiquitous open-source standard implementations for the ZIP format on Linux.
                                                  While 7-Zip can handle ZIP archives, maintaining native Info-ZIP binaries provides a lighter,
                                                  highly standardized parsing alternative when wrapped by Bubblewrap.
    1h Origin & supply chain risk                 Very Low Risk. Shipped natively by all major Linux distributions (Debian, Red Hat, Ubuntu).
                                                  Source tarballs are maintained inside distro mirrors, cryptographically signed,
                                                  and heavily protected against malicious upstream tampering.
    1i Dependency traps for existing installs     The Symlink Overwrite Trap. Unzipping untrusted archives carries risk if the utility processes malicious
                                                  nested symlinks that attempt to traverse outside the target folder. External isolation via Bubblewrap is mandatory.
    2a System package versus a source build       System Package Preferred. The distribution-provided package is heavily validated, structurally integrated,
                                                  and automatically updated against emerging security bugs by the underlying platform repository maintainers.
    2b Build flags, libraries & features          Default distribution compilation profiles are optimized and fortified. Custom flags are not required
                                                  if system-provided package tracking is maintained.
    2c Minimum version & version edge cases       Strictly 3.0+ as defined by the manifest facts to ensure standard archive boundaries and proper large-file parsing features.
    2d Licensing implications of the build        Info-ZIP License (BSD-style permissive copyright). Highly business-friendly, contains no copyleft restrictions,
                                                  and carries zero compliance risks for bundling or commercial use.

    3c How an installer obtains this version      Automated package fetch and management via the system package utility (apt-get install -y zip unzip).
