--About This File--

CODE & OUTPUT SAY WHAT HAPPENS. THIS FILE SAYS WHY.
Command line output & code comments state facts. The reasoning behind them, & the history
that explains it, is recorded here by subsystem, so neither has to carry it.

  This file                   Why a subsystem is shaped the way it is, & what came before.
  ABOUT_ documents            How a subsystem works now.
  CHANGELOG.txt               What changed in each release.
  ERROR_DESCRIPTIONS.txt      Every numbered error, its cause & its fix.

Each entry opens with the decision in capitals, followed by its reason.
A release number is given where one is known.
v4.0.6 moved the history out of the command line output, & v4.0.8 moved it out of the code comments.

--Command Line Output--

ONE FACT OR ONE INSTRUCTION PER LINE.
A report line is a label, a status word & a detail. A detail states what is true or what to
run. It does not narrate, explain history, or say what an earlier release did.

A STATUS WORD IN UPPER CASE NEEDS ATTENTION. ONE IN LOWER CASE NEEDS NOTHING.
An operator reads the case before the words. A benign state such as carried, unconfined or
unrestricted is shown as ok, because each of those reads like a fault & is not one.
A state that changed the host, such as installed, repaired or kept, keeps its own word.

STATUS WORDS & THE OPENING OF EVERY SUMMARY LINE ARE STABLE.
Tests, documents & the administrators' own scripts match words such as OK, FAILED, KEPT,
NOT ASKED & Corrected 0 path(s). The sentence after a status word may change, & so may the end
of a summary line. The word & the opening may not.

LOG ENTRIES ARE NOT COMMAND LINE OUTPUT.
Root repeats its warnings & errors on a terminal, so they appear among the output. Their text
is the log's & did not change in v4.0.6.

--Listener & Resource Awareness--

ONLY ROOT & THE WEB SERVER ACCOUNT MAY RUN LISTENER COMMANDS.
A standard user holds a per user secret. A per user secret cannot derive a valid startup key,
so a listener a standard user started could never be reached by a worker.

WITHOUT A LISTENER, A CONVERSION RUNS WITHOUT A BUDGET, UNLESS RESOURCE AWARENESS IS REQUIRED.
That is how every conversion ran before resource awareness existed, & a stopped listener must
not stop a site. --Require Resource Awareness-- is for a site that must never accept work it
cannot account for. It halts on a missing Engine or install secret, & from v4.0.7 it refuses a
conversion the listener gives no answer for. Until v4.0.7 that conversion ran, although the
documents said it would not. Without the setting, a listener a flood has slowed still lets
conversions through, which is the price of never stopping a site.

ROOT DOES NOT READ WHAT THE WEB SERVER ACCOUNT WRITES.
The listener's state lives in that account's folder & reading it refuses root. --status run as
root hands the question to that account & relays its answer, which is the truth about a
listener that account runs. -v run as root reports the listener as NOT ASKED for that reason.

WORK STOPS BEFORE THE KERNEL RUNS OUT OF USER NAMESPACES. v4.0.6.
Every sandbox is a user namespace, & the kernel refuses a new one once the web server account
holds user.max_user_namespaces of them. A conversion started then fails inside its sandbox, where
the reason is hard to see. The Resource Manager counts the account's namespaces at each poll,
warns at 10% free & refuses budget requests at 1% free, so a conversion is refused with a reason
instead. The thresholds are fixed rather than configured. Each change of state is logged once,
because a poll comes every few seconds & a state can last for hours.
The count reads /proc. A process of another account cannot be read, & a namespace with no
process of its own is not seen, so the count is a floor. That is the cheap answer, & it is
enough to catch sandboxes that pile up or a limit set too low.

WORK STOPS BEFORE A DISK HOLDING A DATA LOCATION FILLS. v4.1.3.
A full disk stops more than uploads. The logs, the sessions & the operating system all write to
it, & a log that cannot be written cannot say why. The Resource Manager measures every disk
holding a data location at each poll, & refuses uploads & every operation that takes a budget
while one has --Storage Reserve-- or less free. Unlike the namespace thresholds, both storage
thresholds are configured, because what a disk can spare depends on how large it is & on how
large the files converted on it are. The reserve is an amount rather than a share, because a
share large enough to matter on a small disk is wasteful on a large one.
A disk is measured again when a request asks, because uploads can fill a disk faster than the
poll comes round. A request may only name a configured data location, so the web server account
never measures a path a worker chose.
An upload names the bytes it holds, so one that would take a disk into the reserve is refused
before it is written. PHP has already written it to its own temporary folder, & the copy into the
session needs as much again, so the bytes are counted whatever disk that folder is on.

AN ANSWER THAT MEASURED NOTHING IS NO ANSWER. v4.1.3.
A drop in replaces the code & leaves the listener running the release it started with. That
listener's Request Manager refuses the storage request type as one a worker may not issue, & a
refusal read as a verdict would refuse every upload until somebody restarted it. Every answer the
Resource Manager gives a storage request names the disk's state, so an answer that names none
measured nothing, & the Engine treats it as a listener that did not answer.

THE STORAGE MONITOR RUNS ONLY IN THE LISTENER. v4.1.3.
An installation, -fp & --setup measure nothing & refuse nothing. A container image is built on
whatever disk its builder has, & a continuous integration runner's disk is often nearly full by
the time the image is built, so an installer that refused would fail a build for a reason that
has nothing to do with the host the image will run on. The listener only runs once a host is set
up, so the monitor is enabled after setup by construction rather than by a setting.

QUOTAS ARE A HOOK UNTIL THERE ARE USERS. v4.1.3.
A quota needs an owner, & every request is anonymous until the Authentication Manager signs users
in. So every budget & storage request carries an owner from storageQuotaOwner(), which is empty,
& the Resource Manager asks evaluateStorageQuota(), which allows everything, once it has measured
the disk. That manager fills both, & nothing between them changes.

SYSTEMD IS JUDGED RUNNING, NOT INSTALLED.
A container can ship systemctl without systemd running. A unit written there is read by nothing,
& makes the listener defer to a service manager that never answers. Without systemd no unit is
written, & -l starts the listener as a plain process.

--Environment Manager--

THE TIMER IS WRITTEN & NOT ENABLED.
The listener is enabled at installation because nothing works without it. The timer puts a root
process on a schedule. That is a decision for an administrator who has read what one pass
reports, & not one an installer makes on their behalf.

A PASS REPORTS WHAT IT FOUND BEFORE IT REPAIRED ANYTHING.
A finding that a repair then corrected is still worth seeing. Something changed the host.

--Sandbox--

THE HAND WRITTEN BUBBLEWRAP PROFILE IS REPORTED & LEFT ALONE.
Install guides before v3.8.0 asked administrators to write /etc/apparmor.d/bwrap by hand. It
lets any program on the host build a namespace through /usr/bin/bwrap, whatever the kernel
restricts. HRConvert2 does not use it. No package owns it, so nothing says what else relies on
it, & only the administrator can remove it.

THE NAMESPACE RESTRICTION AN EARLIER RELEASE LIFTED IS KEPT LIFTED.
Earlier releases lifted kernel.apparmor_restrict_unprivileged_userns for the whole host, & held
it lifted at every boot with /etc/sysctl.d/99-hrconvert2-userns.conf. From v4.0.5 every sandbox
runs HRConvert2's own copy of bubblewrap, which an AppArmor profile is attached to, & the
restriction is lifted only where that copy cannot carry a sandbox. Other programs on the host
may depend on a lift by now, so one HRConvert2 no longer needs is not undone automatically.
--Allow Unprivileged Namespaces-- set to FALSE makes -fp switch the restriction back on. An
administrator who switches it back on by hand runs -fp afterwards, which removes the drop in
once a sandbox is built through the copy.

A SANDBOX MAY NOT MAKE A USER NAMESPACE. v4.0.7.
A converter a crafted file takes over runs as the web server account inside its sandbox. Until
v4.0.7 it could make user namespaces from there, hold them open with file descriptors, & spend
every one the account may hold, so every other conversion failed at bubblewrap until it was
reaped. The Resource Manager cannot count a namespace held that way, because no process is in it.
Bubblewrap's --disable-userns closes it at the source. It is proved on each host by building a
sandbox with it rather than read from a version, so a host it does not work on keeps working.

ONLY ROOT CAN JUDGE THE SANDBOX FOR EVERY ACCOUNT.
HRConvert2's own bubblewrap may be run by root & the web server account's group & nobody else.
Any other account running -v cannot try it, so its sandbox lines read n/a & say to run -v as
root.

AN APPARMOR PROFILE WRITTEN NOW MAY NOT BE IN FORCE YET.
The kernel honours a new profile once AppArmor reloads it, which can take a reload or a reboot.
-fp says so when the sandbox is still unavailable after writing one.

ONE RULE DECIDES WHETHER A SANDBOX IS REQUIRED. v4.1.7.
sandboxIsRequired() reads --Require Sandbox On Docker-- in a container & --Require Sandbox--
anywhere else, as sandboxCommand() always did. The environment check required both in a
container, so with --Require Sandbox-- FALSE & --Require Sandbox On Docker-- TRUE it said
conversions would run unprotected while sandboxCommand() refused every one. config.php also said
--Require Sandbox-- must be FALSE in a container, where it is not read at all.

--Policies--

FROM v4.0.5 A POLICY TRAVELS WITH ITS PIPELINE.
The ImageMagick policy is carried into each conversion's sandbox, so nothing on the host is
changed for it. Earlier releases wrote it into the host's own configuration. -fp retires every
host policy an earlier release wrote by putting the host's own file back.

A POLICY WRITTEN OVER THE HOST'S FILE WITH NO COPY IS KEPT.
Removing it would leave the converter with no policy at all. It is reported as kept until the
administrator restores the original from the package or the build that provided it.

OPENSCAD NEEDS NO APPARMOR OVERRIDE.
Nothing on the host confines it. The bubblewrap sandbox isolates it.

--Data Directory Protection--

A PROTECTION FILE THAT EXISTS PROVES NOTHING.
DATA/.htaccess is read only where AllowOverride permits it. Where it does not, Apache ignores the
file in silence. -fp therefore asks the tree for a canary over HTTP rather than believing the
file, & a canary it could not fetch is not a pass.

AN UPLOAD SERVED AS A DOCUMENT IS EXPOSURE.
An uploaded SVG served as a document rather than a download runs its own script in this
application's origin.

A SERVER ERROR FROM DATA IS AN OUTAGE, NOT EXPOSURE.
The usual cause is a directive in DATA/.htaccess that the directory's AllowOverride level does
not permit. Apache refuses such a request rather than ignoring the directive, & an <IfModule>
guard does not prevent it. Removing the file restores service at once. The rules belong in the
server configuration.

AN APACHE CONFIGURATION THAT DID NOT PARSE BEFORE HRCONVERT2 WROTE ANYTHING IS LEFT ALONE.
HRConvert2 tests the configuration before & after writing its own file. A fault that was already
there is the administrator's, & HRConvert2's file is kept. A fault HRConvert2 caused is
withdrawn, & what was there before is put back & tested again.

--Uploads--

AN UPLOAD IS CAPPED IN PHP & IN APACHE AT ONE SIZE. v4.0.7.
PHP's drop in accepts 5000M. Apache 2.4.54 & later refuse any request body over 1 GiB by default,
so until v4.0.7 an upload between the two failed at Apache, with nothing in HRConvert2's log.
uploadCeilingMegabytes() is the one number both read.

HOW LONG AN UPLOAD MAY TAKE IS THE ADMINISTRATOR'S CALL.
A slow upload holds an Apache worker for as long as it lasts, & 150 of them hold every worker.
RequestReadTimeout bounds it & applies to every site on the server, so HRConvert2 documents it
rather than writing it. See ABOUT_RESOURCE_RATE_LIMITING.txt.

--Installation & The Hosted Location--

A RELEASE COPIED INTO THE WEB ROOT BRINGS .git & .github WITH IT.
STEP 2 of the installation instructions copied the repository there until v4.0.9. The installation
never uses either folder, & the Apache configuration refuses both. -v reports the hosted location
as KEPT & names them until they are moved out of the web root. A .old folder is an earlier
installation an update left beside it.

THE REPOSITORY IS CLONED WHERE ONLY ROOT CAN CHANGE IT.
Root installs only a tree no other account could change, so a clone in a home folder is refused &
-fp exits with status one. Until v4.0.9 the README & the installation instructions cloned into the
current folder, which was refused wherever that was a home folder.

-fp RUN FROM A TREE NOT YET INSTALLED INSTALLS IT AS IT ENDS.
The tree is installed into the Application folder of the data location, & then the installed
copy's own -fp runs, which publishes the hosted location.

A LISTENER RUNNING DURING AN INSTALLATION KEEPS RUNNING THE RELEASE IT STARTED WITH.
It is reported, & the administrator restarts it.

A DROP-IN HOLDS ONLY THE FILES THAT CHANGED.
Unpacked beside the loader, it finds no Engine, because the Engine lives in the installation.
The remedy is to unpack it into the installation & run -fp there.

A MISMATCHED ENGINE CAN ONLY BE REPLACED BY HAND.
Every repair path reaches into the Engine. --config --repair, --setup --install-complete & -u
were each measured failing on an Engine call of their own, so the output names the file to
replace rather than a command.

--Managed Locations & Trust--

ROOT REFUSES TO RUN CODE ANOTHER ACCOUNT COULD HAVE CHANGED.
Error 28008 refuses every command run as root on such a tree except the ones that give the tree
back to root, which are -fp, --setup & --config --repair.

-fp LEAVES LINKS, HARD LINKS & OTHER FILESYSTEMS AS THEY ARE.
Changing one would reach outside the installation. What -fp names afterwards is for the
administrator to remove or put right.

A LOCATION ANOTHER ACCOUNT COULD REPLACE IS SKIPPED.
Root keeps nothing there & changes nothing there, because the account that can replace the
folder can replace it between root's check & root's write.

--Install Secret--

THE INSTALL SECRET LIVES IN SECRETS, & ONLY THE WEB SERVER ACCOUNT'S GROUP MAY READ IT.
An older layout kept it at the top of the data location. -fp copies it into Secrets with its

--Dependencies--

AN OWN BUILD IS RETIRED ONCE THE PACKAGE MANAGER CATCHES UP.
HRConvert2 builds its own copy of a dependency when the package manager's version is outside
the window the manifest declares. When the package manager's version is inside the window
again, --setup --update-depends takes the own build away.

A LONG BUILD PRINTS A STATUS LINE EVERY MINUTE.
A build from source takes several minutes, & an hour or more on an ARM board. pip downloads
everything before it installs anything, so a slow connection makes it slow. The status line is
how an administrator knows it has not hung.

--setup --uninstall-depends REQUIRES A SUBSYSTEM.
Every dependency together includes PHP, Apache & the package manager. Removing all of them
would leave a host that cannot be recovered remotely.

A DEPENDENCY THAT CANNOT ANSWER IS RECORDED AS UNKNOWN, NOT AS EMPTY.
Unknown leaves its pipeline's declaration standing. Empty would read as a tool that converts
nothing.

AN APACHE CONFIGURATION A PACKAGE INSTALL ENABLED IS TURNED OFF WHEN NOTHING USES IT.
Installing a package can enable configuration HRConvert2 never asked for.

THE SUPPLY CHAIN TEMPLATE'S RIGHT HAND COLUMNS ARE BLANK ON PURPOSE.
They are the audit, & a person fills them in.

EVERY TOOL IDENTIFY RUNS IS AN ENTRY OF ITS OWN, EVEN ONE ANOTHER ENTRY ALREADY INSTALLS.
FFprobe comes from the FFMPEG build & PDFInfo from the package Poppler Utils names. Each has an
entry, so Identify asks for it by name & a host missing one is told which, rather than being
assumed to have it because its sibling is there. v4.1.2 added both, with File. PDFInfo keeps
Poppler Utils' subsystem, so removing Identification never removes a package Documents & OCR need.

FILE'S FLOOR IS 5.43.
Every release before 5.38 overflows the heap reading a CDF document, CVE-2019-18218, & every
release before 5.43 reads past a buffer on the stack copying a string, CVE-2022-48554. Ubuntu
24.04 carries 5.45 & Debian's bookworm 5.44, so the floor costs neither a build of its own.

A BUILD THAT FAILED IS NOT RUN AGAIN IN THE SAME INSTALL. v4.1.7.
The v4.1.3 Docker publish built arm64 under QEMU. x265 did not compile for aarch64, so FFMPEG's
build failed, & FFprobe, which names the same build, ran it again from the start. The image's first
install also ran before Documentation/Build was copied in, so every source build failed there & ran
again in the full install. Builds of FFMPEG under emulation ran past GitHub's six hour limit.
Each architecture now builds on a runner of its own, the build scripts arrive with the manifest, &
a build that failed is not run again for another entry it also makes.

x265 3.5 ON AARCH64. v4.1.7.
Its aarch64 assembly is 8 bit only, so the 10 & 12 bit libraries do not compile with it, & its
HDR10+ library hands -mfpu=neon, -mfloat-abi=hard & -marm to an aarch64 compiler, which refuses all
three. Both were reproduced with an aarch64 cross compiler, & with both corrected the 12 bit, 10 bit
& 8 bit libraries & the library joining them all build. Only Linux on aarch64 is corrected.

PHP PCNTL & POSIX ARE ENTRIES OF THEIR OWN. v4.1.7.
runAsAccount() forks & drops to the web server account, & refuses rather than run a command as root
without both extensions. A distribution's command line PHP has both. The official PHP container
image has posix & not pcntl, & cannot build its zip extension without libzip-dev, so the Dockerfile
installs that one header package before the manifest takes over.

THE IMAGEMAGICK BUILD'S DELEGATE REPORT NEVER FAILS. v4.1.7.
The script runs under set -e & its report returned 1 for a delegate it did not find. AVIF is read &
written by the HEIC coder through libheif, so it is never listed as a delegate, & the script ended
with an error after every good install. AVIF is now looked for among the formats.

THE BUNDLED SCANCORE KEEPS HRCONVERT2'S OWN FILES. v4.1.7.
ScanCore's application update replaces every file its subscriptions name. HRConvert2's copy of
ScanCore_Config.php carries a command line guard upstream's does not, & its index.html is
HRConvert2's page, so neither is subscribed. A ScanCore release that adds a configuration entry is
refused by ScanCore until the entry is merged by hand, which is the signal to merge it. ScanCore
1.8, the release bundled, is the manifest's minimum.

--Pipelines--

A PIPELINE'S ERROR NUMBERS DID NOT CHANGE WHEN ITS CODE LEFT convertCore.php.
Operators had already read them. A number a block no longer raises is retired, not reused, as
13001 through 13005 are.

NO PIPELINE CARRIES ITS OWN VERSION CHECK.
Every pipeline asks verifiedToolPath(), so the manifest alone owns each tool's minimum. Two
checks eventually disagree. Stream once had its own, higher FFMPEG minimum, & the manifest's
6.1 now covers it.

A CONVERTER THAT LEAVES NO FILE AFTER EVERY ATTEMPT SAYS SO.
Until v4.0.6 that was reported as a time out, which no time limit caused, & one more attempt
was made after it. It was also raised after the attempt that used the count up, even one that
worked. An archiver that left nothing was reported twice, under its format's number & the
Archive pipeline's.

sandboxCommand() RETURNS A PAIR.
Until v3.9.9 ClamAV, ScanCore & Stream took the pair as the command, so the shell ran a program
called Array. ClamAV reported every file clean. ScanCore read Array: not found as a detection &
reported every file infected. No stream converted.

A SCANNER CHANGES NOTHING & WRITES NOTHING A USER SEES.
An earlier ScanCore wrote straight into the user facing report, so the scanner decided what a
user saw, & the application could not filter, order or consolidate any of it.

ARCHIVING A SELECTION & SCANNING FOR A USER ARE OPERATION PIPELINES. v4.1.6.
archiveFiles & the user scan helpers were the last operations left in convertCore.php. The
Archiver & Scan pipelines took them, with every error number they raised, & the core keeps a thin
adapter for each, as it does for OCR & Identify. The Scan pipeline is the user's way to reach the
scanners, & names neither tool itself. It asks the ClamAV & ScanCore pipelines through
runVirusScan(), as everything else does. The Archiver shares the Archive pipeline's subsystem &
tools, & the two are different things. The Archive pipeline converts one archive into another,
& the Archiver makes an archive from any file.

AN OPERATION PIPELINE OFFERS ONLY WHAT IT DECLARES IT WRITES.
The core offered every format config.php allows for archiving a selection, the bootable disk
images among them, & each of those failed with 4004, because only the Archive pipeline makes a
bootable image, from an archive that already holds a bootloader. The Archiver declares what it
writes, the core offers what both it & config.php name, & a format sent anyway is refused by 4006
before any file is touched.

AN INFECTED FILE IS REFUSED BY A PIPELINE, NOT DELETED.
Whether an infected file is deleted is the application's policy, set by --User Virus Scanning--,
which a pipeline cannot read. The core deletes one when it lands. The Archiver refuses one with
4003 & leaves it where it is.

CLAMAV'S LIMITS ARE SIZED TO THE FILE, & IT UNPACKS TO DISK.
Until v3.9.9 an upload over ClamAV's 100M default was reported clean without being read.
ClamAV unpacked into the sandbox's /tmp, which is memory, so a large archive was killed by the
Scan ceiling. Its writable mount was the session's temporary location, which the web server
serves.

SCANCORE'S CHUNK IS A QUARTER OF ITS MEMORY LIMIT.
Until v3.9.9 the configuration shipped a 256M limit with a 128M chunk, & every file over 128M
ended in a PHP fatal error rather than a verdict. The sandbox was not handed ScanCore's own
directory, so php inside it said Could not open input file. Any line containing found counted as
a detection.

THE IMAGE & OCR PIPELINES CARRY THEIR OWN IMAGEMAGICK POLICY.
Until v4.0.5 -fp rewrote the host's policy.xml, for every program on the host. The OCR page split,
whose sandbox shows no ImageMagick configuration, ran under no policy at all.

AN ICON IS SHRUNK TO 256 PIXELS A SIDE.
ImageMagick refuses a larger icon & leaves an empty file. Until v4.0.6 a screenshot converted to
an empty icon.

THE VIDEO CODEC FOLLOWS THE CONTAINER.
An earlier version asked for libx264 whatever the target was. WebM & Ogg reject H.264, so neither
could ever have converted. FFMPEG's standard error was not captured either, so a failed conversion
produced a time out & no explanation.

DIA & THE SUBTITLE CONVERTER ARE VERSION GATED.
Each once invoked its tool blind, & a missing binary produced a time out rather than naming the
cause.

CALIBRE WRITES PML ONLY ZIPPED.
Until v4.0.6 pml & oeb were offered as Ebook outputs, & every conversion to either failed.

THE MODEL PIPELINE NAMES THE FORMAT IT ASKS ASSIMP FOR.
A guessed format failed an obj to off conversion with a message naming neither. Asking for json
produced no output format specified and I failed to guess it, & the retry loop ran the same
impossible command four more times. obj wrote a material library as a second file, which the
session counted & never showed.
The route was once chosen by what a utility could read, so obj to off went to Assimp, which has no
OFF exporter.
3mf, x, ctm, dxf & wrl became outputs at v3.9.0. u3d was left out.
The binary check once tested the $UsePyMeshLab setting rather than whether PyMeshLab loaded, so
buildMeshLabCommand() assembled xvfb-run with an empty program path. The route log tested the
setting too, so a failed import left no record of which utility did the work. A host without a
matching interpreter once failed the whole conversion, though meshlabserver worked on it.

A PyMeshLab IMPORT IS PROVEN, NOT ASSUMED FROM ITS INTERPRETER.
An earlier version stopped at finding an interpreter. It found python3.14, reported PyMeshLab in
use, built a command that raised ImportError, & left nothing to fall back to. Installing the
interpreter to clear a warning broke the conversion path that had worked. A directory that could
not be imported was once reported as success, & a bundle directory that did not exist was still
put on the Python path.

meshlabserver RUNS UNDER xvfb-run INSIDE ITS SANDBOX.
It only ever worked unsandboxed, where /tmp/.X11-unix is the host's & root's. It failed from the
day its profile began sandboxing, & nobody saw it, because the normalize route fell through to
Assimp, so every model conversion skipped normalization. A fallback that works too well turns a
hard failure into a silent regression.
xvfb-run discards the X server's output by default, so several rounds of diagnosis read Qt's guess
at a cause. A server that could not bind TCP in the sandbox made xvfb-run retry the next display,
so a failure named display 109 rather than 99.
MeshLab removed meshlabserver from its releases in 2022, so PyMeshLab is the only route on a
current distribution.

SANITIZATION IS NOT THE SCAD BOUNDARY. THE SANDBOX IS.
Four bypasses were reported against the line oriented SCAD scanner, & a fifth against the stateful
rewrite that replaced it. One applied the main loop's comment rule in the lookahead, which missed
surface/**/("file"). Another defeated rectifySCAD() while it commented out the whole line a call
started on, because a block comment closing part way along that line swallowed the marker. It has
edited by position since.
Until v4.0.5 convertSCAD() ran the system's bubblewrap, relying on a profile an earlier release
attached to it or on the restriction being lifted. Its render once ran under a fixed nice -n 19
rather than its resource ceiling, which walked around the limiter as well as the sandbox builder.

THE STREAM COMMAND IS SANDBOXED.
An earlier version did not sandbox it, believing a backgrounded sandbox would hand back bwrap's
process ID rather than FFMPEG's. bwrap is PID 1 in its namespace & lives exactly as long as its
child, so its ID is the right handle.
An identical log block once sat above the walk loop as well, so every refused walk logged ALLOWED
with zeroes, then DENIED with the real numbers.

NETWORK EGRESS & SSRF JUDGEMENT STAY OUT OF EVERY PIPELINE, WHATEVER THE CALLER COUNT.
When the pipelines left convertCore.php, a helper with no other caller moved with its pipeline.
The eight stream network helpers had no other caller & stayed, so a pipeline that fetches something
gets the protection & cannot opt out of it by accident. They were renamed off the word Stream.

LIBREOFFICE RUNS ONCE PER CONVERSION, INSIDE A SANDBOX.
Documents were once converted through a persistent unoconv listener, which parsed hostile documents
in a long lived process with full network access, so sandboxing the client protected nothing.
Until v4.0.0 an unsandboxed conversion used a profile path shared by every conversion & by any
account that made it first. Until v4.0.6 a LibreOffice its ceiling killed reached the log only as
a time out, once every retry had been killed the same way. Its log line once compared two commands
to say whether a conversion was sandboxed, & said YES for every unsandboxed one.

A PDF IS OPENED IN WRITER ONLY FOR A WORD PROCESSING TARGET.
LibreOffice opens a PDF in Draw, which has no export filter for a word processing format, so until
v4.0.9 a PDF to doc, docx, odt, ott, fodt, rtf or xml failed. Writer's PDF import keeps the text for
those. On LibreOffice 24.2 it leaves plain text & EPUB empty & HTML as pictures, so those stay with
Draw. Draw writes HTML with its text, & has no filter for plain text or EPUB, so a PDF to either
fails. The v4.0.9 test of plain text passed only because LibreOffice's rename found the text file
the PDF was made from & renamed that into place.

became the web server account's home. The install secret moved into Secrets at v4.0.4.

A PATH NO RELEASE SHIPS IS TAKEN AWAY.
FFmpeg's build left its whole tree in Documentation/Build/ffmpeg-build until v4.0.6, links & files
with more than one name included, because the build command changed into Documentation/Build first.
Root refuses an installation holding a link from v4.0.1 on, & -fp could not take that tree away, so
the installation stayed one root refused, which is why the v4.0.5 image never answered.

THE MANIFEST DECIDES HOW EVERY DEPENDENCY IS INSTALLED.
Until v3.8.9 a source Type was declared in depends.php & refused by Dependency Core, so anything
outside a package repository had to be installed by a hand written script kept in step with the
manifest by hand. The FFMPEG build script was called by hand from the Dockerfile until v3.8.9, so
the manifest did not know this dependency was built & the audit did not record it. PyMeshLab was a
bundled x86_64 binary until v3.9.2, when it became a pip wheel, & the architecture limit its entry
carried went with it. Until v4.0.6 a request found no MeshLab while -v run from a desktop found it,
because meshlabserver aborts without a display, & every Model request warned. An earlier release
routed Model conversions on the input extension alone, sent an obj to off conversion to Assimp, &
retried a command that could never succeed until it timed out.

--Interfaces--

AN INTERFACE READS WHAT THE CORE HANDS IT.
The file list button once assembled its own query string out of $_GET, & one test asked whether a
language was set & then printed the gui parameter. A user who chose a language but not an interface
got an Undefined array key warning printed into the page & an empty gui parameter, & watched their
interface change to the default.

EVERY BUTTON DECLARES ITS TYPE.
The settings toggle once opened a PHP tag inside its own style attribute that assigned
$oppositeAlignment & echoed nothing, leaving a text-align with no value, so a browser discarded the
whole declaration & the display:block after it, & the automatic margins beside the button never
centred anything. The session buttons in convertGui2.php carried no type until they were inside a
form.

A REFUSED UPLOAD IS MARKED AS ONE. v4.1.3.
A core error arrives with an HTTP 200 & a reply, & Dropzone marks every upload with an HTTP 200
finished unless it is told otherwise. Until v4.1.3 nothing told it, so an upload the core refused,
for a format it does not accept as much as for a full disk, looked uploaded & was simply missing
from the list. The script library tests the reply as every other control does.

A BULK CONTROL READ THE FILE LIST WHEN IT WAS PRESSED.
The file list publishes the session's files every time it is drawn, & Archive All & Scan All read
them when pressed. Until v4.1.0 both were handed the files the page held when it was first drawn,
so a file converted afterwards was left out & a deleted one was asked for, & neither refreshed the
list when it finished. Start Over still reads them.

BULK FILE OPTIONS WAS RETIRED. v4.1.6.
Scan All, Identify All & Archive All did what a workflow does, in a second panel with its own
controls & its own dividers. The library ships a workflow for each, beginning with a Select step so
it needs no ticked file, & a user changes one in the builder where the panel offered fixed choices.
Nine strings went from every language pack with it.

EVERY COLOUR IS A SCHEME'S, NAMED ONCE. v4.1.6.
The Workflows panel drew its accent, its washes & its edges in one fixed blue & a few greys in every
scheme, & the file's own panels in a fixed pale blue, which put pale text on a pale panel in the
dark scheme. Each scheme in styleCore.php now names eight colours as custom properties, each a
colour it already had, & HRConvert2.css draws from them & names none of its own.

A PANEL STAYS & A CARD COMES & GOES.
The boxes of a workflow's steps & the boxes that never move looked alike. Every box is one of two
kinds now. A panel is framed in the scheme & casts a deep shadow, & a card has a light edge & a
light shadow, so what can be rearranged reads differently from what cannot. A menu a button opens
is a panel, & no menu has a divider before or after it, because a frame already says where it ends.

THE BOX THAT RUNS A WORKFLOW IS SIZED BY ITS ROW, NEVER BY ITS WORDS.
It grows a third as fast as a card, so it keeps to its buttons beside them & fills a row of its
own. It names its buttons once it is wide enough, measured as a container, & a box sized by its
words would move onto another row the moment it named them, then lose the room to name them.

THE ORDER OF THE FILE LIST IS TWO DIGITS IN THE ADDRESS.
There are no cookies & no storage, so the order has to travel with the page. Four fields & two
directions fit in two digits, which say nothing about the session, need no encoding & are checked
by a pattern before they are used. The core sorts, because it already reads the folder & the
Files pipeline already stats it, & the interface would otherwise need every size & time sent to
it to sort them itself. Every link & form carries the order, or a refresh would quietly undo it.

IDENTIFY ANSWERS IN JSON, NOT IN LINES.
A conversion answers with filenames because the interface downloads them. Identify's answer is
read into a panel field by field, & a list of lines would need a parser of its own in every
interface. It is one line, so the interface finds it among any warnings PHP printed. The
exclamation mark is escaped too, because a PDF's title is text its author chose, & an interface
reads three of them after ERROR as a failure.

OPENING A FILE'S PANEL IDENTIFIES IT.
A panel full of blanks waiting for a second press is a step that teaches nothing. A file is
identified once for each page, when its panel is first opened, & what was read is held by name, so
a list drawn again after a conversion fills its panels in again without asking.

A VALUE IN A LANGUAGE READ FROM RIGHT TO LEFT IS ISOLATED.
A size, a time & a hash read left to right in every language. Without isolation, an Arabic page
moved the number of 3.8 KB to the far end of the line & turned a date & its time around.

A STEP'S OPTIONS OPEN IN ITS OWN BOX. v4.1.5.
The box grows across the row, so a step's options sit where the step is. Each change is kept as it
is made, & the box is drawn again only once it closes, so typing is never interrupted.
Until v4.1.6 the back arrow sat in the corner a line starts from, on a line of its own, which
pushed the step's number onto the line below its name, & put the arrow across the box from the
options button that opened it. It takes the options button's place now.

THE ADD MENU IS PLACED BY THE LIBRARY.
The box that runs a workflow is at the end of the row, or alone at the start of the next one on a
narrow screen, so a menu anchored to one side of it left the screen on the other. The library
opens it under the button & moves it back onto the screen. Until v4.1.6 it opened from the side a
line starts on, which is away from the boxes it adds to, & hung past the edge of the panel.

A PATTERN'S TEST IS LINEAR.
The builder marks an extensions box whose text cannot be a list of extensions. Its test requires
a separator between two extensions, because a test that lets a run of letters be split into
extensions every way it can takes exponential time on a long word that fails.

--Workflows--

A WORKFLOW RUNS IN A WORKER, & A PAGE READS A STATUS FILE. v4.1.4.
A web request is bounded by the time PHP & the web server give it, & a workflow of several
conversions outlasts that. So the request that starts one hands it to a worker, the
application's own entry point in a process of its own, & returns. The worker writes a status
file in the session, & the page reads it until the workflow ends. Each operation still takes its
budget from the Resource Manager as a button does, so resource management did not change at all.

AN ENDED STATUS IS READ ONCE, & THEN IT IS GONE.
Every way a workflow can end leaves a status, & every one of them is cleared. The request that
reports an ended status removes it with the job & any stop marker, a run started in the session
clears an ended one, & the sweep removes the session. A worker writes its last status only where
one is still there, so a status that was cleared is never written back.

THE ENGINE NAMES NO OPERATION.
The Workflow Core belongs to the Engine so that any application built on it can run workflows, so
everything it knows about operations it is told, by the application's operation provider. An
operation the application switches off is still a valid step, because a workflow should not
become invalid while an administrator turns a feature off & on again.

A WORKFLOW RUNS A BUTTON'S CODE.
Each operation is an adapter both the buttons & the workflows call, so the two cannot disagree
about what Convert does. convertFiles & archiveFiles stopped printing for this, because a step
passes what it made to the next one, & the core prints for a button.

THE WORKER NEVER RUNS AS ROOT, & NOTHING IT IS GIVEN IS ON A COMMAND LINE.
A command line can be read by every account on the host, & a session's name is how its files
are fetched from DATA, so it travels in the worker's environment with a startup key bound to
the job & the session. The key is spent when it is checked, so a job starts once. The worker is
started without a shell, through setsid, so it outlives the request & leads a session of its own.

A WORKFLOW IS READ ONLY FROM A FOLDER ROOT HOLDS.
The web server account runs every workflow it reads, so it must not be able to write one. The
installed library has the library role, which is the code role's owners & modes, & --workflow
--install writes the text it checked, so a file changed after the check is never installed.

A SESSION'S OWN WORKFLOW IS ASKED ABOUT BEFORE THE SERVER'S COUNT.
The count includes the session's own workflow, so asking the server first told a user whose own
workflow was running that the server was busy. Busy is asked first, & the claim, which creates the
status file only where none exists, still refuses a second run asked for at the same moment.

A KILLED WORKER IS GONE, EVEN BEFORE ANYTHING COLLECTS IT.
A worker's parent exits as soon as it is started, so whatever adopts the worker collects it when it
ends. Until then it is a zombie, & /proc still lists it. The Workflow Core asks the Engine's test,
which reads a zombie as ended, as the listener does for its managers, so a killed worker's workflow
reads as interrupted & its place on the server is given back.

AN UNKNOWN KEY IS A PROBLEM, & EVERY PROBLEM IS NAMED AT ONCE.
A misspelt key would otherwise be a setting silently ignored, & the workflow would do something
other than what its author wrote. One reading names everything to fix.

THE PANEL IS A LIBRARY OF ITS OWN.
The Workflow Core may run where the interfaces are not installed, & an interface may be installed
where the core is not. HRC2-Workflows.js needs no other library & speaks only the API, & says
workflows are unavailable whenever it cannot read an answer. It never says why, because a reason
from the server is the administrator's business & not a visitor's.

TICKED FILES ARE KEPT BY NAME, IN THE ORDER THEY WERE TICKED.
The list is drawn again after every operation & a file's row number changes with it, & a workflow
takes its files in the order a user chose them. Nothing is stored, because there are no cookies &
no storage, so the selection lasts as long as the page.

A TICKED FILE CONVERTS EVERY ELIGIBLE TICKED FILE, ONE REQUEST AT A TIME.
One request for many files would take one budget for all of them & run as long as all of them.
One at a time, each takes its own budget, can fail on its own & keeps its own name. A file is
eligible when its own row offers the same control, because the core drew that control by the
same test, so the page cannot offer a conversion the core would refuse.

THE MENU REPLACES THE SELECTION.
Choosing a kind from the arrow beside the top box ticks exactly the files of that kind, as such a
menu does everywhere else, so what is ticked is never a surprise.

EVERY ELEMENT A PAGE OPENS IS CLOSED. v4.1.4.
Each row of the file list was left open, so every row held every row after it, & the card the
file list page opens was left for the footer to close, which it never did. Browsers forgave both,
which is why neither was noticed. The upload page also wrote an ampersand bare in an address, &
the orange, purple & dark schemes named select arrows neither interface shipped, so every
visible select in them asked for a file that answered 404.

THE BUILDER SENDS A WORKFLOW, & THE SERVER DECIDES. v4.1.5.
A workflow a page built is sent as the text of the format, & the Workflow Core reads it through
the check a library's file passes & starts it through the launch a library's workflow takes. So
the builder holds no rules of its own, & a workflow sent by hand is held to exactly what one built
in the page is. The job keeps the workflow as the runner reads it, & nothing as the page sent it.

A LIBRARY'S WORKFLOW LEFT AS IT WAS RUNS BY ITS IDENTIFIER.
So the workflow an administrator installed is the one that runs, & the status names it. Anything
changed, imported or built is sent whole & has no identifier.

SELECT READS THE SESSION THROUGH THE APPLICATION'S OWN LISTER.
A step that read the folder itself would see what the application never shows a user, such as a
file of a dangerous extension. The provider names the function its pages list files with, so
Select finds exactly what a user could see & tick. Select is the Workflow Core's own, because a
step that runs nothing & takes no budget needs no adapter, & an application has it by naming its
lister. Rescan, as v4.1.4 planned it, is this.

A SELECT STEP IS ASKED ABOUT BEFORE THE WORKFLOW STARTS.
A run is refused when no step would find a file, so a Select step is resolved against the
session as the ticked files are, & a workflow holding one needs none ticked. One that would find
more than a step may take is refused before anything starts, rather than failing when it gets
there with every step before it spent.

THE CANONICAL FORM IS THE ONE THE SERVER WRITES.
An export & the builder both read a workflow as the Workflow Core writes it, so the page reads one
form only, & a workflow exported, imported & exported again is the same text. Mode & every option
are written, because the defaults belong to the application & another server's could differ, & a
reference is written as step N, so a reader need not count steps to follow one.

A CHECK, A RUN & A LIBRARY'S FILE ARE ONE READING.
checkWorkflowText() parses, validates & asks whether each operation is on, & a library, the
command line, an import & a built workflow's run all call it. --workflow --check names a valid
workflow's turned off operations as a result, & --workflow --list names them for one that is
disabled, where both said less before.

A PATTERN A USER TYPES IS BOUNDED BY PCRE & BY THE RUNTIME.
A built workflow puts a user's regular expression in front of preg_match. PCRE stops a match at
pcre.backtrack_limit, which ends a catastrophic pattern against a file's name within milliseconds
& reads as no match, & a workflow is bounded by --Maximum Workflow Runtime-- besides. fnmatch
stayed linear for every wildcard pattern tried against long names.

NOTHING THE BUILDER HOLDS IS STORED.
There are no cookies & no storage, so a page loaded again starts with an empty builder, & a
workflow worth keeping is exported.

A RUNNING WORKFLOW IS DRAWN FROM ITS STATUS. v4.1.6.
A page loaded again while a workflow ran reset the panel, & followed the run only in its status
lines. The status now holds the workflow in canonical form, written once when it is launched, &
reports it while it runs, so the page opens it in the builder, locked, & a library's workflow is
shown as chosen. It is the status & not the job that holds it, because the status is already what
a page reads, & the job holds every file the user selected.

--Updates--

A DROP IN IS UNPACKED WITH --touch. v4.1.3.
tar gives each file the time recorded in the archive, & every drop in recorded the day it was built.
PHP's opcode cache decides whether a file changed by its modification time alone, so the v4.1.3
drop in, unpacked over v4.1.2's on the day both were built, left Apache running v4.1.2's core &
Engine from the cache. That core read the Engine's version from the file on disk, refused v4.1.3,
& every web request failed with error 28005 until Apache restarted, while the command line, which
has no opcode cache, reported nothing wrong. --touch gives every file the time it is unpacked.

EDGE IS NOT A RELEASE.
-u=edge installs the master branch as it stands. It carries whatever version master holds,
which may match no release at all.
