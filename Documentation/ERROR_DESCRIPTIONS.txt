This plain text file contains descriptions of all the native error messages contained in or produced by the HRConvert2 Diablo engine. 
These descriptions should give administrators a starting point for debugging problems with HRConvert2 installations. 
Each section in this file contains information about a different error message. The first one is an example to demonstrate the structure of this file.
Details about each section are below.

HARDWARE REQUIREMENTS ... 
This application requires at least a Raspberry Pi Model B+ or greater. 
This application will run on just about any x86 or x64 computer.

DEPENDENCY REQUIREMENTS ... 
This application requires Debian Linux, Apache 2.4, PHP 8+, FFMPEG, Dia, LibreOffice, 
Mkisofs, 7zip, Unoconv, libgxps-utils, Tesseract, Unzip, OpenSCAD, Rar, Inkscape, Calibre,
Unrar, ClamAV, MeshLab, PopplerUtils, PDFTOTEXT, ImageMagick, Assimp, Bwrap, Dia & xvfb-run.
ADDITIONAL INFORMATION
HRConvert2 logs information about it's operational activity to the Logs subdirectory where HRConvert2 is installed by default.
The default logging directory can be adjusted by modifying the --Log Storage Directory-- section of the config.php file. 
Log entries that represent normal, expected behavior begin with 'OP-Act:' to signify "Operational Activity".
Log entries that represent abnormal behavior begin with 'ERROR'.
If a log file does not exist; HRConvert2 will attempt to create one. 
If an attempt to create a log file or write log entries fails for any reason; HRConvert2 will output errors directly to the page instead. 
If a log file exists, was created on the current date, and is smaller than the "Maximum Log File Size" in config.php; HRConvert2 will append log entries to it. 
Once the "Maximum Log File Size" specified in config.php has been reached; HRConvert2 will create a new log file with a numerically incremented file name.
Actual maximum log file size will vary slightly from the "Maximum Log File Size" because it must be exceeded before HRConvert2 will replace it. 
Typically the "Maximum Log File Size" is only exceeded by a small number of bytes.
Time will be ommitted from logs in situations where time has not been initialized yet.
The application name will be replaced with 'HRConvert2' from errors in situations where the config.php file has not been initialized yet. 
The log number will be replaced with '###' in the event that the error number supplied by the calling code was invalid.
If "Enhanced Logging Verbosity" is enabled in config.php; all significant core operations will produce a log entry.
If "Enhanced Logging Verbosity" is disabled in config.php; only warnings and errors during core operations will produce a log entry.
As of v3.8.5 every conversion pipeline is a detachable component beneath /Resources/Pipelines/ rather than code inside convertCore.php.
No error number changed value when those pipelines moved. Only the FILE section of each affected entry was updated to name its new location.
An operator who read a number in an older release reads exactly the same number today.
Every FILE section below was derived by scanning the code for the call that raises each number rather than by assuming which pipeline owns a block.
A number raised from more than one file names every file that raises it.
The 2000 block is raised by /Resources/Pipelines/Shared/libreOffice.php, which serves the Document pipeline and the OCR pipeline alike.
An operator seeing one of those numbers may have been running either one. The log line above it names which.
The Pipeline Manager component reserves 34000 through 34019.
The 32000 and 33000 blocks were already taken by Setup Core and Dependency Core.

ERROR MESSAGE
  The exact error response produced by the application.
  Text wrapped in angle brackets < > denote encoded information.
  <TIMESTAMP> will be replaced with an abbreviated date.
  <SESSION_IDENTIFIER> will be replaced with a short but unique number to identify related log events.
  <APPLICATION_NAME> will be replaced with whatever the --Application Name-- is set to in config.php.
  <FILE_PATH> will be replaced with an absolute file path.
  <FILE_NAME> will be replaced with a file name.
  <ADDITIONAL_DATA> will be replaced with the result of a system call or standard output from a called dependency.
  <FILE_TYPE> will be replaced with a human readable one word string describing the file such as 'Video' or 'Document'.
  <FILE_EXTENSION> will be replaced with a file extension.

FILE
  The file path pointing to the file which contains this error message. 
  File is relative to the root HRConvert2 installation directory. 
  <SELECTED_LANGUAGE> will be replaced with the ISO 639-1 code that represents the language that was used during the event.
  <SELECTED_GUI> will be replaced with a text string that represents the GUI that was used during the event.
  <SELECTED_COLOR> will be replaced with a text string that represents the color that was used during the event.

FATAL
  Whether or not the occurance of this error will halt execution of the application.
  Will either be YES or NO.

LOGGED
  Whether or not the occurance of this error will be written to a log file in the --Log Storage Directory--  section of the config.php file.
  Will either be YES or NO.

ERROR DESCRIPTION
  A brief and concise description of the error message as well as possible causes & solutions.

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-17, <SESSION_IDENTIFIER>: Could not display the GUI!

FILE
  /convertCore.php

FATAL
  YES

LOGGED
  YES

ERROR DESCRIPTION
  The GUI was assembled but did not complete.
  This error has two distinct causes & the WARNING entries above it identify which.
  FIRST CAUSE. No language pack met the version the core requires.
  The version check is an EXACT match, not a minimum, because a pack newer or older than
  the core expects may be missing strings the interface reads.
  buildGUI() loads the default pack over a mismatched one, so this fires only when the
  default pack is ALSO the wrong version. That means every pack in the installation is stale.
  An update did not complete successfully, or a language pack was installed by hand.
  SECOND CAUSE. One of the four interface files did not set its display flag.
  header.php, convertGui1.php or convertGui2.php, & footer.php must each report success.
  A file that is present but did not execute to completion produces this.
  The www-data:www-data user:group needs read access to the UI subdirectory.
  This may be the result of incorrect file permission levels on the UI subdirectory.

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-502, <SESSION_IDENTIFIER>: ClamAV is missing, too old, or unusable, so <FILE_PATH> was NOT scanned!

FILE
  /convertCore.php

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION
  clamscan could not be located on the server.
  clamscan was located but reported a version older than --Minimum Clam Version-- in config.php.
  clamscan was located but did not report a version that could be read at all.
  The file named was NOT scanned. No clean result is implied by this error & none should be inferred.
  The scan reports failure rather than a clean result, because an absent scanner produces the
  same silence a clean scan produces & the two must never be confused.
  The caller answers this with a fatal 'Could not perform a virus scan!' error, so a server with
  --Virus Scanning-- enabled & no usable scanner refuses to process files rather than processing
  them unscanned.
  Install ClamAV, or disable --Virus Scanning-- in config.php if scanning is not wanted.

  The DATA exposure check fetched its canary & the web server answered with a 5xx.
  THIS IS AN OUTAGE, NOT AN EXPOSURE. Every download & every share link is failing while
  this is true, because nothing in that tree is being served at all.
  The usual cause is a directive in DATA/.htaccess that the AllowOverride level configured
  for that directory does not permit. Apache REFUSES such a request rather than ignoring the
  directive, & an <IfModule> guard does not prevent it, because <IfModule> tests whether a
  module is loaded rather than whether a directive is allowed.
  Only Header & RemoveHandler are legal under AllowOverride FileInfo. Options & php_flag
  require AllowOverride Options & return this error wherever that is not granted, which is
  why the file this application writes contains neither.
  The web server error log names the offending line. Deleting DATA/.htaccess restores service
  immediately. Apply the rules in the server configuration instead, where no override level
  applies. See Documentation/ABOUT_DATA_DIRECTORY_PROTECTION.txt.
  A hand edited DATA/.htaccess is the other common cause.

FILE
  /Resources/Pipelines/Image/pipelineCore.php

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION
  An image conversion was refused because the server could not build a sandbox for it.
  ImageMagick parses untrusted image files & has a long history of memory corruption bugs.
  The delegate system invokes other programs by design, which is what ImageTragick abused.
  policy.xml restricts that natively, but a policy file is a blocklist & has been bypassed.
  HRConvert2 therefore runs the conversion inside a bubblewrap namespace that can see only
  the two directories the conversion needs, & refuses rather than running without one.
  Bubblewrap requires unprivileged user namespaces, which several situations prevent.
  The bubblewrap package may not be installed.
  Debian 12 & Ubuntu 24.04 set kernel.apparmor_restrict_unprivileged_userns to 1, which
  blocks bubblewrap until an AppArmor profile is installed for it.
  A container blocks the required syscalls unless it was started with the correct options.
  See --Require Sandbox-- & --Require Sandbox On Docker-- in config.php.
  Run  php convertCore.php -v  to confirm whether this server has a working sandbox.
  See INSTALLATION_INSTRUCTIONS.txt for the AppArmor profile this requires.

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-9004, <SESSION_IDENTIFIER>: Neither Assimp nor MeshLab can write the <FILE_TYPE> format!

FILE
  /Resources/Pipelines/Model/pipelineCore.php

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION
  A model conversion was requested into a format that no installed utility can produce.
  The two utilities cover different sets & neither covers the whole of --Supported Model Formats-- in config.php on its own.
  Assimp writes obj, stl, ply, 3ds, dae, x3d, fbx, gltf, glb and 3mf.
  MeshLab writes ply, stl, obj, off, dae, x3d, dxf, wrl, ctm and u3d.
  A format in neither list cannot be produced, however the conversion is routed.
  This is reported before the retry loop is entered, because retrying a command that cannot succeed only delays the same failure.
  READING A FORMAT IS NOT THE SAME AS WRITING IT.
  Assimp reads OFF perfectly well and has no OFF exporter at all.
  An earlier version routed on the input extension alone, so an obj to off conversion reached Assimp, which answered that it could not guess the output format, and the retry loop repeated the identical command until it timed out with error 9000.
  Remove the format from --Supported Model Formats-- in config.php, or install a utility that can write it.

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-27007, <SESSION_IDENTIFIER>: Bubblewrap is missing or non functional, so OpenSCAD renders cannot be isolated!

FILE
  /Resources/Pipelines/Scad/pipelineCore.php

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION
  HRConvert2 could not create the sandbox that every OpenSCAD render is required to run inside.
  OpenSCAD reads any file the web server user can read & provides no sandbox of its own.
  It also cannot be given one through its arguments, the way FFMPEG accepts a protocol whitelist.
  HRConvert2 previously filtered the source instead & that approach was reported as bypassable.
  A filter that inspects one line at a time cannot agree with a parser that carries state across lines.
  A block comment closed part way through a line is inert to the filter & live code to OpenSCAD.
  A statement whose name & opening bracket sit on different lines matches no filter pattern at all.
  Both were confirmed working bypasses, so filtering is no longer treated as a boundary.
  Scad conversions are now refused outright when the sandbox cannot be created.
  There is deliberately no fallback to filtering alone, because filtering alone does not hold.
  Install bubblewrap on the server with 'apt install bubblewrap' to resolve this error.
  Bubblewrap may also be installed but non functional on this system.
  Unprivileged user namespaces can be disabled at the kernel level on some hardened systems.
  Check the setting by running 'sysctl kernel.unprivileged_userns_clone' on the server.
  Some container runtimes also block the namespaces bubblewrap requires.
  Running HRConvert2 inside Docker may require adding the SYS_ADMIN capability, or a seccomp profile that permits unshare.
  Verify the sandbox works by running the following as the web server user, which must exit silently.
  bwrap --unshare-all --ro-bind /usr /usr --proc /proc --dev /dev --tmpfs /tmp /usr/bin/true
  Set the Allowed Conversion Types configuration entry to exclude Scad if this server cannot support the sandbox.

  A large real world assembly of roughly thirty sources renders well within the default.
  OpenSCAD builds newer than the pinned minimum render considerably faster because they use multiple CPU cores.

  YES

  NO

ERROR DESCRIPTION
  The config.php file does not define every setting this version of the core requires.
  This almost always means convertCore.php was updated but config.php was not.
  Replacing config.php with the one supplied alongside the new core is the correct fix.
  Settings that were customized must be carried across to the new file by hand.
  A missing setting is not a harmless omission that the core can work around.

  This error can also appear when a setting was added to config.php & to the required list, but not to
  the global declaration at the top of verifyInstallation(). A setting absent from that declaration
  never reaches global scope & is therefore reported as missing even though config.php defines it.
  Because this error takes place before the logging environment is initialized; this error will not be logged.
  Because this error takes place before the time environment is initialized; this error will not contain a timestamp.
  Because this error takes place before the configuration file has been validated; the Application Name configuration entry will not be used.

  The update target supplied is neither a recognized keyword nor a valid version number.

ERROR MESSAGE
  ERROR!!! <TIMESTAMP>, <APPLICATION_NAME>-31017, <SESSION_IDENTIFIER>: A startup key for <ADDITIONAL_DATA> was presented a second time & refused as a replay!

FILE
  /convertCore.php

FATAL
  NO

LOGGED
  YES

ERROR DESCRIPTION
  A manager startup key that had already been spent was presented again.
  A startup key is an HMAC over a short time bucket and is valid for the current window and the one before it.
  A key that crosses a process boundary is now spent the moment it validates, and a second process presenting the same key is refused however soon it happens.
  Time alone cannot make a leaked key dead. Whoever holds a copy validates it against the same clock this application does, so the window decides only how long they have and never whether they succeed. Spending the key is the part this application controls.
  The key is also carried in the environment rather than on the command line, because /proc/PID/cmdline is world readable and a manager process runs for days.
  CAUSE. Almost always a second launch of the same manager role within the same window, such as a service unit and an operator both starting the listener at once.
  It is also what a replay of a captured key looks like, so a run of these with no matching launch is worth investigating.
  RESOLUTION. Start the listener once. Run --status to see what is already running, and --stop-listener before starting it again.
  The ledger of spent keys lives in the manager socket directory and holds hashes rather than keys, so reading it grants nothing. Entries older than three windows are dropped automatically.
  This control defends against a key that leaked, not against an account that holds the install secret.
  Deleting the ledger un-spends a captured key, and the only accounts that can delete it are root and the web server user, both of which can already read the secret and mint a valid key directly. Losing the ledger to either of them costs nothing that was not already lost.
  The directory holding it sits inside the data location, owned by the web server user, so an unprivileged local account cannot remove it. That is the account this control exists for.
