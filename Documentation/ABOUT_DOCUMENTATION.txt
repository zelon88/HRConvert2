--About The Documentation Paradigm--

All reference materials are centrally housed inside the Documentation folder located at the root of the repository.

Every core administrative subject must be fully detailed using a matching pair of specialized informational files.

The framework enforces an absolute segregation between raw technical mechanics and user-facing instructional content.
----------------------------------------------------------------------------------------------------------------------------------------------------------------

----------------------------------------------------------------------------------------------------------------------------------------------------------------
--The Plain Text File Flavor--

The plain text format utilizes the standard .txt file extension to serve as the absolute source of truth for the codebase.

These documents are designed to remain universally readable in any text reader on any operating system without processing.

Each text file acts as a rigid, uniform, and hyper-concise engineering specification stripped of unnecessary fluff or prose.

Every informational statement must be direct, containing nothing but explicit technical facts, definitions, or instructions.
----------------------------------------------------------------------------------------------------------------------------------------------------------------

----------------------------------------------------------------------------------------------------------------------------------------------------------------
--The Markdown File Flavor--

The rich media format utilizes the standard .md file extension and must match the precise base name of its plain text sibling.

These files transform the strict engineering data from the text version into a highly digestible, engaging layout for humans.

The styling resembles a premium, colorful user manual that adds clear aesthetic value for hobbyists who enjoy interacting with it.

The layout heavily leverages markdown tables, clear bullet structures, visual warning blocks, bold text anchors, and color.
----------------------------------------------------------------------------------------------------------------------------------------------------------------

----------------------------------------------------------------------------------------------------------------------------------------------------------------
--The Plain Text File Layout--

Every plain text file opens with the same header, between two rules of 160 dashes.

  COPYRIGHT INFORMATION ...      The application, the date the file was created & the author.
  LICENSE INFORMATION ...        The license & where to read it.
  APPLICATION INFORMATION ...    What the application is.
  FILE INFORMATION ...           The version of the file, then what the file is for.
  HARDWARE REQUIREMENTS ...      What the application runs on.
  DEPENDENCY REQUIREMENTS ...    What the subject of the file needs.
  <3 Open-Source                 The last line before the closing rule.

Each block is its label, the lines under it & one blank line. Nothing else goes inside the
header, & a section placed there splits it in two where nobody reading it will look.

Every section after the header is an opening rule, a title between two pairs of dashes, a
blank line, the body & a closing rule. One blank line separates a closing rule from the next
opening rule.

  ----------------------------------------...
  --About The Subject--

  The body of the section.
  ----------------------------------------...

A title names one subject & is written in title case. A subject too large for one section
is two sections, never a title inside another section's body. A subheading is written the
same way in sentence case & may sit inside a body. The case is the only thing that tells a
reader, or a checker, which of the two a line is.

The version in FILE INFORMATION is changed by the maintainer & by nothing else.

Older files use rules of 83 dashes & titles written as -----TITLE-----. That is an older
style rather than a defect, & those files keep it.

Documentation/Build/hrconvert2-doccheck.py holds every plain text file to this layout & holds
ERROR_DESCRIPTIONS.txt to its own. Run it from the installation root after changing a
document. ABOUT_QUALITY_CONTROL.txt says what it checks & what it cannot see.
